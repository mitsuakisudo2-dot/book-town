# BookTown の使い心地の見直し

「仕様どおり動くか」は通しの確認（`tests/*-journey.mjs`）と CI が見ます。この手引きは、その先の「迷わず使えるか」「使いたくなるか」を、毎回同じ物差しで見るためのものです（プロジェクトの指示の3章と9章「製品としての完成」）。

見直すだけで、直すのは見直しのあとです。見つけたことは直す前に一覧にし、小さく確かなもの（文字、余白、押せる大きさ）はそのブランチで直し、体験や仕様が変わるものはけにーさんに聞きます。

## 1. 画面を実際に動かす

コードを読むだけで判断しません。デモのビルドを立てて、スマホの大きさで触ります。

```bash
env -u NEXT_PUBLIC_SUPABASE_URL -u NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY pnpm build
python3 -m http.server 5173 --bind 127.0.0.1 --directory out &
```

- Playwright（`@playwright/test` の `chromium`、`executablePath: process.env.BOOK_TOWN_CHROME || undefined`）で、**390×844 と 320×568**（いちばん狭い幅）を、`hasTouch: true, isMobile: true` で開きます。パソコン幅（1280）も一度は見ます。
- 見る画面のスクリーンショットを撮り、Read で画像として見ます。撮った画像はスクラッチパッドに置き、リポジトリに入れません。作業用の `tests/zz-*.mjs` もコミットしません。
- 初めての人で見ます。localStorage を空にした新しいコンテキスト（デモの街）と、ログインしたばかりの空の街（`tests/login-journey.mjs` のビルド）の両方が要る変更なら両方。
- 既存の部品が使えます: 読める濃さ `expectReadable`（`tests/journey-contrast.mjs`）、キーボードを勝手に出さない `expectNoKeyboard`（`tests/journey-keyboard.mjs`）、小窓を閉じたあとの待ち `layersSettled`（`tests/journey-layers.mjs`）。

## 2. 物差し

変更が触る画面ごとに、上から順に見ます。当てはまらない項目は飛ばします。

### 目的まで迷わず、少ない操作で
- 説明を読まずに、次に押す所が分かるか。いちばん大事な操作が、いちばん目に入る所にあるか（視線の順番と情報の優先順位）。
- 目的までのタップ数を数え、減らせる手順がないか。確認の小窓や途中の画面が本当に要るか。
- 機能が増えても画面が混まないか。足すなら見せ方を変えて、今ある物の上に重ねていないか。
- 押したあと、何が起きたかすぐ分かるか（押した反応、保存できた知らせ、読み込み中）。

### させるより、できることを示す（けにーさん 2026-10-18）
BookTown は読書家に何かをさせるサービスではなく、やりたいことが自然にできるサービスです。操作の数だけでなく、心の負担も少なくします。主に登録・整理・設定などの実用的な操作に当てはめます。
- **促すより選択肢を示す。** 「〜しましょう」「〜してください」「片づける」「並べましょう」と言わず、「〜できます」「まとめて設定できます」のように、何ができるかを伝える。
- **使い方に正解を押し付けない。** 記録だけの人、本棚を作る人、交流する人、どれも正しい。特定の行動を当然のものとして扱わない。
- **目的を果たしたあとに新しい作業を求めない。** 本を登録したら、それで完了。追加の設定をしなくても気持ちよく終えられる（何もせず［完了］で閉じられる、未完了のような印や言葉を出さない）。
- **説明を足す前に、画面で分かるようにする。** ボタン名・見出し・配置・選んだ状態で伝える。ただし誤操作やデータが消える所では、説明と確認を省かない。違う考え（読書の状態と持っている本など）は見出しを分けて見た目でも区別し、まとめて変える操作はそうと分かる言葉にする。
- **楽しい問いかけは別。** 「人生の9冊」「今日のお題」のように、思わず参加したくなる問いや企画は BookTown の魅力。楽しむきっかけと、要らない作業の要求を分けて考える。

### BookTown の決まり（CLAUDE.md）
- **0 を出さない。** 人数・件数が0の欄は出さないか、行動の入口（本屋を開く、書店めぐりに出かける など）に置き換える。数は順位にせず事実の言葉にする。検索の結果に件数を出さない。
  - 例外: 読書の記録の自分の統計は0も出してよい（自分の本棚の中の順位もよい。連続記録は出さない）。
- **戻るは直前の画面とタブへ。** タブ・絞り込み・路地はアドレスに置き換えで持つ（`src/lib/url-state.ts`）。小窓と手に取った本は1回の戻るで閉じ、手で閉じたら履歴に残らない（`src/lib/back-layer.ts`）。小窓から別の画面へは `leaveLayers`。リロードしても同じ場所に戻るか。
- **書きかけを失わない。** 読書家が書いたり並べたりした物は、保存が確かめられるか本人が消すと決めるまで残る（`src/lib/kept-draft.ts`、`KeptDraftNote`）。断られた保存を成功の知らせで閉じない。
- **キーボードを勝手に出さない。** スマホでは、開いただけで欄にフォーカスしない。書く画面だけは開いたらすぐ書ける（X 式）。欄にフォーカスしても画面が拡大されない。
- **本棚が主役。** 本・棚・POP を別々に触れる形を保ち、よくあるカード型の読書アプリに寄せない。
- **表紙はそのまま。** 切り抜き・重ね描きをしない。Google の表紙には「powered by Google」とリンク。表紙のない本は装丁カード。
- **見本と、ログインしていない人。** 見本へのいいねなどは断って一言だけ伝える（`src/lib/sample-notice.ts`）。ログインしていない人が変えようとしたらログインに招く。どちらも行き止まりにしない。
- **ネタバレ。** 読む人の「ネタバレの表示」の選択どおりに、たたむ・一覧に出さない・すべて表示になっているか。
- **見せてはいけない物。** 非公開の本棚や登録した本の題名、たたんだ投稿・ポスターの中身が、別の画面（一覧、ホーム、本のページ）から漏れていないか。

### スマホで押しやすい・読みやすい
- 押せる所は 44px 以上（`min-height: 44px` が街の基準）。隣の押せる物と近すぎないか。親指の届く下側に主な操作があるか。
- 320px 幅で横にはみ出さない（横スクロールが出ない）。長い題名・名前・英数字の続く文字で崩れないか。
- 文字は背景から読める濃さか（`expectReadable`、4.5:1）。夜や色の違う店内でも。
- 下のタブ・画面の端・iPhone の下の帯に、押せる物が隠れていないか。

### 空・失敗・遅いとき
- 空の状態（本が0冊、フォロー0人、便りが無い）に、次に何をすればいいかの入口があるか。
- 失敗したとき、責めない平易な言葉で、どうすればいいかが書いてあるか。書いた物は残っているか。
- 遅い通信で、押した物が二度送られたり、画面が飛んだりしないか。

### 楽しいか
- 本を登録する、棚を作る、書店を訪ねる、人と交わる、その行為そのものに手応え（動き、音のない小さな喜び、街の世界観）があるか。
- 事務的な管理画面に見えていないか。BookTown の言葉づかい（本屋、店主、便り、書店めぐり）とそろっているか。

## 3. 報告の形

見つけたことを、重い順に並べます。各項目は1〜2行で「どの画面の、どの幅で、何が起きて、読書家がどう困るか」と、直し方の案。スクリーンショットがあればその場所も。

- **止める**: 決まりを破る（0 が出る、戻るが飛ぶ、書きかけが消える、見せてはいけない物が見える）、目的に届かない。取り込む前に直す。
- **直す**: 迷う、押しにくい、はみ出す、読みにくい。そのブランチで直すか、直さない理由を書く。
- **相談**: 体験や仕様が変わる案、楽しさを足す案。けにーさんに聞くか、後の改善として記録する（スレッドを開けたままにする理由にはしない）。
- 実際の利用者の反応が要る所は「検証待ち」と分けて書く。

けにーさんへの報告は平易な日本語で、技術の言葉と内部の名前を避けます。見つからなかったら「見直しで止める所はありませんでした」の1行で足ります。
