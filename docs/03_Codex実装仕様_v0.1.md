## 画面案A: 本の街（最優先UIプロトタイプ候補）

### レイアウトと操作

- **縦方向**: 1軒ずつ別の個人書店が続く。店の名前と特色、原則2棚（仮）がまとまりとして見える。
- **横方向**: それぞれの棚をスワイプし、本の背表紙・面陳を眺める。
- **本をタップ**: 同じ画面に前景／オーバーレイを開く。表紙、書誌、店主のPOPが第一優先。
- **本を開いた状態で横スワイプ**: **その棚で隣に置かれた本へ**。店主が決めた配列を保つ。
- **閉じる**: 元の店・元の棚・元の横スクロール位置に戻る。
- **別の書店の本に進む**: 本→店主→別の棚→別の店という説明可能な道を見せる。
- **匿名・未ログインで閲覧可能**が有力案。保存や投稿時に必要なら登録導線を出す。
- **空き地（提案）**: まだない店舗や未展示の本の存在を嘘なく示す。これは「無限表示」という目標と両立できるよう検証する。

### 画面要素の優先度

1. 本棚・本・店主のPOP。
2. 店名・店主の選書理由が伝わる必要最小限の情報。
3. 本を手に取った後の「読みたい」「伝える」「本を添えて薦める」。
4. 公開が許可された出来事の控えめな案内（店と店の間。表示しない場合も可）。
5. 反応数・コメント数の大量露出、広告的な煽り、強制モーダルは避ける。

### UI受け入れ条件案

- [ ] 320px程度の狭い画面でも本棚が読め、横スクロールで棚の内容を確認できる。
- [ ] **縦スワイプが横スワイプに誤判定されにくい**。実端末で検証する。
- [ ] 本を開き、横操作で店主が並べた順の隣の本へ進める。
- [ ] 本を閉じると、縦の訪問位置と横の棚位置が維持される。
- [ ] スワイプだけでなくタップ可能な「前の本／次の本」「閉じる」がある。
- [ ] キーボード・スクリーンリーダー・フォーカス管理を考慮。アクセシブルな非ドラッグ操作を用意。
- [ ] 同じ書店ばかりの繰り返し表示を避ける。探索済みの場合は誠実に伝える。
- [ ] 通りの棚に勝手なコメント数、人気指標、匿名投稿との紐付きを表示しない。

## 画面案B: 本を手に取る（本詳細の前景）

**情報の順番**:

1. 表紙、書名、著者。
2. **「この棚に並べた店主」**、POP、関連棚の位置。
3. 読みたい保存、任意の店主宛て付箋、公開の会話への入り口（後者2つは検討案）。
4. 店主が並べている別の本（店主が明示的に「愛した」ものと、単に陳列したもののコピーを区別）。
5. 作品についての会話・感想はネタバレ保護と明瞭な境界を付ける。

**隣の本**は棚の手動配置順。アルゴリズムでこの順番を変えない。

## 画面案C: SNS（別の入口）

読書感想に加えて、読書環境・積読・本屋巡り・雑談・質問などを自由に投稿できる。書籍への紐付けは任意。

通常投稿は最新性に閉じず「まだ続いている話」も発見できる。ただし古い人気投稿が上位を独占しないよう、新規・少反応・未知の会話も候補に入れる。

- SNSのホームナビゲーション、公開／非公開付箋との分離、コメントの所属先は**未決定**。
- 「本への手紙」（読了後の深い感想）は一般投稿とデータ基盤を共通化できても、表示面・ネタバレ保護・長期保存の扱いを区別。
- 投稿・画像・返信・フォロー・ブロック・通報・削除など、実サービス化時に必要な最小限の安全運用を確立してから公開する。

## 推薦アルゴリズムの段階的設計案

### フェーズ0: ほぼ利用者がいない時期

登録時に複数質問を強制せず、**最初の一軒を設計された偶然で見せる**。

- 未訪問の公開書店を優先。
- 多様なジャンル・店主を順に見せる。
- 無関係なジャンルを見せる場合も説明を添える。なぜ出てきたか誤認させない。
- 実在しないPOPやいいね・訪問者数を生成しない。
- 店舗が尽きたら既訪問店への帰り道、未展示書籍、空き地などの候補を示す。

### フェーズ1: 利用者が自分の反応を持つ

- 「読みたい」を押した本と、店主の紹介・棚の関係。
- 店主のお気に入りや人生の9冊など、**本人が意図を表明した**情報。
- 店主の別の棚、ほかの店主が置く同じ本、会話で添付された関連本。
- **能動的な角**（店主をたどる）と**偶然の角**（未知の趣味を見せる）の両方。
- 人気と投稿数だけで推薦を固定せず、露出の分散、同一店主の連続抑制、見飽きた作品の抑制を取り入れる。

### フェーズ2: データが増えた後

- 「どのPOPに興味を持ったか」から、書誌のジャンルだけでは見えない感性の関連を推定。
- 新規店と少人数の声を発見可能に保つ。
- 成功の検討指標は、単なる滞在時間だけでなく**読みたい本との出会い、感謝、再訪、交流、読書につながったか**。

重み（例: 60/25/15）は**議論の例示にすぎない**。固定しない。

## データ設計の叩き台（本番スキーマ未確定）

既存の Book, Reader, Shop, Shelf, ShelfItem を尊重し、将来の拡張候補として次を区別する。

- `Book` と版（ISBN）／作品同一性。
- `ShelfItem`: 棚に置いた書籍、表示方法、配列順、任意のPOP。
- `UserBookRelationship`: 読了、読みたい、お気に入り、人生の9冊など**意味の違う関係**。
- `DiscoverySource`: どの書店・棚・POPを経由して興味を持ったか。**これだけでは感謝や好意を断定しない**。
- `Post`: 任意の書籍関連付けを持つ自由投稿。
- `Reply` /`BookAttachment`: 文章に本を添えて薦める行為。
- `PrivateNote`（提案）: 店主への付箋。公開コメントとアクセス制御を明確に分離。
- `BookLetter`（提案）: 読了者向けの継続的な感想。通常投稿と同一テーブルにするかは未決定。
- `ActivityEvent`（提案）: 棚替え、読了など公開許可された活動の案内。
- `VisibilitySettings`, `Block`, `Report`, `NotificationPreferences`。

**匿名投稿と店主IDの安易な結合をしない**。読みたい／読了の公開はデフォルトでオフ。生の活動ログを他者に漏らさない。公開される推薦理由は同意のある情報のみ使用。

## 進め方: 既存試作品を壊さず段階的に

1. **UIだけの検証版**: モックデータで縦の通り、横の棚、本の前景、隣の本へ移動と戻り位置を試作。既存ルートから分離するか切り替え可能にする。
2. **店の育成**: 1冊から下書き棚を作る操作、2棚／容量の使い心地、編集と展示の分離を検証。
3. **会話の試作**: 公開コメント／非公開付箋／本を添える返信をモックで比較。実装前に誰に見えるかを決定。
4. **複数ユーザー対応**: 認証、DB、権限、画像、通報・ブロック、削除、セキュリティ。静的エクスポート等の現行構成と互換性を再確認して計画。
5. **推薦**: 少人数ルールベース → 人の感性を経由する経路 → 公平性・多様性検証。機械学習は必須ではない。
