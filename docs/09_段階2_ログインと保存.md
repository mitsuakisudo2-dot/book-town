# 段階2：ログインと保存

> 更新日: 2026-10-14 / 状態: その3b（店内と書店めぐりの保存）を実装。通報・ネタバレの表示・表紙の削除依頼の安全な初期値と、注釈モード（運営の注釈）を追加。マイライブラリの表（L1。アプリはまだ読まない）を追加

今はデータがブラウザの中（localStorage）にしかなく、ログインも本物のユーザーもいません。段階2では、Supabase にデータベースとログインを置き、最初の店主たちが本当に本屋を開けるようにします。技術構成はユーザーから Claude に一任されています（2026-10-12）。

## 決めたこと

- **保存先は Supabase**（Postgres、ログイン、画像の保存）。
- **段階2では静的な書き出し（`output: "export"`）を続け、ブラウザから Supabase を直接呼ぶ。** 誰が何を読めて書けるかは、すべてデータベースの行レベルセキュリティ（RLS）で決める。アプリ側の判定だけには頼らない。
  - 理由: スマホアプリ化（Capacitor）と相性がよく、自前のサーバーなしで安全に作れる。本屋ごとの紹介画像（OGP）のためのサーバー処理は段階4で足す。
- **ログインは、メールに届く6桁のコードか、メールのリンク。** パスワードはない。コードはWebでもスマホアプリでも同じ手順で使え、リンクは同じ端末のブラウザで開くときに便利。
  - 最初の20人は招待制なので、Supabase の新規登録を止め、店主のメールアドレスをダッシュボードの Authentication → Users → Add user で先に登録しておく。
  - メールの件名と本文は `supabase/templates/magic_link.html`（コードとリンクの両方）。Supabase は独自のメール送信（SMTP）を設定するまでメールの文面を変えさせず、標準の英語のメールにはリンクしか入らない。それまではリンクでログインする。コードの有効期限は10分。
  - リンクの戻り先はログイン画面（`/login/`）。Supabase の Authentication → URL Configuration で、Site URL を本番のURLにし、Redirect URLs に本番と、試したいPRのブランチのURL（末尾に `/**`）を入れる。リストにない戻り先は Site URL に置き換わるので、ほかのサイトにログインの鍵が渡ることはない（`pnpm test:supabase` で確認）。
  - プレビューのURLは `*-booktown1.vercel.app` のようなワイルドカードで許可しない。`*` はハイフンをまたぐので、名前が `booktown1` で終わる他人の Vercel チームのURLにも当てはまってしまう。ブランチごとの決まったURL（`book-town-851k-git-<ブランチ名>-booktown1.vercel.app`）を1つずつ足す。
  - Google と Apple のログインは、ストアの審査条件に合わせてアプリ公開前に足す。
- **公開先は Vercel**（プロジェクト `book-town-851k`、本番は https://book-town-851k.vercel.app/ ）。main への取り込みで本番が更新され、PRごとに確認用のURLができる。ただし `claude/` で始まるブランチ（Claude の作業ブランチ）では確認用のURLを作らない（`vercel.json` の `git.deploymentEnabled`）。Vercel の無料プランはデプロイが24時間で100回までで、確認用のURLで使い切ると main を取り込んでも本番が作られないため（2026-10-13 に一度起きた）。確認したい `claude/` のブランチは、下の Vercel の deploy で作る。ビルド時に `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`（または旧名の `NEXT_PUBLIC_SUPABASE_ANON_KEY`）を渡す。どちらも公開してよい値で、なければデモのまま動く。Vercel では種類を「Config」にして、Production、Preview、Development のすべてに入れる（「Secret」で保存すると書き込み専用になり、あとから種類を変えられないので、消して作り直す）。収益を得る段階では Vercel の有料プランが必要になる。
- **1人1店舗**（`shops.owner_id` に一意制約）。複数店舗にするときはこの制約を外す。
- **数を見せない。** フォロワー数や反応の数は、他の人が数えられないようにしてある（思想メモ「数で価値を決めない」）。反応を見られるのは、反応した人と受け取った人だけ。画面でも、本屋のフォロワー数は店主本人にだけ「この数はあなたにだけ見えています」と添えて出す。デモの書店とデモの読書家は、今までどおり数を出す。

- **非公開の棚**: 店主のアプリは全部の棚を `shop_private` にだけ書く。公開する棚は、データベースのトリガーが `shops.public_shelves` に写す。店主は `public_shelves` と `public_scene` を自分では書けない（列ごとの権限）。アプリに不具合があっても、非公開の棚が他の人に届くことはない。
- **店内（Scene）も同じ仕組み。** 店主のアプリは店内の全体を `shop_private.scene` にだけ書き、データベースが公開してよい部分を `shops.public_scene` に写す（関数 `public_scene_of`）。規則は画面の `publicStoreScene` と同じで、置いていないもの、公開でない棚の段、非公開や棚に置いていない本と、その上のPOPを除く。写しの `storeId` はデータベースが本屋のIDに書き換える。
- **手入力の本は、使われている場所で読める。** 手入力やスキャンで登録した本（`source = 'manual'`）を読めるのは、入力した人と、その本を自分で使っている人（読みたいなどの印、マイライブラリ（外していない本）、出会いの記録、投稿とひとりメモ、記録、読書、人生の9冊、ポスターと下書き、自分の本屋の棚と店内。非公開のものも含む）。ほかの人とログインしていない人には、公開の場で使われているあいだだけ見える：開店中の本屋の公開の棚と店内、ひとりメモ以外の投稿（返信、一緒に読むメモ、たたんだ投稿も）、公開の記録、人生の9冊、貼り出したポスター、一緒に読む記録（終わったものも）。運営が隠したものと隠した人のもの、深刻な通報で確認まで見えなくしているものは数えない。ブロックは数えない（ログインしなければ同じものが読めるため）。目録の本（`ndl`）は誰でも読める。
  - 決めるのはデータベースの関数 `private.book_is_listed`（公開の場で使われているか）と `private.book_is_mine`（読む本人が使っているか）で、`books` の読み取りの方針がこの2つを聞く（`20261024000000_hide_registered_titles.sql`）。本のIDを持つ表や列を足すときは、方針は変えずに、この2つを `create or replace` で広げる（関数の `set` の行は残す）。広げ忘れると、その本が画面から消える（本を指す外部キーが増えると、`pnpm test:db` の「every book a reader sees used, they read」が気づかせる）。もう1つ、`private.book_is_shared`（フォロワー限定の記録の本を、その記録を読める人に見せる。`20261029000000_visibility.sql`）も同じ方針が聞く。フォロワー限定で使える物（棚など）を足すときは、こちらも広げる。
  - 速さ：方針は、読む人に見せない手入力の本ごとに、この2つを聞く。自分の本屋は ID を先に見つけ、その1軒の棚だけを探す。公開の棚と店内は、本屋が何軒でも GIN の索引で探す（本屋が数百軒より少ないと、データベースは棚の中身を開く手間を数えずに1軒ずつ読むほうを選ぶので、`book_is_listed` は順に読む計画を使わない設定にしてある）。街の新しい300冊は `books_created` の索引で新しい順に読み、読める本が300冊になったところで止まる。それより新しい、見えない手入力の本の数だけ時間がかかる。`pnpm test:db` の「a book is asked about without searching every shop」が、この計画を確かめる。
  - 本のIDを知っている人は、その本に印を付けたり投稿したりでき（外部キーは RLS に関係なく確かめられる）、そうすると題名が読める。手入力の本のIDはでたらめな UUID で、ほかの人が読める行に載るのは公開の場で使われている本だけなので、これで足りるとしている。表紙の削除依頼（本への通報）は「使っている」に入れない。IDを知らない本の題名を読む手段にしないため。
  - 元に戻すときは、新しいマイグレーションで読み取りの方針を `using (true)` に戻す。行は書き換えていない。
- **店内に並ぶ本の一覧。** `shops.public_scene_books` と `shop_private.scene_books` は、店内に置かれた本のIDをデータベースが自動で並べた列。街の読み込みは、店内を全部読まずにこの一覧で本を集める。
- **他の人の本屋のデータ**は、読み込むときに必ず検証する。棚は `cleanShelves`（`src/lib/town-remote.ts`）で、形が崩れた棚や知らない本を落とす。店内は `sceneFromRow`（`src/lib/walk-remote.ts`）で `validateScene` を通し、崩れたものは書店めぐりに出さない。
- **ブロックは双方向に効く。** どちらからも相手の本屋、投稿、一緒に読む記録が見えなくなり、フォローは両方向とも外れ、新しいフォローや反応、返信もできない。プロフィールだけは見えるままにして、ブロックした人が自分の一覧から解除できるようにしている。誰が誰をブロックしたかは、本人以外には調べられない。
- **ブロックの画面**（管理表43、`src/components/BlockReader.tsx`、`src/lib/blocks.ts`）。相手のプロフィールの「通報」の隣と、便りの「…」から、確かめる小窓（「相手には知らされません」「あとで設定から外せます」）を通してブロックする。ブロックした人のプロフィールには名前と「ブロックを解除」だけを出し、設定の「ブロックした読書家」に一覧と［解除］を出す（いるときだけ）。解除はトーストの「元に戻す」で取り消せる。
  - 街は `TownState.blocked` に相手のIDを持ち、`blocks` の行として足す・外す（`planWrites` の relation）。ブロックした瞬間に、相手の便り・本屋・記録・一緒に読む記録・ポスター・ひとこと、自分の便りへの相手のいいねを街から外す（`withoutReaders`）。自分の返信は外さない（街から消えた自分の便りは、次の保存で削除されるため）。読み込みでも、あとから届く便りでも、データベースに頼らず同じように外す。
  - 解除しても、外したものは次に街を読み込むまで戻らない（トーストでそう伝える）。フォローは戻らない。
  - 見本とデモの街には出さない（通報と同じ）。ログインしていない人には、ログインに招く。
  - **まだ DB で止めていないこと（管理表43の残り）:** ブロックされた側からも、ブロックした人の人生の9冊（`profile_nine`）と、ブロックした人が相手の投稿や POP に付けた反応（`post_reactions`、`pop_reactions`）が見える。ブロックした側の画面では、相手の9冊を出さず、相手の反応は数えない。
- **通報**は運営が Supabase のダッシュボードで読み、状態を変える。アプリストアの審査でも、ブロックと通報は投稿のあるアプリに求められる。
- **返信は1段まで**、ひとりメモには返信できない。どちらもデータベースのトリガーで止める。
- **退会**すると、その人のデータはすべて消える。手入力した本だけは目録に残り、作成者が空になる（公開の場で使われているあいだは読めるが、どこにも使われていなければ、もう誰も読めない）。ただし運営の注釈（`site_notes`）は画面の写しを含むので、退会した読書家の名前や言葉が写っていることがあり、運営が消すまで残る（通報の行と同じく、運営のための例外）。
- **退会した人への通報と、運営の非表示の記録は残る。** 退会した人のプロフィールへの通報（`reports.target_id`）と運営が隠した記録（`moderation_hides.target_id`）は、ほかの人の通報や運営の記録なので、投稿が消えたときと同じく運営のために残す。どちらも、もう何にもつながらない ID だけが残る。

## アカウント削除の型（2026-10-16、管理表の2）

表を足すたびに、退会で消し忘れる所とブロックの抜けが出ないようにする仕組み。

- **台帳。** `tests/fixtures/account-tables.ts` に、全部の表について「人を指す列が退会でどうなるか」（行ごと消える `delete`／列が空になる `forget`）と「ブロックした相手に見えるか」（本人だけ `own`／ブロックで隠す `blocks`／別の表を通して読む `via`／API から誰も読めない `nobody`／理由つきで見える `open`）を書く。
- **台帳と DB の照らし合わせ（`tests/account-tables.test.ts`）。** 次のどれかがあると `pnpm test:db` が止まる。
  - 台帳にない表がある。
  - 人（`auth.users`・`profiles`）を指す外部キーが、退会を止める形（on delete の指定なし）になっている。
  - 外部キーの消え方と台帳が違う。
  - 人と一緒に消える行（投稿、店など。そこから連鎖して消える表も）を指す外部キーが、連鎖も空にもならない形になっている（退会が止まる）。
  - 外部キーのない uuid の列が、人を指すかどうか台帳に書かれていない（主キーでも、`id` という名前の1列の主キー以外は同じ）。
  - 新しいスキーマやビューの表も台帳に要る（Postgres と auth の分だけ除く）。
  - `blocks` の表の読む規則が `is_blocked_with` を聞いていない（規則が呼ぶ関数の中で聞いていればよい）。`own` の表の規則が `auth.uid()` を聞いていない。`nobody` の表を API から読める。
  - わざと間違えた表を足して、それぞれ止まることもテストで確かめている。
- **退会の通し（`tests/database-policies.test.ts` の「deleting an account removes everything it owned」）。**
  - 台帳で人を指す列の全部に、消える人（ベン）の行を入れる。
  - 退会の前に、ベンと互いにブロックしたチーとして、`own` と `blocks` の表を読み、ベンの行が1つも見えないことを確かめる（規則の字面だけでなく、実際に読めるか）。
  - 退会のあと、全部のスキーマの全部の表の全部の列（文字や JSON の中も）に、ベンの ID が残っていないことを確かめる。台帳で「残す」とした列（上の通報と非表示）だけは除く。控えの中の確かめは `tests/db-copies.test.ts` にある。
- **表を足すとき。** 台帳に1行足し、退会の通しで消える人の行を入れる。どちらかを忘れると止まる。
- **今あるブロックの抜け**（43 で決める）: ブロックした相手にも、人生の9冊（`profile_nine`）が見える。投稿を書いた人と本屋の店主には、ブロックした相手からの反応（`post_reactions`、`pop_reactions`）も見える。台帳に理由を書いて残している。

## 退会の画面（2026-10-16、管理表の45）

## メールアドレスの変更（2026-10-18、管理表の107）

## パスキー（2026-10-18、管理表の107）

メールのコードの代わりに、指紋・顔・端末の画面ロックでログインする。前もって作った人は、メールが読めなくなっても入れる（けにーさん 2026-10-18「パスキーと窓口」）。Supabase の機能（実験的と書かれている）で、費用はかからない。

- **入口。** 作るのと消すのは、設定の「アカウント」の「パスキー」か、アカウントの画面の「メールのコードなしでログイン」から開く `/login/?change=passkey`（`loginPath({ passkeys: true })`）。作ったパスキーは、名前（Supabase が端末やパスワードの管理アプリから付ける。「iCloud Keychain」「Google Password Manager」など）、作った日、最後に使った日を並べる。1つもないときは何も並べず、作るボタンだけ（0 を出さない）。消すときは「消すと、このパスキーではログインできなくなります。消す／残す」と聞く。作るように促す言葉は出さない（何ができるかだけを書く）。
- **ログイン。** ログインの画面の最初に「パスキーでログイン」。アドレスは聞かない（パスキーが誰のものかを持っている）。ブラウザの窓を閉じたときは何も言わない。パスキーを使えないブラウザでは、ボタンを出さない。
- **作れる所。** パスキーは決めたドメイン（relying party）に結びつく。本番は `booktown.page`（と `www.booktown.page`）で、`book-town-851k.vercel.app` やブランチのURLでは作れず使えない（「このページやブラウザでは、パスキーを使えません」）。**`booktown.page` をあとから変えると、それまでのパスキーがすべて使えなくなる。** 1人10個まで（Supabase の上限）。
- **持つもの。** Supabase が `auth.webauthn_credentials` に、公開鍵、名前、作った日と使った日を持つ。秘密の鍵は端末かパスワードの管理アプリにあり、BookTown には来ない。端末の側には、パスキーの名前としてそのときのメールアドレスが残る。退会すると、Supabase がアカウントと一緒に消す（外部キーの cascade）。
- **気をつけること。** ログインしている人なら、確かめなしでパスキーを作れる（Supabase の動き）。ほかの人がその端末を開けたまま使うと、その人のパスキーが作れてしまうので、知らないパスキーは一覧から消せるようにしている。作ったことをメールで知らせる仕組みは Supabase にない（作る前にメールのコードで確かめ直すことも、Supabase の側では求められないので、画面だけで求めても盗んだセッションは止められない）。supabase-js はパスキーの問い合わせをしてからブラウザの窓を開くので、遅い回線の Safari では押した直後の扱いが切れて窓が開かず、何も言わないことがありうる（手元では確かめられていない）。人間の確認（46 の Turnstile）では `signInWithPasskey` にもトークンを渡す（Supabase はパスキーのログインの最初の問い合わせにも CAPTCHA を求める）。確認は画面を開いたときに始めておき、押したときに答えがもうあればそのまま渡すので、窓はほぼすぐ開く。答えがまだなら最大15秒待つので、その間に押した直後の扱いが切れることはありうる。
- **本番の設定。** `supabase/hosted-auth.json` の `passkey`（`passkey_enabled`、`webauthn_rp_id`、`webauthn_rp_display_name`、`webauthn_rp_origins`）。手元は `supabase/config.toml` の `[auth.passkey]` と `[auth.webauthn]`（relying party は `localhost`。IP アドレスはなれないので、確かめは `localhost` で開く）。
- **確かめ。** `pnpm test:supabase` の `tests/supabase-passkey.test.ts`（本物の Supabase と Chromium の仮の認証器で、ログインしていないと作れない、同じ端末で2つ目は断られる、コードなしで入れる、アドレスを変えても入れる、ほかの人のパスキーは見えず消せない、消したパスキーと退会した人のパスキーでは入れない、窓を閉じても何も言わない）、`pnpm test:account`（言葉の対応）、`pnpm test:settings`、`pnpm test:login` の「パスキー from 設定」（`localhost` で開いて、作る、2つ目、コードなしで入る、消す前に聞く、消したあとは入れない）。

## 移す工事の前の控えと戻す手順（2026-10-16、管理表の3）

今あるデータを移す工事（作品と版など）を安全に始めるための手順。Supabase は無料の段で毎日の控えがないので、工事のたびに、移す表の控えを DB の中に取る（毎日の控えは管理表の46）。

- **控えの置き場所。** 同じ DB の `keep` スキーマ。API にも、ログインした人にも、service_role にも開いていない。行は DB の外に出ないので、公開のリポジトリにも Actions のログにも載らない（エラーの文も、表の名前と件数だけにしている）。マイグレーション `20261026000000_moving_copies.sql`。
- **移す工事のマイグレーションの書き方。** 1つのファイルに、控え → 移す → 照らし合わせ、の順で書く。

  ```sql
  select private.keep_copy('20261101000000_works',
    array['public.books', 'public.posts']::regclass[]);
  -- ここで移す
  select private.check_copy('20261101000000_works');
  ```

  - 控えの名前は、そのマイグレーションのファイル名（拡張子なし）。
  - 移す表と、その表をトリガーで追いかけている表（`book_marks` と `library_entries` など）を全部控える。主キーのない表は控えられない。
  - `keep_copy` は控える表を全部まとめて押さえ、ファイルの終わりまで書き込みを待たせる（読むのは止めない）。押さえるのに10秒待っても書き込み中の人が終わらなければ、工事ごと止まる（もう一度流せばよい）。
  - `check_copy` は、控えにあった行が主キーで見つからない（失った行）か、外部キーの列が控えでは入っていたのに今は空か列ごとない（失ったつながり）を数え、1つでもあれば例外を出す。ファイル全体が1つのトランザクションなので、移した分も控えも取り消され、本番は元のまま。意図して減らす表は、つながりなら2つ目の引数、行なら3つ目の引数に渡すと、数えて記録するだけにする（`check_copy(名前, array['public.x']::regclass[])` はつながりだけ、`check_copy(名前, '{}', array['public.x']::regclass[])` は行だけ）。主キーが変わった表は行を照らし合わせられないので止まる。
  - 移す SQL も、行の値を含むエラーを出さないように書く（`raise exception` には件数と表の名前だけ）。Postgres 自身のエラー（一意や check の違反）は行の値を含み、Actions のログは公開のため。
  - `supabase db push` はファイルを1つのトランザクションで流すが、`create index concurrently` などは外で流す。控えを取るファイルにこれらと `begin`・`commit` を書くと、`pnpm test:db` が止める。
  - 照らし合わせた数（前後の件数、失った行とつながり）は `keep.copies.checked` に残る。Supabase の接続（select だけ）で読める。

- **戻すとき。** 新しいマイグレーションで `select * from private.restore_copy('20261101000000_works');` を呼ぶ（本番への書き込みなので、取り込みの了承が要る）。
  - 控えの行を全部書き戻す（なければ足し、変わっていれば控えの値に戻す）。親の表から順に書く。そのあいだ表のトリガーは止める（更新日時などは控えのまま）。
  - 控えのあとに増えた行は残る。消すときは3つ目の引数を `true` にする（その行から連鎖して消えるものも消える）。
  - 表を選ぶときは2つ目の引数に配列で渡す。
  - 控えのあとに親が消えた行（退会した人の行、消えた投稿への返信）は戻さない。親が消えたら空になる外部キー（set null）の列だけは、空にして戻す。
  - 戻したあとで、同じ値の一意の列（ハンドルなど）がぶつかると、全体が止まって何も変わらない。そのときのエラーは表の名前と SQLSTATE だけにして、行の値は出さない。
  - 行を1つずつ控えの値に戻すので、移す工事が2つの行のあいだで一意の値を入れ替えていると、戻すときにぶつかる。そういう工事を戻すときは、戻すマイグレーションで先にぶつかる値をよけてから `restore_copy` を呼ぶ。
  - 止めていたトリガー（もともと止まっていたもの）は、戻したあとも止まったまま。
  - 戻した表、戻した行、戻さなかった行、消した行の数を返す。
- **退会と控え。** 控えを取るとき、行ごとに「退会で一緒に消える人」を `keep_owners` の列に書いておく（その行の人への連鎖のほか、連鎖の外部キーをたどった先の持ち主。店の非公開の棚は店主、返信と反応は元の投稿の書き手）。控えがあるあいだに退会があると、`auth.users` のトリガー（`forget_in_copies`）が、全部の控えからその人と一緒に消える行を消し、元の表で空になる列（本の作成者）は空にする。元の表が運営のために残す行（その人への通報）は、控えにも残る。手で消した控えがあっても、退会は止まらない。
  - たどるのは人まで5段まで。もっと遠い表は `keep_copy` が断る（そのときは、たどり方を広げてから控える）。自分の表を指す連鎖（返信の返信）だけは5段で止まり、それより深い行は退会のあとも控えに残る（その人の行ではなく、ほかの人の返信。親が消えているので戻されず、`drop_copy` で消える）。今の返信は1段まで。
- **片付け。** 本番で確かめたら（管理表で「本番確認済み」）、次のマイグレーションで `select private.drop_copy('20261101000000_works');` を呼んで控えを消す。退会した人の行は控えからも消えるが、控えを長く置かない。開いている控えは「開発の引き継ぎ」に書く。
- **試したこと。**
  - `pnpm test:db`（`tests/db-copies.test.ts`）: 行を失う工事・つながりを失う工事・列を消す工事が丸ごと取り消されること、失わない工事が控えを残すこと、あとから壊したものを戻すと控えを取る前と全部同じになること、増えた行の扱い、選んだ表だけ戻すこと、トリガーが止まって戻ること、複合キーと自分の表を指す外部キーの戻し方、退会した人と一緒に消える行（店の非公開の棚、投稿への返信と反応）が控えからも消えて戻らないこと、戻せないときのエラーに行の値が出ないこと、手で消した控えがあっても退会できること、API の役から届かないこと、控えの名前と主キー、片付け。
  - 2026-10-16、手元の本物の Supabase（CLI 2.120.0、postgres は superuser でない本番と同じ形）で一度ずつ: 全部のマイグレーションが流れること、行を失う工事が取り消されること、控えを取って本を書き換え、投稿を消して記録を書き換えたあと、`restore_copy` で4つの表の中身（md5）が工事の前と同じに戻ること、認証の管理 API でアカウントを消すと控えからも消え、そのあと戻してもその人の行が戻らないこと、REST から `keep` と `private` に届かないこと、`drop_copy` で片付くこと。

- **まとめ方。**
  - 同じ ISBN は、原則として同じ版。ISBN のある本は、登録したその場でその版に入り、版の作品につながる。ISBN-10 はアプリが ISBN-13 に直して保存し、DB も13桁しか受け取らないので、同じ本は同じ番号になる。
  - 登録のときに題名や著者は比べない。運営の確認や照らし合わせで登録が止まることはなく、ほかの人の登録（非公開のものも）は、登録の結果にもエラーにも影響しない。ほかの人がその ISBN を登録しているかどうかは、登録の様子からは分からない。
  - 待つのは、同じ ISBN の別の登録が保存の途中にあるときだけ（同じ ISBN の初めての登録が同時に来ても1つの版になるように）。登録は保存されるまで版の行を押さえる。版があればその行を止め、なければ自分で作った行なので、あとから来た同じ ISBN の登録は、版があってもなくても同じように待つ（新しい ISBN のときだけ待たせると、待ち時間で分かってしまう）。押さえるのは行なので、何千冊をまとめて送られても DB 全体の鍵の表は埋まらず、止まるのはその ISBN の登録だけ。残る違いは、初めての ISBN では作品と版の2行を書く分だけ処理が数十マイクロ秒長いことで、ネットワークの揺れよりずっと小さい。`tests/db-works.test.ts` が、隠れた本があってもなくても、登録した人に分かることと押さえる行が同じで、300冊送っても鍵の数が増えないことを確かめている。
  - 本の ISBN を直すと（本人でも運営でも）、その本は新しい ISBN の版へ移る。ISBN を消すと、その本だけの作品になる。移ったことは履歴に残る。題名を直しても作品は変わらない。
  - 版どうし（ISBN が違う本や ISBN のない本）を1つの作品にするのは、運営がまとめたときだけ。まとめた結果は版ごと残るので、あとからそのどれかの ISBN で登録された本も、そのまま同じ作品に入る。
  - 方針は「誤ってまとめるくらいなら、まとめずに候補に残す」（10-16 12:10Z）。
- **次の工事（書誌マスタ）。** 版の書誌（書名・著者・出版社）を、国立国会図書館と openBD の公開データから裏側で入れ、登録の題名との食い違いを確かめる。比べる相手はこの公開の書誌だけで、ほかの人の登録とは比べない。食い違っても登録は止めず、直すのは裏側。仕様はけにーさんの見直し（10-16 22:36Z）を入れて決まっている（共有の資料「書誌マスタ　仕様」）。取りに行くのは Supabase の中（pg_cron と pg_net）で、Actions のログに ISBN を出さない。取ってくる所までは下の「書誌マスタ」。
  - そのときに気をつけること: `editions` には、非公開で登録された本の ISBN と、最初の登録の日時（`created_at`）も入っている。読めるようにするときは誰でも見られる本の版だけにし、`created_at` は出さない。送り直しや ISBN の直しで、本が1冊もない版と作品も残るので、取りに行く前に本のある版だけに絞る。
- **今ある本。** 移す工事で、ISBN ごとに版と作品を1つずつ（いちばん古い本の日付で）、ISBN のない本には1冊ずつ作品を作る。本の列（題名・ISBN・作成者・日時など）は1つも変えない。本番は17冊（ISBN のある本が12冊、すべて違う ISBN）なので、12の版と17の作品になる。
- **見せる範囲。**
  - `works` と `editions` は API から誰も読めない。版の書誌は `private.edition_sources` に入り、読めるのは `book_bibliography` を通した分だけ（下の「書誌マスタ」）。
  - `books.work_id` は本と一緒に読める。作品の ID は新しいでたらめな ID で、本の ID を使わない。同じ作品のほかの本は、その本が読める所でしか読めない（`hide_registered_titles`）。作品は ISBN だけで決まるので、作品の ID から、ほかの人が非公開で登録したかどうかは分からない。ただし運営がまとめた版の ISBN をあとで登録すると、その本はまとめた作品に入るので、その版がまとめられたこと（だれかが登録したこと）は分かる。運営は候補（誰でも読める本）からまとめ、非公開の本の ID ではまとめない。
  - 読書家は作品を書けない。`books` の列の権限から `work_id` を外していて、書こうとすると断られる（アプリは書かない）。作品は DB のトリガー（`books_work`、`books_work_edited`）が決め、挿入で名指しされた作品も使わない。同じ本を送り直しても、新しい作品はできない。
  - 本の版（`books.edition_id`）は、`work_id` と同じく読書家は書けず、`work_id` と違って API からも読めない（アプリは読まない）。
- **アプリが読む作品。** アプリは本と一緒に `work_id` を読み（`src/lib/supabase/town-backend.ts` の `BOOK_COLUMNS`）、`Book.workId` に入れる（`bookFromRow`）。`workOf`（`src/lib/works.ts`）はこれで同じ作品を見分け、ライブラリの数（同じ作品の版は1つと数える）と、ひとことで読みかけの本の行を伏せる判定（`guardedWorks`。ほかの人が同じ ISBN を別に登録した本のひとことも伏せる）に使う。デモの本と見本は作品を持たず、それぞれが自分の作品になる。登録したばかりの本は、次に街を読むまで作品を知らない（アプリは書くときに作品を受け取らない）が、同じ ISBN の本はライブラリの数でもともと1つに数えるので、数は変わらない。列を読み忘れると型の確かめ（`pnpm typecheck`）が止める。
- **運営の道具**（Supabase のダッシュボードの SQL Editor で流す）。本の ID は、手入力の本では題名を隠す鍵なので、公開のリポジトリや Actions のログに書かない。そのため、この操作はマイグレーションにしない。ISBN のある本を渡すと、その版（同じ ISBN の登録すべて）ごと動く。どの道具も、終わるまで本の書き込みを待たせるので、途中に登録された本も、終わったあとの作品に入る。
  - 候補を見る: `select * from private.work_candidates();` 誰でも読める本（目録の行と、公開の場で使われている手入力の本）の題名と著者だけで作る。非公開の登録は使わない。題名は検索と同じたたみ方（`src/lib/search/fold.ts` の `searchFold` と同じ手順。旧字、かなとカタカナ、長音もそろう）で、同じか、一方がもう一方の頭で数字が同じとき（「華氏451度」と「華氏451度 新訳版」は候補、「ONE PIECE 1」と「10」、「進撃の巨人」と「進撃の巨人 1」は出さない）。著者は、同じ人がいるか、一方がもう一方に含まれるとき（「ブラッドベリ, レイ」と「レイ・ブラッドベリ 著」は合う。「村上春樹」と「村上龍」、「スティーヴン・キング」と「ホーキング」は合わない）。著者が空の本は出さない。同じ題名と著者の作品がたくさんあるときは、いちばん影響の大きい作品と1組ずつ。公開の記録をつけた人の数・公開の感想の数・並べている開店中の本屋の数を返し、合計の大きいものから並ぶ。数えるのは誰でも見られるものだけで、ライブラリ、非公開の記録、隠れた投稿は数えない。
  - まとめる: `select * from private.join_works('<残す作品の本>', '<移す作品の本>');` まとめの ID と、移った本の数を返す。移した側の作品は消さず、`merged_into` に行き先を残す。動いた本の `updated_at` は変えない（本の中身を変えたのではないので、`books_touch` は作品だけが変わる更新では動かない。ISBN を直したときは変わる）。
  - まとめを戻す: `select private.undo_join('<まとめの ID>');` そのまとめで移った版（ISBN のない本の版も）と、そのあとその版に登録された本を元の作品に戻し、行き先もまとめる前のとおりにして、2つの作品に「別の作品」の印を付ける。あとのまとめで残した側がさらにまとめられているときは、先にそちらを戻す。まとめの ID は `select * from private.work_joins order by joined_at desc;`。
  - 外す: `select private.part_books(array['<本>']::uuid[]);` 1つの作品の中の版（渡した本の版ごと。ISBN のない本はその本の版）を新しい作品に移し、元の作品とのあいだに「別の作品」の印を付ける（候補に戻ってこない）。違う作品の本を混ぜたときと、作品の本を全部渡したときは断る。戻すときは `join_works`。
  - 別の作品の印: `select private.keep_apart('<本>', '<本>');` 2つの作品を候補から外す。印は付けたときの作品に残り、まとめられた作品はまとめた先の作品として読む（`merged_into`）ので、まとめても戻しても印を書き換えずに正しい作品を指す。印をやめるときは、たどった先が2つの作品になる行を消す: `delete from private.works_apart x using public.works a, public.works b where a.id = x.work_a and b.id = x.work_b and array[coalesce(a.merged_into, a.id), coalesce(b.merged_into, b.id)] <@ array['<作品>', '<作品>']::uuid[];`
  - 履歴: `private.work_joins` にまとめ（動かした版と ISBN、戻したか）、`private.work_changes` に本ごとの移動（ISBN を直した `edited`、まとめた `join`、戻した `unjoin`、外した `part`）が、元と先の作品と時刻つきで全部残る。登録で版に入ったことは、ISBN が決めたことなので残さない。
- **移す工事の確かめ**（ファイルの中、1つのトランザクション）。
  - 本を指す表を先に、本を最後に止める（逆だと、本を指す表に書いている人と待ち合って止まることがある）。`supabase db push` はファイルを BEGIN なしで送り、裸の `lock table` はそこで断られるので、`do` の中で止める（`tests/db-copies.test.ts` がどのマイグレーションにも裸の `lock` がないことを確かめる）。
  - 本と、本の ID を持つ9つの表（投稿、印、マイライブラリ、テーマ棚、出会い、記録、読書、人生の9冊、ポスター）の控えを `keep` に取る（控えの名前 `20261027000000_works`）。
  - `check_copy` で行とつながりを確かめ、そのうえで、本の列が控えと同じか、同じ ISBN の本だけが同じ作品にいるか、本が版の作品にいるか、どの作品にも本があるかを確かめる。1つでも違えば全部取り消し、本番は元のまま。「どの作品にも本がある」は工事のときだけの確かめで、そのあとはまとめた側の作品などが空で残る。
  - 本番で確かめ（本17冊がどれも版の作品にいる）、控えは `20261030000000_drop_kept_copies.sql` で消した。
- **戻すとき。**
  - アプリが `work_id` を読む前なら、マイグレーションの頭に書いた SQL（トリガー・関数・表と `work_id`、版へのつながりを外し、`books` の書く権限を元に戻す）を新しいマイグレーションで流す。本の行は無傷。`pnpm test:db` が、戻したあと DB が工事の前と同じになり、控えを消せばもう一度流せることを確かめている。
  - アプリが `work_id` を読むようになったあとは、先にアプリを前の版に戻してから。DB にない列を読むと街が開かない。
  - 控えは消したので、本の値を控えから戻すことはもうできない（工事は本の列を1つも変えていない）。
- **テスト**（`tests/db-works.test.ts`）: 読書家のいる DB での移す工事（どの表の行も変わらない、版と作品の分かれ方、控え、見える本が前と同じ）、隠れた本があってもなくても登録した人に分かることと押さえる行が同じで、たくさん送っても鍵が増えないこと、新しい本（同じ ISBN、新しい ISBN、ISBN なし、送り直し、同時に2冊、名指しの作品は使わない）、ISBN を直すと版を移ること、読書家が作品を書けないこと、API から作品・版・道具に届かないこと、たたみ方が検索と同じこと、候補の規則と順（非公開の本も、ライブラリや非公開の記録、運営が隠した投稿も使わない、旧字、巻の数字、1組ずつ）、運営の道具（まとめる、あとの本もまとまる、戻す、続けてのまとめを逆の順に戻す、外す、別の作品の印がまとめと戻しのあとも正しい作品を指す、動いた本の `updated_at` が変わらない）、退会と控え、戻す SQL と控えからの書き戻し、確かめで止まった工事が全部取り消されること。
- **版の ID**（`20261031000000_edition_ids.sql`）。版は ID で持ち、ISBN は版の属性になった。書誌マスタが ISBN のある版もない版も同じに扱い、作品から外して確かめを待つ登録（次の工事）も自分の版を覚えておけるように。
  - 変わらないこと: 同じ ISBN はその場で同じ版（`editions_isbn_key` で ISBN は1つの版にしかない）。登録のときに題名は比べず、待つのは同じ ISBN の登録が保存の途中にあるときだけ（版の行を押さえる仕組みは同じ。`private.isbn_edition`）。版の ISBN・作品・日付も、本の列と `updated_at` も変えない。

  - 確かめ（ファイルの中）: 本だけ控え（版は主キーが変わるので `check_copy` で照らせない。前の版は一時の表に写してファイルの中で比べる）、本の列が控えと同じ、どの版も ISBN・作品・日付がそのまま、ISBN のある版が増えていない、ISBN の本はその ISBN の版、ISBN のない本はその本だけの版、本のない ISBN のない版がない、どの本も版の作品にいる、まとめが動かした版（ISBN の版と ISBN のない本の版）を全部知っている。1つでも違えば全部取り消す。
  - 戻すとき: アプリはまだ `edition_id` を読まないので、マイグレーションの頭の SQL（トリガー、まとめの列、本の版、ISBN のない版を消して版の主キーを ISBN に戻す）と、作品と版のファイルの関数を流し直すだけで戻る。ISBN のない本の作品は残る。控え `20261031000000_edition_ids` は本番で確かめ、書誌マスタのマイグレーションで消した。

## 書誌マスタ（2026-10-17、管理表の4）

ISBN のある版ごとに、国立国会図書館（NDL サーチ）と openBD がその本について言っていることを裏側で取ってきて持ち、項目ごとに1つの書誌にする。仕様はけにーさんの見直し（10-16 22:36Z、共有の資料「書誌マスタ　仕様」）。マイグレーション `20261101000000_bibliography.sql`。登録は止めず、本の行も変えない（本は読書家が打ったまま。公開の画面は書誌、本人の棚は本人の入力、をアプリが選ぶ）。食い違いの判定と保留は `20261102000000_bibliography_holds.sql`（下の「食い違いの判定と保留」）、画面は下の「画面」。

- **何を取るか。**
  - 国立国会図書館: NDL サーチの SRU（外部提供インタフェース仕様書 第1.5版）に、ISBN 1つを1回で、図書館自身の書誌だけを聞く（`dpid="iss-ndl-opac iss-ndl-opac-inprocess"`。完成した書誌と作成中の書誌。全国書誌は `iss-ndl-opac` に入っている）。所蔵は聞かない（`onlyBib=true`。答えの大きさは約半分になり、書誌は欠けない）。答えのうち `bibRecordCategory` が R100000002（国立国会図書館）のレコードだけを使い、完成したもの（C7 など）を作成中（C3）より、ISBN の少ないもの（巻）をセットより先に選ぶ。申請なしで使える範囲（仕様の「外の条件」）。

- **持つもの**（版ごと・取り元ごとに1行、`private.edition_sources`）: 答えの状態（待ち・あった・なかった・失敗・取り下げ）、取ってきたまま（国立国会図書館は書誌の XML、openBD は使う所の JSON）、国立国会図書館の書誌 ID、作成状況（C3・C7）、読み取った値（`fields`）、答えの日時、その値を聞いた問い合わせを送った日時（`found_sent_at`、題名は `title_sent_at`）、続けてなかった・失敗した回数、次に聞く日時、答えが出た最後の問い合わせを送った日時（`settled_at`）、運営が聞き直しを頼んだ日時（`refetch_at`）、出ている問い合わせ。読み取る値は、題名、題名の読み、副題、巻、版（新訳版など）、シリーズ（いくつでも。名前・番号・読み）、著者（いくつでも。下の「著者の形」）、責任表示、出版社、出版年月、NDC。
- **著者の形**（`creators`、並び順の配列。画面と、題名と著者の出し方（管理表87）はこれを使う）。1人ずつ、ないものは入れない。

- **答えが来たとき。**

### 食い違いの判定と保留（2026-10-17、`20261102000000_bibliography_holds.sql`）

読書家が打った題名と著者が、その ISBN の書誌と明らかに違う登録を、裏側で「保留」にする（けにーさんの見直し 10-16 22:36Z「食い違いの扱い」）。登録は止めず、本の行（題名・著者・ISBN）も変えない。動かすのは、その本がどの作品に数えられるかと、書誌を出すかだけ。

- **比べるもの。** 読書家の題名・著者と、その本から見える書誌（その本の番か、それよりあとの番に聞いた答えと、運営の直し）。検索と同じたたみ方（`private.fold_book_text`）でそろえる。たたむと消える文字（キリル文字、ギリシャ文字、「Łódź」の Ł など）を含むときと、たたむと何も残らないとき（ハングルなど）は、全体を小文字にして空白と記号を外したもので比べる（`private.bib_key`。「Война и мир 1」が「1」にならないように）。判定は `private.bib_verdict`。
  - 同じ: 題名、題名と巻、題名と副題、題名と副題と巻のどれかと同じ。同じ巻の書き方の違い（下の「巻」）も同じ。
  - 近い: 片方がもう片方に入っている（短いほうが2文字以上。題名の読みとも比べる。新装版、副題つき、かなで打った題名）。または、書誌の著者のだれかが読書家の著者の欄と合う（名前、読み、典拠の見出しから生没年を外したもの。「Ray Bradbury」と「Bradbury, Ray, 1920-2012」）。書誌の著者は先頭の20人まで比べる（アンソロジーには何百人も並ぶことがあり、裏の判定が遅くなる。題名はもう比べてある）。近い本は書誌を出し、読書家の入力も残す。
  - 明らかに違う: どれでもない。著者を打っていなければ、題名だけで決まる。
  - なし: 書誌に題名がない。本が入ったあとに両方の取り元が答え終えたら（その本の番かあとの番で）、または1日たったら、そう決める。読書家の題名に文字がなく（「！？」）、著者も合わないときも「なし」。作品には数え、書誌は出さない。題名が来たら判定し直す。ISBN のない本は、入ったときから「なし」。
  - 本番の29冊を10-17に比べると、同じが16、近いが13、違うが0（巻の決まりを直す前）。
- **巻**（けにーさん 10-17 04:15Z「巻数の番号が明確に異なる場合は保留。表記揺れと巻数の不一致は区別し、巻数の記載がないだけでは不一致と判定しない」）。1作品＝1巻。

  - 書き込みの途中の本（登録し直し、題名の直し、本人の答えの途中）は待たずに飛ばし、次の回に回す（`skip locked`）。
  - 取り元の答えと公開の本のキャッシュで判定し直す印も、書き込みの途中の本を待たない（待つと、版の取り元を待つ読書家と互いに待ち合う）。印を付けられなかった本は `private.book_rechecks` に書き、次の回に判定する。判定はその本をこの表から外してから書誌を読むので、そのあいだに付いた印は次の回に残る。
  - 運営の直しと取り下げは、判定の途中の本を待ってから印を付ける。まだ判定していない本にも付け直す（その回の判定が前の書誌を読んでいるかもしれないため）。
  - 運営が本を作品のあいだで動かしているあいだ（まとめる・戻す・外す）は、その回の判定を丸ごと休む（`nowait`。待つと運営の道具と待ち合う）。
  - 判定がもし失敗しても、答えの読み取りと問い合わせは続ける（データベースのログに警告が残る）。
- **保留で変わること。**
  - 明らかに違う本はその本だけの作品に移す（ISBN のない本と同じ）。版の作品のページにも、数にも、まとめる候補にも入らない。書誌は本の欄にはどこにも出さない（本人の棚も、ほかの人が読む所も、読書家が打ったまま）。書誌の題名と著者は、本人への知らせ（下）にだけ出す。
  - 判定が変わって違わなくなったら、版の作品に戻す。もう一度違うになったら、前に保留にした作品が空のままならそれを使う（作品を増やさない）。移したことは `private.work_changes` に `hold`・`unhold` として残す。保留の作品は「違う」で本人が答えていない本にだけある（表の決まりで止める）。
  - まだ判定していない本も、作品の数に入れない（`private.book_counts_in_work`）。ふつうは最初の10分で、書誌に題名がなく取り元の答えを待つあいだは長くて1日。どの本も同じに扱う。
- **本人への知らせと答え。**

  - **使うときに写す。** ほかの人が入れた本を初めて使うとき（読みたい・お気に入り・棚・書店・投稿・記録・読書中・9冊・ポスター・ライブラリ）、街の中で写しを作って ID を決め（`src/lib/own-books.ts` の `owning`、ストアの `own`）、保存では写し（`copy_book(original, copy)`）を先に、写しを指す行をあとに書く（`planWrites` の `copy-books`）。断られた操作は写しも残さない。ISBN のある本は、自分の同じ ISBN の本があればそれを使い、写しを作らない。写しは元の本と同じ版に入り、その人の登録として今から判定される（`book_copies` の理由は `taken`）。自分のリストに入っているかを聞くときは `mine` / `holds`、街の外に書く物（店内の飾りつけに置く本）は先に `actions.ownBook` で写しにしてから使う。2つのページがそれぞれ相手の写しを読む前に写すと、写しが2つになる。どちらもその人の本で、リストへの問いと変更は、そのリストに入っている方で答える。同じ写しを2つのページが同時に送っても、1つにしかならない（`copy_book`）。
  - **登録。** 登録はいつも自分の行を作る。同じ ISBN でもほかの人の本は使わない（`bookByIsbn` もほかの人の本を返さないので、登録の下書きは書誌か openBD から）。検索と本のページの1タップ登録（`RegisterBook`）も同じ。ほかの人の本は直せない（`fixBook` が断る）。
  - **同じ本の人は作品で集める**（`booksOfWork`・`workOfId`、`src/lib/works.ts`）: 本のページの便り・ポスター・読後の気持ち・読んでいる人・並べている書店、読みたくなった元、知らせ、検索の手がかり。検索と本選びは、自分の本があるほかの人の本を出さない（`withoutTwins`）。
  - **見本の行はアプリから書かない**（行はマイグレーションが作ったもの）。
  - **出会い。** 投稿から出会った記録は、投稿の本と同じ版の自分の本（写し）を指してもよい（`check_book_encounter`）。
- **気をつけること。** 2本目が本番に入る前に置かれた送り待ちの変更や、前の版のアプリを開いたままのページから、ほかの人の本を指す書き込みが届くと、DB が断る（断られた変更として知らせ、書きかけは戻す）。2本目のトリガーがある間は、`private.give_own_copy` で付け替えをやり直せない（ポスターの本を付け替える途中で、まだ写していない本を指す行をトリガーが断る）。もう一度付け替えるときは、トリガーを外してから流し、終わったら戻す。店内の飾りつけは街とは別に送るので、つながらないあいだに写しを作った本を置いて保存すると、つながったときに写しより先に店内が届いて断られることがある（書きかけは残り、もう一度保存すれば通る）。
- **戻すとき。** それぞれのマイグレーションの頭の「Rollback」（1本目は関数と表を外し、`touch_updated_at` を元に戻す。2本目はトリガーと関数を外し、`check_book_encounter` を元に戻す）。写しはその人の登録として残る。付け替えそのものを戻すときは、頭の2つ目の注記の `restore_copy` と削除を、付け替えのすぐあと、だれもその表に書いていないうちに流す（`restore_copy` は表の行を全部控えの値に戻すので、あとからの書き込みも戻り、削除は写しを指す行を全部消す）。控えは本番で確かめてから、別のマイグレーションの `drop_copy` で消す。

## 版を確かめて書く（2026-10-18、監査 AUD-003）

書店の棚、店内の飾りつけ、人生の9冊、ポスターは、どれも丸ごと1つとして書く。これまでは、昨日読んだまま開いていた端末で今日直すと、そのあいだに別の端末で保存した分を、古い写しで黙って上書きしていた。マイグレーション `20261107000000_write_versions.sql` で、DB が数える版を確かめてから書くようにした。

- **版。** 4つに DB の数える版がある。店の棚は `shop_private.shelves_version`、店内の飾りつけは `shop_private.scene_version`、9冊は `profiles.nine_version`（行は `profile_nine` にあるので、プロフィールに持つ）、ポスターは `posters.version`（型・見た目・ページ・ネタバレの印・タイムラインに出すか・下書きか）。
  - どの書き方で変えても上がる（前のアプリの `shop_private` の upsert、`replace_profile_nine`、`posters` の update も。9冊の行をその場で直したときも）。同じ中身を書き直しても上がらない（`replace_profile_nine` も、もう同じ9冊なら何も書かない）。
  - 読書家は版を書けない（送っても DB が無視する。`posters.version` には列の権限もない）。
  - 保存したことのない物は版0（店の非公開の行がない、9冊を一度も保存していない）。行を作ったときは、空の棚・飾りつけなしからの変更として1から始まる（別の端末が先に行を作ったら、行がないと読んだ端末は断られる）。
  - 9冊は1回の保存で2つ上がることがある（古い9冊を外して新しい9冊を入れる）。版は上がったことだけを使い、いくつ上がったかは使わない。
  - ほかの人の店に飾ってよいか（`allow_display`）は、まだアプリが書かないので数えない。
  - 版は、その物を読める人が読める（棚と飾りつけは本人だけ、9冊と公開のポスターは見える人）。何回変わったかが分かる（ポスターは下書きのあいだの直しも数える）。9冊を変えると、プロフィールの `updated_at` も動く（9冊は見える人に見えているので、新しく分かることはない）。
- **書き方。** `save_shelves(shop, value, base)`・`save_scene(shop, value, base)`・`save_nine(book_ids, notes, base)`・`save_poster(poster, value, base)`。`base` は書き始めた版。
  - DB がまだその版なら書いて、新しい版を返す。
  - もう同じ中身なら（答えが届かずに送り直したとき）何も書かず、今の版を返す。
  - どちらでもなければ書かずに PT409（HTTP 409）で断る。
  - 作ったばかりのポスターは `base` なしで送る。なければ作り、もうあれば（答えの届かなかった前の送り）版0として書く。`base` つきで送ったポスターがなければ、別の端末で下げたものとして断る。
  - どれも読書家の権限で動き、行の決まり（RLS）と表の確かめ（自分の本だけ、ポスターの形など）はふだんどおり効く。
  - 比べて書くあいだは、その行を押さえる（`for no key update`。その行を指す行、フォローやポスターの本は書ける）。前のアプリの `replace_profile_nine` も先にプロフィールを押さえるので、`save_nine` と互いを待ち合わない。作ったばかりのポスターを2つの送りが同時に作ったら、あとの送りは先に作られたものとして書く。
- **アプリ（`src/lib/supabase/sync.ts`）。** 版は読んだ値と一緒に保存の仕組み（`backgroundSync`）が持つ。読み込みが `Versioned`（値と `Versions`）を返し、キーは `writeStake`・`walkStake` と同じ（`shelves`・`scene`・`nine`・`poster:<ID>`）。画面の状態（`TownState`・`WalkData`）には入れない。書くときは `apply(write, base)` に、その書き込みを作った値の版を渡し、DB の返した版に進める。
  - 断られたら（`CHANGED_ELSEWHERE`）、その変更は送らず、ほかの変更は送り、読み直して「別の端末で先に変わっていたため、書店の棚の変更は送りませんでした。」と出す（`missed-changes.ts` の言葉）。画面は読み直した DB の中身になる。
  - 人生の9冊・ポスター・店内の飾りつけは、この端末で直した分を書きかけとして残す（下の「書きかけを残す」）。帯の言葉は「…の変更は送りませんでした。書きかけは残しています。」で、断られた物がどれも書きかけを残す種類のときだけ「書きかけは残しています」を付ける（`townMissedLine`・`walkMissedLine`）。書きかけは書き始めた保存の印（`from`）を持つので、開くと「書きかけより新しい…が保存されています」と出て、読書家が開くか消すまで待つ。開いたら「保存すると、いま保存されている…と入れ替わります」と出す。9冊の小窓は、別の端末で先に変わって送らなかったときは「保存できませんでした」を重ねて出さない（`useKeptUntilSaved` が、街の知らせでどう戻ったかを分けて伝える。同じ回で保存できていたら、書きかけを手放す）。保存を待つあいだにサインアウトして別の街になったら、書きかけは手放さない（アカウントの送り待ちの箱から、あとで送られることがあるため。`useKeptUntilSaved` と `keepPosterUntilSaved` が街の世代を見る）。
  - 書店の棚は、送らなかったこの端末の棚をこのブラウザに残す（`src/lib/shelves-draft.ts`、持ち主ごとに新しい順で4つまで。あとの棚が前に残した棚の場所を取らない）。帯は「書店の棚の変更は送りませんでした。書きかけは残しています。」で、書店の画面の「棚をつくる」の下に「別の端末で先に棚が変わっていたため、この端末で直した棚を残しています。この端末の棚にすると、いまの棚と入れ替わります」と［この端末の棚にする］［書きかけを消す］を出す。合わせることはせず、どちらかを選ぶ。［この端末の棚にする］は残した棚を街に戻して（`restoreShelves`、なくなった本は外し、ほかの人の本は自分の写しにする）読んだ版の上に送り、トーストの「元に戻す」で前の棚に戻せる（戻した棚はそのあと直した所ごとまた書きかけとして残り、保存されたあとでも出し直せる。この端末の棚が断られたか別の端末で先に変わっていたら、何も入れ替えず「この端末の棚は保存されなかったため、いまの棚のままです。」と言う）。残した棚は、DB が受け取って保存された棚と同じものだけを手放し、ほかに残した棚は残る。この端末の棚にしたものは、保存される前に本や POP を直しても、保存されたら手放す。同じ棚は1つだけ残す。断られたら残ったまま（帯も「書きかけは残しています」と言う）、また別の端末で先に変わっていたら一番新しい書きかけとしてまた残す。
  - ポスターの書きかけは、送ったポスターの場所（`owner:poster:<id>`）で受け取りを待つ。新しいポスターも同じで、送ったあと「ポスターを作る」の場所は空くので、そこで書き始めても送った書きかけを上書きしない。受け取りは、ほかの変更が断られた回（`recovered`）でも、DB がそのポスターをそのまま持っていれば済んだとする。送るあいだに「直す」で書き始めた分は、送ったものが断られたら、DB が持つポスターから書き始めたことにする（別の端末で変わっていたときは古い書きかけのまま）。断られた新しいポスターや別の端末で外されたポスターのように、ポスターが見つからない書きかけは、そのポスターのページに「このポスターの書きかけを、このブラウザに残しています。新しいポスターとして開けます。」と［書きかけを開く］を出し、「ポスターを作る」の続きの一覧にも出す。開くと「もとのポスターが見つからないため、書きかけを新しいポスターとして開いています」と出し、貼り出すと新しいポスターになる。ポスターのページは、書きかけが保存されたポスターと同じになったら手放す（タブを閉じて受け取りを待てなかったとき）。
  - 古い書きかけで待っている9冊の小窓は、キャンセルで閉じても書きかけを消さない（見せていない書きかけを消さない）。
  - つながらずに途中で切れた送りは、あとの変更より先に、同じものをもう一度送る（DB が受け取っていれば同じ中身なので、何も書かずに版が返る）。先にあとの変更を送ると、自分の前の送りを別の端末の変更として断ってしまうため。
  - 送り待ちの箱の変更は、今までどおり印（`valueMark`）で確かめてから、次のページが読んだ版の上に送る。そのページが箱から送った変更の版は、ページ自身の版にしない（ページの変更は箱の変更より前の値から作ったので、読み直すまでは断られて知らせる）。
  - DB に断られた丸ごとの物は、箱に印なしで残る。次のページはそれを送り直さず、断られたことだけを伝える（送ると、そのページの読んだ版の上に古い写しを書くため）。
  - 9冊は、版をプロフィールと読み、本人の9冊の行はそのあとでもう一度読む（`readTown`）。並べて読むと、あいだに別の端末が保存した9冊を、新しい版と古い中身で持ってしまうため。棚・飾りつけ・ポスターは中身と版が同じ行にある。
  - 版を数える DB では、版の分からないポスターの直し（作ったときに断られた、別の端末で変わっていた）も、作ったときの版0の上にだけ書き、前の書き方では書かない。
  - 何枚かまとめて作ったポスターの1枚が別の端末で変わっていたら、1枚ずつに分けて送り、その1枚だけを外す。
- **版のない DB でも動く。** アプリと DB はばらばらに本番へ入るので、版を読めないときは今までの書き方で書く。DB に版があるかは、自分のプロフィールに `nine_version` があるかで見る（街）。書店めぐりは店の非公開の行を `scene_version` の列つきで読み、列がなければ（42703）飾りつけだけを読み直す。店がまだないときは、行を読まずに列があるかだけ聞く（`limit(0)`）。
- **ほかの読み込みに版を持たせるとき**（AUD-006 の 6a など）。版は `loadTown` と `loadWalkRows` の `versions` で返る。丸ごとの物を読む新しい読み込みは、同じキーで版を返し、その値から作った書き込みは `apply` の `base` で書く。版を読んでいない値から作った書き込みを、版なしで書かない（古い写しで上書きする元になる）。
- **残ること。** このアプリより前のアプリを開いたままのページは、版を使わずに上書きする（その書き込みも版を上げるので、新しいアプリの端末はそれに気づく）。読み込み直せば直る。DB を戻したときは、開いたままの新しいアプリのページの次の保存が、関数がない（404）と断られて「保存できませんでした」と出し、読み直して今までの書き方に戻る。

## その3で決めたこと（保存先の切り替え）

- **画面は今までの `TownState` のまま使う。** ログインしている人の街はデータベースから組み立て、自分は `me`、自分の本屋は `mine` という今までの呼び名に置き換える（`townFromRows`）。画面の部品はデモと同じものが動く。
- **保存は差分で、後ろで行う。** 最後にデータベースが受け取った街と今の街を比べ、変わった行だけを書く（`planWrites`）。どの書き込みも、やり直しても同じ結果になる。0.4秒待ってまとめて送る。
  - つながらないときは 2秒、5秒、15秒、30秒と間を空けて送り直し、画面の上に「つながらないため、まだ保存できていません。つながりしだい保存します。」と出す。
  - データベースが断った変更（消えた便りへの返信、閉じた書店へのフォロー、ほかの人が先に取ったIDなど）は、**その1件だけを外し、ほかの変更は送る**（2026-10-18、監査 AUD-002）。何行かをまとめた書き込みが断られたら1行ずつに分けて送り直し（`splitWrite`・`splitWalkWrite`）、断られた行だけを外す。送り終えて待つものがなくなったら街を読み直し、画面をデータベースの状態にそろえる（読み直すあいだに変えたものは先に送ってから、もう一度読む）。上の帯には何を保存できなかったかを画面の呼び名で出す（「返信、読書の記録を保存できませんでした。書きかけは残しています。」、`src/lib/missed-changes.ts`）。そのとき出ていた「投稿しました」などの知らせは、帯と同時に消す（取り消しのできる知らせは残す）。断られた便りの言葉は「投稿する」の書きかけに（返信の便りは消えていることがあるので）、読書の記録はその本の記録の書きかけに戻す。前の書きかけがあれば消さず、そのあとに改行して続ける。
  - **送り待ちの箱**（`src/lib/outbox.ts`、AUD-125）。まだデータベースが受け取っていない変更は、変えたその場でこの端末に置き、受け取ったら消す（localStorage、アカウントごと、街と書店めぐりで別のキー、ページごとの入れ物）。ページを閉じた、タブが落ちた、ログインが切れた、つながらないまま読み込み直した、のどれでも、次にその人の街を読んだページが、ほかの何よりも先に送り、読み直す。7日たったものは消す（連続スキャンの控えと同じ）。箱に置けたので、ページを閉じるときにブラウザは確かめない。置けなかったとき（保存がいっぱい、使えない）だけ確かめる。
    - データベースに断られた変更も、画面に伝えて言葉を書きかけに戻すまでは箱に残す。伝える前にページが閉じたら、次のページがもう一度送り、断られたことを伝えて言葉を戻す。
    - 箱の変更が、つながっているのに3回続けて送れないとき（まだない書店の飾りつけ、この版では送れない形）は、このページでは後回しにして箱に残し、このページの変更を先に送る。後回しにした変更は次のページがまた送る。
    - 書き込みの形を変えるときは、箱のキーの版を上げる（今の街は `-v2:`、次は `-v3:`）。前の版のアプリが置いた変更を、新しい版が送らないためと、開いたままの前の版のページが、知らない書き込みを箱に書き戻すときに落とさないため。`-v2:` は本の写し（`copy-books`）を足したときに上げた。`-v1:` の変更は今の版でも送れる形なので、新しいページが一緒に送り、送れたらそこから消す（`OUTBOX_KEY_BEFORE`）。

  - .wasm は外の CDN ではなく、このサイトの `/zxing/zxing_reader-<版>.wasm` から配る。ビルドと dev の前に `scripts/copy-zxing.mjs` が node_modules から `public/zxing/` に写し、barcode-detector が求める sha256 と比べる（`public/zxing/` は git に入れない。Vercel でもこのビルドを走らせるよう `vercel.json` に `buildCommand` を書いてある。Vercel では1年キャッシュ）。ライセンスの表記（ZXing-C++ の Apache-2.0 全文と、zxing-wasm・barcode-detector の MIT）は同じ場所の `LICENSE.txt` に書き出す。Apache-2.0 の全文は `scripts/licenses/` に置いてある。

  - **2つの版は一緒に固定する**（package.json で `^` を付けない）。barcode-detector の JavaScript は決まった版の zxing-wasm の .wasm 向けに作られていて、zxing-wasm だけを上げると起動しない（copy-zxing がビルドを止める）。上げるときは barcode-detector の新しい版を入れ、その `dependencies` にある版に zxing-wasm をそろえ、`pnpm test:domain` と `pnpm test:library-journey`（本物の WebAssembly でカメラの本を読む確認がある）を回す。

## 書きかけを残す（2026-10-13）

- **読書家が書いたり並べたりしているものは、保存が確かめられるか、読書家が消すと決めるまで、このブラウザに残す。** 投稿と感想と返信、読書メモ、読み終えた本の記録、通報と表紙の削除依頼、本屋を開く途中、プロフィールと人生の9冊、看板と紹介、棚の名前、店内の飾りつけ。どれも `src/lib/kept-draft.ts` の入れ物を使い、種類ごとに localStorage のキーを分け、読み戻すときに形と上限を確かめる。小窓を Escape、外のタップ、✕、「戻る」で閉じても、読み込み直しても消えない。
- **消えるのは、保存できたときと、読書家が消すと決めたときだけ。** 書きかけのある画面は静かな一行「書きかけを続けています」と「書きかけを消す」を出す（`KeptDraftNote`）。言葉が失われるときは「書きかけを消しますか？ 消す／残す」と一度だけ聞く。やめる・キャンセルのあとも同じ問いで、「残す」は書きかけを残したまま閉じる（`StopConfirm`）。ブラウザが残せないときは「このブラウザに書きかけを残せませんでした」と出し、画面の言葉はそのまま。
- **断られた保存は、成功の知らせで閉じない。** その場で断られたら（街の読み込み中、保存できない状態、見本など）、画面は開いたまま書きかけを残し、わけを伝える。アカウントでは、本屋を開く途中、プロフィールと人生の9冊、看板と紹介、棚の名前、店内の飾りつけ、ポスターを、データベースが受け取ったと分かるまで残す（`useKeptUntilSaved`、店内は `keepUntilSaved`、ポスターは `keepPosterUntilSaved`）。あとから断られたら、先に出た知らせのあとに「保存できませんでした。書きかけは残しています」と伝え、次に開くと続きから書ける。投稿と読書の記録は、街が受け取った時点で書きかけを消し、そのあいだは送り待ちの箱が言葉を持つ。あとから断られたら、言葉を書きかけに戻して上の帯で伝える（上の「保存先の切り替え」）。つながらないときに投稿・返信・記録すると、「投稿しました」ではなく「つながらないため、まだ投稿できていません。つながりしだい投稿します。」と言う（`offlineFor`、`townOffline`）。カードに「送信中」は付けない（仮決め。箱と書き戻しで言葉は失われず、上の帯が待っていることを伝えるため）。
- **書きかけは持ち主ごと。** キーの最初は `draftOwner`（`src/lib/draft-owner.ts`。アカウントのID、デモ、ログインしていない人）で、同じブラウザでも別のアカウントの書きかけは出さない。投稿の下書き（新しい投稿、感想、返信、読書メモ。`src/lib/post-draft.ts`）とポスターの書きかけ（`src/lib/poster-draft.ts`）も同じで、アカウントを替えると前の人の下書きは見えず、その人がログインし直すと戻る。アカウントを確かめているあいだは何も残さず、何も出さない。投稿の欄と読書メモはそのあいだも書け、書いた言葉は持ち主が分かったところでその人の下書きになる。その人に同じ所の下書きがあれば、どちらも消さず、前の下書きのあとに改行して続ける（`joinPostDrafts`）。合わせると投稿の長さを超えるときは、書いた言葉を画面に残したまま「このブラウザに書きかけを残せませんでした」と伝え、前の下書きはそのまま残す。ポスターは2つを合わせられないので、ポスターを作る画面は持ち主が分かるまで開かない（「ポスターを開いています…」）。
- **ログインしていない人が書いたものは、ログインするとそのアカウントの書きかけになる。** 読み終えた本の記録（「記録する」でログインに招かれたとき。`adoptVisitorRecords`）、投稿の下書き（`adoptVisitorPosts`）、ポスターの書きかけ（`adoptVisitorPosters`）。どのログインも終わるログインの画面で渡す。アカウントに同じもの（同じ本の記録や感想、同じ投稿への返信、新しい投稿、同じポスター）の書きかけがあればそちらを残し、ログインしていない人の書きかけは、次にログインしていない人が開くときのためにそのまま残す。渡すときは書きかけの持ち主を書き換えるだけで、新しく書いたことにはしないので、上限（投稿の下書きは50）でほかの書きかけが外れることはない（`move`）。
- **持ち主で分ける前の投稿とポスターの下書きは、このブラウザで最初に分かった持ち主が一度だけ引き取る。** 以前は、この2つを同じ localStorage のキー（`book-town-post-drafts-v1`、`book-town-poster-drafts-v1`）に持ち主なしで残していた。誰が書いたかはもう分からないので、最初の持ち主（ログインしているアカウント、デモ、ログインしていない人）に渡すのがただ一つの推測で、ログインしていない人が引き取っても、ログインすれば上のとおりアカウントに渡る。引き取るのは、その持ち主が初めて下書きを読むか書くとき（`claim`、`src/lib/kept-draft.ts`）。その持ち主に同じ所の書きかけがあればそちらを残し、古いほうは捨てる。引き取ったら持ち主のない下書きは消すので、2人目の持ち主には何も見えない。引き取るときにブラウザを読み直すので、タブを2つ開いていても渡るのは一度だけで、もう一方のタブが書いても古い下書きは戻らない。ブラウザが書き込めないときは古い下書きをそのまま残し、次に開いたときにまた引き取る。投稿の下書きの上限（50）はそのままで、超えるときは引き取った古いほうから外れる。
- **書きかけが保存されたものより古いときは、黙って重ねない。** 記録・プロフィール・看板は変えた所だけを残し、変えていない所は保存されている今の値に従う。店内の飾りつけ・人生の9冊・ポスターは、書きかけを始めたあとに別の端末で保存されていれば「書きかけより新しい店内（人生の9冊、ポスター）が保存されています」と出し、読書家が開くか消すまで待つ（印は `sceneMark`・`nineMark`・`posterMark`）。開いたら、保存すると今の物と入れ替わることを書きかけの一行で伝える。ポスターのページと書店の「書店めぐりの店内」には、書きかけがあることだけを一行で出す。印を持たない前の9冊の書きかけは、今までどおり続きから開く。
- **ログインの途中（コードを送ったメールアドレスと時刻。コードは残さない）と最初のプロフィールは、そのタブの sessionStorage に残す。** メールのアプリへ行ったあいだにページが閉じられても、同じ手順に戻れる。

## 指で操作する画面では、開いただけでキーボードを出さない（2026-10-14）

- **どの画面でも、指で操作する画面（`(pointer: coarse)`。スマートフォンとタブレット）では、何かを開いたり出したりしただけで入力欄にフォーカスを入れず、欄の言葉も選択しない。** 小窓、ページ、手順の次の段、モード（スキャナーの「打つ」、注釈のシート）、書きかけを消したあとの欄も同じ。キーボードが、開いたばかりのものを覆ってしまうため。読書家は開いたものを見てから、欄に触れて書く。欄のあるものを開くボタン（スキャナーの［手で入力］）でも同じで、開いた欄にもう一度触れるまでキーボードは出ない。1回多く触れることになるが、何が開いたかを先に見られるほうを選んでいる。例外は、下の「書く画面」と、スキャナーの［ISBNを打つ］。［ISBNを打つ］は打つことそのものを頼むボタンなので、押したその場で ISBN の欄にフォーカスを入れ、キーボードを出す（押したタップの中で `flushSync` で欄を出し、`focusField(欄, { asked: true })`）。カメラがない、カメラを断られたなどで、スキャナーがひとりでに打つ入力へ替わったときは、今までどおりキーボードを出さない。書く画面の中の［本を添える］は、本を探す欄にフォーカスが入り、キーボードは出たまま。確かめるのは `tests/library-journey.mjs` で、［ISBNを打つ］を指で押すとそのタップの中で欄にフォーカスが入ること（押しても欄にフォーカスが入らない前の形に戻すと落ちる）と、［手で入力］とひとりでに替わった打つ入力ではキーボードが出ないこと。
- **フォーカスは開いたものの中へ移す。** 小窓はその最初のボタン（たいてい ✕）、ページや段はその見出し、注釈のシートは見出し。小窓の外で書きかけを消したとき（読書メモ、本のページの感想、看板と紹介）と、書店めぐりの「ひとことを書く」から看板と紹介が開いたときは、その欄のフォーム。キーボードやスクリーンリーダーで使う人が、開いたものの中、いた場所から始められるように（ページの先頭へ戻されない）。フォーカスを持つだけの見出しとフォームには、枠を描かない。
- **読書家が触れた欄は、その人のもの。** 書いている途中に欄のそばのボタン（スキャナーの［登録］［♪］［取り消す］、「隠す」など）を押しても、フォーカスはその欄に残り、キーボードは出たまま。
- **送ったあとに間違いが見つかった欄**（ログインのメールアドレスの形とコードの桁、最初のプロフィールの名前・ID・年齢、スキャナーの ISBN）は、フォーカスを入れず、欄を見える所へ動かして赤い枠（`aria-invalid`）を付け、わけを一行で伝える。枠は欄を直すと消える。ブラウザ自身の確かめはフォーカスを欄に入れるので、指で操作する画面のログインのフォームでは使わず、同じ確かめを画面がする。読書家が書いている途中の欄なら、今までどおりフォーカスを置いたまま選択する。
- **閉じたときにフォーカスを戻す先が入力欄なら、指で操作する画面では戻さない。** iPhone ではボタンを押してもフォーカスが移らないので、前に書いていた欄が戻り先になりうる。書く画面の中の欄には戻す。
- **マウスやトラックパッドの画面（タッチ画面つきのノートパソコンも）は今までどおり。** 開いたときに欄にすぐ書け、間違いの欄にはフォーカスが入って選択される。
- 決まりは `src/lib/coarse-pointer.ts` の1か所に置く。画面は `autoFocus` や欄の `focus()` を直接使わず、`focusField`（開いた・出たときの欄。読書家が押したボタンがその欄で打つことを頼むものなら `{ asked: true }`）、`useFocusFieldOnShow`（autoFocus の代わり）、`markField`（間違いの欄）、`focusBack`（閉じたときの戻り先）を使う。`Modal` は自動でそうする。どれも、書く画面（`data-writing` の内側）の欄にはフォーカスを入れる。確かめるのは `pnpm test:domain`（`tests/coarse-pointer.test.ts`）と、ブラウザの通し確認（`tests/journey-keyboard.mjs`。スマートフォンの幅とタッチで、開いてもフォーカスが欄になく選択もないこと、欄をタップすると書けること。マウスで、今までどおり欄にすぐ書けること）。

## 書く画面だけは、開いたらすぐキーボードを出す（2026-10-14）

- **書くために開く画面は、スマートフォンの書くアプリと同じく、開いたその場でキーボードが上がり、書いているあいだは下がらず、ボタンはキーボードのすぐ上に並ぶ。** 上の「開いただけでキーボードを出さない」の、画面としてはただ一つの例外。書く画面は次の5つ。
  - 投稿する（丸いボタン）
  - 感想を書く・『…』の感想（本を閉じるときの［感想を書く］、閉じたあとの「今日の読書」の［感想を書く］、送っていない言葉の［感想に使う］の、3つの入り方のどれも）

  - デモの書店めぐりの「店主に伝える」

## 投稿の欄は「押して、書いて、投稿」（2026-10-14）

- **1つの投稿で考えることを増やさない。** 投稿の欄（丸いボタンの投稿、感想、本のページの感想、返信）に出すのは、書く欄、［本を添える］、［ポスター］（丸いボタンの投稿だけ）、使えるときだけの「ネタバレあり」と「隠す」、［投稿する］（返信は［返信する］）。文字の数は今までどおり、上限に近づいたときだけ出す。書きかけの一行（「書きかけを続けています」「書きかけを消す」）と「書きかけを消しますか？」の問いも今までどおり。
- **外したもの。** タグの列（「タグ」の字、付いたタグ、＋#の候補、「本文に「#ことば」と書くとタグになります」）、「下書きはこのブラウザに保存しています。」、ネタバレの印の説明、「||」の説明。タグは今までどおり、本文に「#ことば」と書けばタグになり、投稿ではリンクになる。下書きも今までどおりこのブラウザに残す（言わなくなっただけ）。読書中のつぶやきの「||」の説明は残す。
- **「ネタバレあり」は付けられるときだけ出す。** 本を添えた投稿、感想、返信。本のない投稿では出さない（前は押せない形で出していた）。本を外すと消え、印も外れる。
- **「一部を隠す」は「隠す」になり、書く欄で言葉を選んでいるあいだだけ、ボタンの列に出る**（Discord と同じ形）。押すと選んだ言葉が「||」で囲まれ、カーソルはそのあとへ移り、選んでいる言葉がなくなるので「隠す」も消える。書く欄はフォーカスを手放さないので、スマートフォンではキーボードが出たまま。読み上げでは「選んだ言葉を隠す」。選んでいるかどうかは書く欄の `selectionchange`（ブラウザによってはページにだけ届く）と `select` で見て、選んだときから言葉が変わったら（打った、隠した、消した）出さない。React の `onSelect` は、ページ全体が React の根のときに `selectionchange` を受け取らないので使わない。「隠す」が出てもボタンの列が2段にならないよう、ボタンの間を詰めている（幅375px以上の画面で1段）。読書中のつぶやきの「一部を隠す」は今までどおり、いつも出ていて、何も選んでいなければ隠す所を作る。

- 隠す判断は RLS の `private.is_hidden()` が行う（`moderation_hides` と、`moderation_folds` の `held`）。`private` スキーマは API に出ないので、外から呼べない。`moderation_hides` は運営（service role）だけが読み書きできる。
- まだないもの: 運営が隠すと決めたこと（`moderation_hides`）を本人に知らせる表示、通報が来たときに運営へメールで知らせる仕組み（送信元のドメインが決まってから）。自動でたたんだこと・確認まで見えなくしたことは、書いた人に知らせている。

## 通報とたたむ仕組み（2026-10-13）

規則はデータベースの1か所（`private.weigh_report` と `private.review_state`、`supabase/migrations/20261022000000_safety_defaults.sql`）にある。

- **3人分の通報で、たたむ。消さない。** 作って7日以上のアカウントの通報は1人分、7日未満は半人分。作られた時刻が24時間以内につながるアカウント同士は、何件あっても合わせて1人分まで。合わせて3人分になると `moderation_folds` に `folded` が立ち、みんなの画面で「通報があったため、運営が確かめるまで、たたんでいます」になる。押せば読める。ポスターも同じで、タイムラインのカードとポスターのページでは、ポスター（ページでは載っている本の一覧も）の前に覆いがかかる。押して読んだあとも、ネタバレの印があれば扉は残る。プロフィールと作品ページの小さな一覧では「たたんでいます」と理由（「通報があったため」）だけを出し、見出しも本も出さない（読み上げの名前は見えている言葉どおり「ポスター たたんでいます（通報があったため）」、ページの見出しは「たたんでいるポスター」）。投稿も、押して読むまでは添えた本を出さない。本屋と人は、紹介文だけをたたむ（名前、棚、POP、投稿はそのまま。それぞれに通報がある）。
- **すぐ見えなくするのは、深刻な理由だけ。** 理由が「個人情報をさらしている」「脅し・危害を加えるという言葉」で、通報した人のアカウントが作って7日以上なら、投稿とポスターは運営が見るまで本人以外から見えなくなる（`held`）。1人が24時間に急ぎにできるのは3件まで。本屋と人は、たたむだけ。
- **アカウントの古さ**は `greatest(auth.users.created_at, profiles.created_at)`。`profiles.created_at` はプロフィールを作ったときにデータベースが付け、本人は変えられない（`private.stamp_profile_time`。変えられると、同時に作ったアカウントが日付を1日ずつずらして別々の人になれる）。招待はけにーさんが同じ日にまとめて作ることが多いので、`auth.users` だけだと最初の読書家たちが1人分にまとまる。プロフィールは各自の初めてのログインで作られるので、遅いほうを使う。
- 急ぎになる通報は、同じ人の通報を1件ずつ数える（同時にたくさん送っても、急ぎは24時間に3件まで）。
- **通報の状態**は運営だけが変える。通報した人には、これだけが届く（相手をどうしたかは伝えない）。通報した人が読めるのは `status` ではなく `progress`（`open`・`checking`・`checked`）で、`resolved` と `dismissed` はどちらも `checked` になる。

| `status`    | 意味                   | 通報した人に見える言葉 |
| ----------- | ---------------------- | ---------------------- |
| `open`      | 届いた、まだ見ていない | 受け付けました         |
| `checking`  | 運営が見ている         | 確認中                 |
| `resolved`  | 対応した               | 確認しました           |
| `dismissed` | 問題なし               | 確認しました           |

- **書いた人には、たたまれたこと・見えなくなったことが届く**（誰が、何人かは伝えない）。運営が `dismissed` にすれば、たたみは自然に戻る。通報した人の画面では、通報したものは結果にかかわらずたたんだまま（「あなたが通報した投稿です」「あなたが通報したポスターです」）。書いた人の投稿・ポスターの下には、たたまれていること（「…ポスターは消えていません。」）や、確認まで見えなくしていることを書き添える。ポスターは、作った人のプロフィールと作品ページの小さな一覧（「通報があり、みんなの画面ではたたんでいます」「運営が確かめるまで、ほかの人には見えません」）と、直す画面にも書き添える。お知らせでは、投稿は本文の書き出しで、ポスターは見出し（なければ本の題名）で名指しし、2つあっても見分けられるようにする。
- **消したものは、たたみも残さない。** 書いた人が投稿・ポスター・本屋を消すと、その `moderation_folds` の行も消える（`private.refold_taken_down`。行の持ち主がいなくなったものは、通報の状態が変わっても行を作り直さない）。通報の行は運営のために残る。
- 通報した人は、自分の通報の id、種類、理由、`progress`、日時だけを読める（`status`、`detail`、`urgent`、`reporter_id` は読めない）。お知らせの「あなたの通報」に1行ずつ並ぶ。確認中・確認しましたのお知らせは「{もの}について{M月D日}にいただいた通報を、運営が確認しています」の形にする（何についてかを先に書く。「…にいただいたポスター」は「いただいたポスター」と読め、「通報してくださった読書家を」は通報した人が確かめられているように読めるため）。表紙は「表紙について{M月D日}にいただいた削除の依頼を、…」。

## 見せる範囲（2026-10-16、管理表の8）

## 表紙の削除依頼

- 表紙の出どころ（「表紙: openBD」「powered by Google」）の下に、小さく「表紙の削除依頼はこちら」。ログインしている人にだけ出す（招待制なので、ログインしていない権利者は依頼できない。押してもログインの案内にしかならないため、出さない）。権利者がアカウントなしで依頼できる窓口は、まだない。本についての通報（`target_kind = 'book'`、`reason = 'cover'`）として届き、説明は必須。アプリが「表紙の出どころ: Google Books / ISBN …」を説明の後ろに足す。
- 運営が受けると `cover_refusals` に ISBN と取得元を入れる。アプリはページを開くたびにこの一覧を読み、その本についてはその取得元に問い合わせない。次の取得元の表紙か、装丁カードになる。画像に手を加えたり、別の画像に差し替えたりはしない。一覧が読めないときは、そのページでは外の表紙を出さない。

  - `library_shelf_books`：どのテーマ棚にどの本があるか。複合の外部キーで、自分の棚と自分のマイライブラリの本しか結べない。主キーは読書家・棚・本（`user_id, shelf_id, book_id`）で、新しい行はこの3つを重なりの目印に insert する。棚と本だけのキーだと、外部キーより先に重なりが調べられ、ほかの人の棚の ID を知っている人が、その棚にどの本があるかを1冊ずつ確かめられてしまう。
  - `book_encounters`：この本との出会い。投稿、POP、本のページで押したいいね・私も好き！・読みたいと、本人のメモ（255字まで）。
- **一度でも使った本は、いいねや読みたいを取り消しても残る。** `ever_used` は、自分の本屋に置いたときと、自分の投稿・ポスター（下書きも）・人生の9冊に使ったときに付き、一度付いたら消えない（`false` にする update が来ても、トリガー `library_entries_keep_used` が `true` のまま残す。断りはしない）。外した行にも付く（行は戻さない）。いいねや私も好き！で入った本も、これが付いていれば、本屋から下ろしたり投稿を消したりしたあとでいいねを取り消しても、マイライブラリに残る（N19・N20、2026-10-14）。読みたいや☆を取り消したときも、この印を「何も残っていない」かどうかに数えるので残り、いいねと読みたいのどちらを先に取り消しても同じになる。ただし、外した本をいいねだけが戻した行（`like_restored`）は、いいねが戻す前のこと（外したときに残っていた状態・読みたい・☆・所有・棚と、外していたあいだに付いた状態・所有・使った印。どれも外した本を戻さない）を数えないので、いいねを取り消すとまた外れる。`like_restored` は、そのあと本人が何かを付けたとき（状態・読みたい・☆・所有・テーマ棚・登録、お店や投稿などに使う）に消え、外すだけのとき（読みたい・☆・テーマ棚から外す、状態・所有を未設定に戻す）は消えないので、この行でも、いいねと読みたい・☆のどちらを先に取り消しても同じになる（古いアプリが読みたい・お気に入りの印を外したときも同じ）。いつ使ったかは持たない（並べるのに使わず、人生の9冊には日付がないため）。
- **いいね・読みたい・☆は、どの順で取り消しても同じになる。** 最後のいいねを取り消したとき、行は、どこから入ったかによらず（いいねで入った本も、読みたいや☆で入った本、古いアプリから写した本も）、いいねのほかに何も残っていなければ外れる。読みたい・☆を取り消したときと同じにするため、4-10 の条件1（いいねで入った行）をどの行にも広げた（2026-10-14 に決まった）。いいねで戻した行は、戻す前のことを数えない（上）。わざと登録した本（スキャン、ISBN、手入力、［＋登録］）は、登録の印（`book_marks` の `library`）があるので残る。順で変わるのは、投稿や POP の「読みたくなった」をほかより後に取り消したときだけで、そのときは残る（「読みたくなった」の取り消しは行を見直さない。4-2 の「反応を取り消しても外さない」）。読みたい・☆・古いアプリの読みたいで入った本の両方の順を、共通の例（`sequence`）に置いてある。
- **消さずに印を付ける。** マイライブラリの本と棚には delete の権限がない。外すと `removed_at`、片づけると `deleted_at` が付き、棚の中身と、ほかの棚への所属は残る。消せるのは、棚から本を外したとき（所属の行）と、メモのない出会いを取り消したときだけ。
- **書き方。** 新しい行は全部の列を insert し（重なりは無視）、変えた行は変えた列だけを update する。部分の upsert（キーと変えた列だけ）は、行があっても `source` が空だとして断られるので使わない。所属の表に既定の upsert を送ると、`position` 以外は update できないので権限で断られる。列ごとの権限：
  - `library_entries` の update は、状態、読みたい、いいね、所有、外した印、`like_restored`、`ever_used` だけ。`source`、`added_at`、`batch_id` は最初のまま。
  - `library_shelves` の update は、名前、説明、並び、読みたいの表示、片づけ、見せる範囲（`audience`）、条件（`rule`）だけ。所属の update は並びだけ。
  - `book_encounters` の update は、メモ（`memo`、`memo_at`）と取り消し（`undone_at`）だけ。
  - 規則（`applySet`）が作る行は、どれもこの権限で書ける。共通の例（`apply` と `sequence`）を、アプリと同じ insert と update にして `pnpm test:db` で流して確かめる。
- **時刻。** 端末の時計が進んでいても、未来の時刻は入らない（トリガーが今の時刻に押さえる）。
- **本は消されない。** マイライブラリの本と出会いの本を指す外部キーは `on delete restrict` で、運営が本の行を消そうとすると止まる。
- **設定**（`reader_settings`）：`library_hidden`（隠す既定の棚のキー。英小文字と `_` の1〜32字を20個まで。知らないキーも入り、アプリが無視する）、`likes_in_library`（いいねした本をマイライブラリに入れる。はじめはオン。オフのときは、いいねのほかに何も残していない本を、どこから入ったかによらず、ライブラリ（全部）・まだ振り分けていない・数から隠し、「いいねした本」の棚にだけ出す。隠すのは、いいねを取り消すと外れる本と同じ本で、同じ判定 `heldByLikeAlone` を使う）、`wanted_clears_on_status`（読み始めたら「読みたい」から外す。はじめはオフ。設定を置くことは問い3で決まった）、`memo_hint`（メモの案内を出す。はじめはオン）。古いアプリの upsert は `user_id` と `spoiler_display` しか送らないので、この4つには触れない。

### 出会いの記録（`book_encounters`）

- **1つの押し方に1行。** 同じ投稿への同じ反応、同じ本屋の同じ本の POP への同じ反応、本のページの読みたいは、それぞれ1行（部分一意索引）。POP の置き場所（`placement_key`）は見つけ直すために持つだけで、同じかどうかには使わない（お店のページと書店めぐりで、同じ POP の呼び方が違うため）。行の ID は端末が作る。
- **取り消し。** メモがなければ行を消す。メモがあれば `undone_at` を付けて残し、押し直すと同じ行の `undone_at` を外して使い直す。
- **insert のトリガー**（`private.check_book_encounter`）は、押した本人の権限で動く（security invoker）。投稿と本屋は、その人が読めるものしか見つからない。
  - 見えない投稿と本屋（ひとりメモ、運営が隠したもの、ブロックし合っている相手のもの、閉店中の本屋）は、ないものと同じ誤り（`the post met is not found`・`the shop met is not found`、23503）で断る。外部キーより先に断るので、断られ方からは、その投稿や本屋があるかどうかは分からない。
  - 自分の投稿と自分の本屋への行は断る。
  - 投稿の行は、その投稿自身の本（返信なら返信の本。親の本ではない）だけ。本のない投稿には作れない。POP の行には本屋と置き場所が要る。本のページの行は、投稿も本屋も持たない。
  - 相手（`other_reader_id`）は、端末が何を送っても、トリガーが投稿の書き手か本屋の店主に置き換える。
  - すでに保存した行（同じ ID の本人の行）を送り直したときは確かめず、insert 自身の ID の重なりに任せる。答えが届かずに送り直すまでに、投稿が消えたり、隠されたり、ブロックしたり、本屋が閉まったりしても断らない（断ると、まだ送っていない変更がまとめて消える）。重なりを無視する insert なら何も起きず、ふつうの insert なら重なり（23505）で断られる。見るのは本人の行だけなので、ほかの人の行のことは分からない。消えた投稿への新しい行は、オフラインのあいだに消えたものでも断られる（23503）。
- **相手が消えたとき。** 投稿が消えると `post_id` が空になり、行とメモと相手は残る。本屋が消えると `shop_id` が空になる。相手が退会すると `other_reader_id` が空になる。本人が退会すると、行ごと消える。
- 今あるいいね（`post_reactions`・`pop_reactions`）は写さない。出会いの記録は空から始まる。

### 古いアプリの印を写すトリガー（`book_marks_follow`）

- マイライブラリを知らないアプリ（開いたままの古いタブ、巻き戻したアプリ）が `book_marks` に書いた印は、データベースがその人のマイライブラリの行に写す（`private.library_follows_marks`）。写し方はアプリの `followMarks`（`src/lib/library.ts`）と同じで、どちらも同じ例（`tests/fixtures/library-cases.json`）で確かめる（`pnpm test:library` と `pnpm test:db`）。
  - 印を付けたとき：行がなければ作る（`source = 'legacy'`、時刻は印の時刻）。読みたい・お気に入り・登録の印は、外した行を戻す（レビュー 4-2 の「戻す規則」）。読みたいは `wanted_at` を付け、読了は状態を読了にする。印は本人の操作なので、いいねで戻しただけの印（`like_restored`）は消える。
  - 印を外したとき：読みたいは `wanted_at` を外し、読了は「読書中」にする（古いアプリが読了を外すのは、読み直しを始めたときだけ）。読了を外したときは、アプリで読み始めたときと同じく `like_restored` も消す。ほかの印を外しても `like_restored` は変えない（アプリで読みたい・☆を外したときと同じ）。読みたい・お気に入り・登録の印を外して何も残っていない行だけを、マイライブラリから外す（読みたい・お気に入りの印を外したときも外すのは、レビュー 4-2 の最後の行。2026-10-14 にけにーが決めた）。残すものは、状態、読みたい、所有、いいね、一度でも使った印（`ever_used`）、片づけていないテーマ棚、登録とお気に入りの印、自分の読書記録、メモのある出会い（取り消したものも）。お店の棚、投稿、ポスター、人生の9冊そのものは見ない。
- **1回の保存の順。** 古いアプリは1回の保存で、外した印をすべて消してから、足した印を書く（`src/lib/town-remote.ts` の `planWrites`）。トリガーは1つずつ写すので、読みたいを外して読了にした保存では、ほかに何も残らない行はいったん外れ、読了は外した行を戻さないので、読了のまま外れる。`markChanges` も同じ順に並べ、共通の例（`save`）を `pnpm test:library` と、`planWrites` の順で流す `pnpm test:db` で確かめる。
- **ヘッダーの約束。** 新しいアプリは、すべての通信にヘッダー `x-booktown-library: 1` を付け、マイライブラリの行を自分で書く。このヘッダーのある書き込みでは、トリガーは何もしない（行の `updated_at` も変わらない）。ほかの値とヘッダーなしは、古いアプリとして写す。ヘッダーを偽っても、変わるのは自分の行の写しだけ。印は重なりを無視して upsert されるので、すでにある印ではトリガーは動かない。
- **security definer にしてある。** アカウントの削除は `auth.users` からの連鎖で `book_marks` に届き、そのあとのトリガーは削除した役（supabase_auth_admin）で動く。この役はマイライブラリの表に権限がないので、呼んだ人の権限で動かすと削除ごと失敗する。トリガーが触るのは、その印の持ち主の行だけで、退会の途中（プロフィールがもうない）では何もしない。`pnpm test:db` の「deleting an account removes everything it owned」は、superuser でない supabase_auth_admin で削除して確かめる。

### いまあるデータからの埋め戻し

- マイグレーションを流したときに一度だけ、それまでにしたことからマイライブラリを作る（`private.library_backfill`。もう一度流しても、そのあと何もしていなければ何も変わらない）。どの行も `source = 'legacy'` で、所有は付けない。状態が付くのは、読了の印（読了）と、終わっていない読書（読書中）だけ。新しい状態は作らない。
  - 先の手順が作らなかった本を、次の手順が足す。順は、印（登録・読みたい・お気に入り・読了。読みたいは `wanted_at` も）、自分の読了の記録、終わっていない読書、終わった読書、自分で使った本（投稿、ポスターと下書き、人生の9冊、自分の本屋の棚（非公開の棚も）と店内）。最後の手順は、その中で一番早い時刻を `added_at` にする。自分で使った本の行には、どの手順で作った行でも `ever_used` を付ける。人生の9冊はプロフィールの、本屋の棚と店内は本屋の作られた時刻で代える。本でない ID（見本の本など）は飛ばす。
  - いいねは写さない。本屋の表（`shops`、`shop_private`、POP の反応）と本は書き換えない。
  - L2b までは、どのアプリもマイライブラリの操作を送らないので、そのあいだに本屋に置いたり投稿・ポスター・人生の9冊に使ったりした本には、行も `ever_used` も付かない。L2b のマイグレーションで `private.library_backfill` をもう一度流して追いつく。2回目は足すだけで、行のない本に行を作り、状態のない行のうち読書が続いているものを読書中にし、`ever_used` のない行に付ける。外したり戻したりはしない（`pnpm test:db` が、あとからの投稿を2回目で拾うことを確かめる）。
  - 2回目は流さないことにした（2026-10-17）。アプリが、行のない本の行を毎回その場で作り、使った本の行は使うのをやめるときに書く（下の「アプリが読み書きする」）ので、データベースに行がなくても画面は同じになる。

### 手入力の本を読める人（R2 を広げる）

- `private.book_is_mine` に、マイライブラリの本（外していない行だけ）と出会いの記録（取り消したもの、相手の投稿が消えたものも）を足した。マイライブラリから外すと、ほかの人が手入力した本は、ほかで使っていなければもう読めない。`book_is_listed` は変えていない（マイライブラリは公開されないため）。

### 元に戻すとき

- この表を読むアプリが本番に出る前なら、新しいマイグレーションでトリガー `book_marks_follow`、4つの表（表のトリガーも一緒に消える）、`private` の6つの関数（`library_follows_marks`、`library_backfill`、`library_keep_used`、`check_book_encounter`、`library_clamp_times`、`encounter_clamp_times`）、`reader_settings` の4つの列を消し、`book_is_mine` を `hide_registered_titles` の形に戻す。関数を残すと、直したマイグレーションでもう一度足すときに「同じ関数がある」と断られる。消す SQL はマイグレーションの頭に書いてあり、`pnpm test:db` がそのとおりに流して、マイグレーションの前と同じに戻ることと、もう一度足せることを確かめる。出たあとなら、まずトリガーだけを消し、表と関数は本番のアプリを前の版に戻してから消す（表を読めない街は読み込めないため）。

### アプリが読み書きする（L2、2026-10-17）

- **アプリは自分で行を書く。** すべての通信に `x-booktown-library: 1` を付ける（`src/lib/supabase/client.ts`）ので、古いアプリの印を写すトリガーはこのアプリの書き込みでは動かない。印（`book_marks`）はこれまでどおり書き、ほかの画面とほかの読書家の見え方は変わらない。
- **行は、読書家が変えた本だけ持つ。** 持っている行は `TownState.libraryEntries`（ログインした人は `library_entries`、デモは localStorage の同じ保存）。それ以外の本は、印・自分の記録・読書・自分の投稿・ポスター・人生の9冊・自分の本屋から、埋め戻しが作る行と同じ形を毎回その場で作る（`entriesOf`、`src/lib/library-town.ts`）。だから、埋め戻しのあとに使った本も、ライブラリより前のデモも、行を書かずにライブラリに入っている。作った行の時刻は `LEGACY_AT`（2026-10-01）からの並びで、本当の時刻ではない。
- **いいねは、出会いの記録ができるまで（管理表 9・10）街の反応で代える。** 投稿のいいね・読みたくなった、POP のいいね・私も好き！・読みたくなった（自分の投稿と自分の本屋は除く）を出会いとして読む（`townEncounters`）。いいねだけの本は、いいねがあるあいだライブラリに入る。設定（`likes_in_library` など）はまだ読まず、はじめの値で動く。
- **読みたい・読了の一覧は、操作した本だけ行に合わせる。** 読みたい・☆・登録・読書を始める・終える・記録は、どれも `applyOp`（`src/lib/library.ts`）を通り、操作した本だけを `wishlist` と `finishedBooks` の最後に足すか外す（`relisted`）。ほかの本は順も印もそのままなので、保存が途中で切れて印と行が食い違っても、次の操作がほかの本の印を消さない。読書を始めると読書中になり、読了の印は外れるが読みたいは外れない（問い7）。登録を外すと、ほかに何も残っていない本だけライブラリから外れる（`withoutRegistering`。古いアプリが登録の印を外したときと同じ）。
- **一度使った本の行は、使うのをやめるときに持つ。** 作った行の「使った印」は、投稿・ポスター・人生の9冊・本屋の棚がそこにあるあいだしか分からない。だから、使うのをやめる操作（投稿を消す、9冊を変える、棚から下ろすなど）で、使った印のある行をまだ持っていない本は、行を持って印を付ける（`keepingUses`、`src/lib/store.ts` の `commit`）。ほかの操作（フォロー、いいねなど）では行を書かないので、ライブラリの書き込みがほかの操作を止めることはない。ほかの端末で使うのをやめたときは、この端末では行を持たない（その端末が持つ）。
- **書くのは変えた列だけ。** 部分の upsert はしない（設計どおり）。新しい行は全部の列を重なりを無視して insert し（`onConflict: user_id,book_id`、`ignoreDuplicates`）、入らなかった行（ほかの端末がもう作っていた）には、変えた列だけを update で送る。前からある行も変えた列だけを update する（`planWrites` の `library-entries`、`src/lib/town-remote.ts`）。行は本のすぐあと、印より先に書くので、保存が途中で切れても、行が印より遅れることはない。見本の本は `sampleBookRowId` で書き、目録の行を先に書く。
- **まとめて変えて、戻す。** 画面は `changeLibrary(本, 変えること)` で状態・読みたい・所有・☆・外すを変え、戻すための控え（`LibraryUndo`）を受け取る。`undoLibrary` は、そのあと変わっていない本だけを前に戻し、何もない所から入れた本は、何も付いていない外した行にする（行は消さない）。
- **まだしていないこと。** 出会いの記録とメモ（9・10）、設定（8 の残り）。デモで古いタブが保存すると、そのタブの知らない行は消える（デモだけ）。
- **確かめ:** `pnpm test:library`（`tests/library-town.test.ts`：作る行、持つ行、読みたい・読了の読み戻し、外す、戻す、デモの保存、行の読み込み、書く列）と `pnpm test:supabase`（「the app's library is written by the app, and comes back as the reader left it」）。

### 自分で作る棚（管理表15、2026-10-17）

- **棚は3つの仲間。** 決まった棚（読了・積読・読書中・読みたい本・いいねした本・お気に入り。行から毎回計算する `DEFAULT_SHELVES`）、自分で作る棚（`library_shelves`、画面では「棚」）、スマート本棚（条件で自動で集まる棚。下の「棚ごとの見せる範囲とスマート本棚」）。1冊の本は自分で作る棚にいくつでも入り、読書の状態や決まった棚はそのまま残る。書店の陳列棚（`Shop.shelves`）とは別のもので、棚に入れても店には並ばない。
- **画面。** ライブラリの棚の並びで、決まった棚のあとに自分で作った棚（作った順。`position` は時刻の62進で、ほかの端末で作った棚も作った順に並ぶ。`positionAfter`）と［棚を作る］が並ぶ。空の棚は数を出さず、「ライブラリから選ぶ」でライブラリ全体から選んで入れる。［選ぶ］の帯の「自分の棚」の段で、選んだ本を棚に入れる・外す（全部入っていれば光り、押すと外す）。本のカードには、今開いている棚のほかに入っている棚を「SF・文学 ほか1」と出す。棚の名前（40字）・どんな棚か（500字）・「読みたい」だけの本も並べるかは［棚を編集］で変え、［この棚を消す］は片づけ（`deleted_at`、本はライブラリに残る）で、知らせの［元に戻す］で戻せる。
- **書きかけ。** 棚の名前と説明は `src/lib/library-shelf-draft.ts`（`owner/new`、`owner/<棚の ID>`）に残し、街に保存できたら離す（`useKeptUntilSaved`）。
- **書き方。** 新しい棚は全部の列を重なりを無視して insert し、前からある棚は変えた列だけを update する（`planWrites` の `library-shelves`）。棚の本は、外したものを delete、入れたものを重なりを無視して insert する（`shelf-books`）。書く順は、本の行（`library-entries`）→ 棚 → 棚の本。棚の本には本の行が要る（外部キー）ので、行を毎回計算していた本を棚に入れると、その行も持つ（`withLibraryOp`）。見本の本は `sampleBookRowId` で書く。
- **戻す。** 棚に入れる・外す操作の控え（`LibraryUndo.shelves`）は、その操作が触った棚の所属だけを、入れた時刻と並びごと元に戻す。ほかの棚の所属は変えない。
- **確かめ:** `pnpm test:library`（`tests/library-town.test.ts` の「a shelf is made last…」から4つ）と `pnpm test:app`（「a shelf of the reader's own is made, filled from the library, kept, and put away with undo」）。

- **古いデータベースでも書ける。** アプリとマイグレーションは別々に本番に届くので、自分だけで条件のない新しい棚は `audience` と `rule` を送らない（データベースの既定値と同じ）。読むときは列がなければ「自分だけ・条件なし」として読む。

## ポスター（第1弾、2026-10-13）

- **ポスターは画像ではなくデータで持つ。** 型（`one_book` 1冊を語る、`lineup` 並べる、`text` 文章）、色（6つのプリセット）と書体（明朝・ゴシック）、ページごとのブロックの並び（見出し、言葉、本の列）。文字が読め、表紙から作品ページへ行け、どの画面でも同じ組版を縮尺だけ変えて出す（4:5）。後で型やブロックの種類（順位、写真）を足すときは、`pages` の中に新しい種類を足し、新しいマイグレーションで `private.check_poster` にも教える。今の画面は知らない種類のブロックを読み飛ばす。
- **上限はアプリとデータベースで同じ。** 10ページ、1ページに見出し・言葉・本の列を1つずつまで、1ページの本9冊（1冊を語る型は1冊、文章の型は0冊）、1枚の本100冊、見出し60字、言葉2000字。データベースはトリガー（`private.check_poster`）で確かめ、ページやブロックにそれ以外のものが入っていれば断り、目録にない本が載っていれば保存ごと断る。`pages` 全体も128KBまで。
- **下書きは本人だけ。** 貼り出したもの（`status = 'published'`）だけが他の人とログインしていない人に見える。ブロックした相手と、運営が隠したポスター・人のものは見えない。通報もでき（`reports.target_kind = 'poster'`）、投稿と同じ規則でたたむ・確認まで見えなくする（上の「通報とたたむ仕組み」）。下書きを貼り出すと、その時刻が新しい日付になる。
- **作品ページから引く索引** `poster_books` は、保存のたびにデータベースが `pages` から作り直す。誰も手で書けない。
- `allow_display`（他の人の本屋に飾ってよいか）は、飾る機能（本棚の第4弾と合わせる）のために先に入れてある。
- 見本のポスター（`src/lib/data.ts`）は、見本の書店と同じように街に並ぶが、保存はされない。見本の本をポスターに載せると、その本の目録の行を先に書く（`sampleBookRowId`）。目録の行は最初に使った読者のものになり、ほかの人には公開の場で使われるまで読めないが、見本の本は端末が自分で持っているので、画面にはいつも出る。

## 本の検索（第1段・第2段、2026-10-13）

設計の全体は共有フォルダの「検索_設計_2026-10-13.md」（PR-1〜7）にある。ここには、いまのコードが守っている決まりだけを書く。

- **文字は1つの「たたみ方」でそろえてから比べる**（`src/lib/search/fold.ts` の `searchFold`）。全角と半角、ひらがなとカタカナ、小さい字、長音（とうきょう・トーキョー）、助詞の「は」と「わ」、旧字（`itaiji.ts`）を同じに読む。ロケールに頼る手順は使わないので、あとでデータベースでも同じたたみ方をくり返せる。打った言葉がローマ字なら、打っている途中でも、かなとしても読む（`romaji.ts`。tokyo は「ときょ」、最後の n は「ん」とも、な行の始まりとも読む）。
- **本の並びは、合い方の種類で決まる**（`rank.ts` の `MATCH`）。ISBN、題名そのもの、題名の始まり、題名の途中、著者、すべての語、1字違いの題名、それ以外の順。同じ種類の中では、打ったとおりの書き方を先にし、街での目立ち方（公開の棚・投稿・読みたくなった、`presence.ts`）はわずかに並びを動かすだけで、数として画面には出さない。
- **4字以上で探したときの1字違い（10字以上なら2字まで）の題名は、合った本として後ろに並べる。字面が近いだけの本は「近い題名の本」として分けて出す**（著者が近いときは「著者名が近い本」）。近い本は合った本とは混ぜない。見出しは小さいが、読める濃さ（4.5:1 以上）にする。
- **本を選ぶ欄の Enter は、確かなときだけ1冊を取る**（`surePick`）。題名の始まりまで合っているか、合う本が1冊だけのとき（1字違いの題名1冊も含む）。「近い題名の本」は Enter で取らない。かな漢字変換を確定する Enter は無視する（`enterPressed`）。投稿に添える本、本屋を開く、読書、本棚の編集、人生の9冊、店内の飾りつけ、ポスターの本は、どれも同じ探し方（`useBookSearch`）を使う。
- **読み**: 本は題名と著者の読み（`titleReading`・`authorReading`、出どころつき）を持てる。見本の本には読みを入れてある。登録した本に openBD などから読みを付けるのは第3段、ログインした人の街を目録全体から探すのは第4段（データベースの変更あり）。
- **読書家と書店も同じたたみ方で探す**（`text.ts`、`town.ts`）。同じ種類の合い方の中では、長音や「は」をたたまずに合うほうを先にする（「ゆき」では、ゆき が ゆうき より先）。読書家は名前と @ID だけ（自己紹介では探さない）。@ID がローマ字なら、かなで打っても見つかる（凪 @nagi は「なぎ」、@shinya は「しんや」）。@ で始めると、読書家も書店も @ID だけを、書いたとおりに見る（@mio2 は @mio_2 ではない）。書店は店の名前、店主（名前と @ID）、店の紹介の順に並べ、最後に公開の棚にある本で探す。通報でたたんだ店の紹介は、見えないのと同じく探す対象にもしない。
- **タグは、同じ言葉の書き方の違いだけを1つにまとめる**（`textKey`）。かなとカタカナ、全角と半角、大文字と小文字、長音の記号（#ミステリ・#ミステリー・#みすてり・#ﾐｽﾃﾘ）。検索のたたみ方とは違い、「は」と「わ」や「へ」と「え」はまとめない（#へび と #えび は別のタグ）。ローマ字で探すと、かなのタグが見つかる（misuteri で #ミステリ）が、ローマ字で書いたタグ（#misuteri）は別のタグのまま。人気のタグは「そのタグを書いた投稿の数」で並べる（1つの投稿は1回）。
- **検索の結果に数は出さない。** 見出しにも件数を付けず、合うものがないときは言葉で伝える（街の検索の読み上げも「まだ見つかりませんでした」と言う）。
- 確かめるのは `pnpm test:search`（`tests/search.test.ts` と `tests/search-text.test.ts`）と、ブラウザの通し確認（`test:app` ほか）。

## 立ち寄り便り（店主への人数）

- **店主は、先週（日本時間の月曜から日曜）自分の本屋に立ち寄った人数だけを知る。** 誰が来たかは出さない。人数は、週が明けた月曜0時（日本時間）にデータベースが1度だけ数えて `private.shop_visitor_weeks` に置き（`private.count_shop_visitors`、pg_cron の `shop-visitors`）、その週のあいだは変わらない。読むのは関数 `shop_visitors()` で、呼んだ本人の本屋の先週の人数と、その週が終わった時刻だけを返す。数える期間は呼ぶ側が選べない。ログインしていない人は呼べず、週ごとの数の表はだれも直接読めない（マイグレーション `20261104000000_shop_visitors_weekly.sql`）。
- 数えるのは本人以外の訪問で、ブロックしている・されている相手も数える。ブロックや解除、来た人がもう一度来ること、訪問の記録を消すことで、その週の数は動かない。ブロックしたあとは相手から本屋が見えないので、新しい訪問は入らない。週より先の日時の訪問（端末が送った値）は数えない。
- 1人以上いた週だけ、お知らせに「先週、○人があなたの本屋に立ち寄りました」を出す（1週に1通）。本屋のページの店主向けの一行にも「先週○人が立ち寄り」と出す。0人の週は何も出さない。
- 人数を出す仕組みをほかに作るときも同じ形にする（数える期間はデータベースが決める、ブロックで数を変えない、その時その時に動く数を出さない）。人が少ないうちに少ない数で人が分かってしまう点は、監査の台帳 AUD-066 で別に扱う。
- 訪問は1人1軒につき最後の1回だけを持つ（`shop_visits` の主キー）ので、同じ人が何度来ても1人と数える。

## 注釈モード（運営の注釈、2026-10-13）

本番のサイトを使いながら、けにーさんが「ここを直してほしい」を指で示して残し、Claude が読んで直すための仕組み。仕組みは `supabase/migrations/20261023000000_site_notes.sql`、画面は `src/components/SiteNotes.tsx`。

- **使い方。** 画面の隅の「注釈」ボタンを押すと画面がうすい黄色になり、次にタップした場所にピンが立って、言葉を書く小さなシートが開く（指で操作する画面では、欄に触れるまでキーボードは出ない）。「残す」で保存してモードを出る。そのページに残した注釈は、次にボタンを押すと番号つきのピンで戻ってくる。ピンを押すと言葉と日時が出て、「取り下げる」で取り下げられる（トーストの「元に戻す」で戻せる）。
  - うすい黄色の幕がタップを全部受けるので、下のボタンやリンクは押されない。スクロールはできる。ページだけでなく、棚の横の列、手に取った本、小窓の中も、幕の上を指でなぞれば（ホイールでも）動くので、見えていない場所に残すためにモードを出なくてよい。シートを書いている途中に幕を押すと、キーボードが閉じるだけ。場所を変えるのは「場所を選び直す」。
  - 「メモしたい場所を…」の案内は、ピンの上に重なると反対の端へ一度だけ動く（↑↓で動かすこともできる）。シートやカードが上に開いているあいだ、トーストは下に出る。
  - 「戻る」は1回でモードを出る。そのあとの「戻る」は、ふだんどおり前の画面へ。Escape もモードだけを出る（小窓や手に取った本は開いたまま）。
  - 書きかけの言葉は、そのページを開いているあいだだけ覚えている。「戻る」で出ても、もう一度ボタンを押せば同じピンで続きから書ける。シートの「やめる」で消したときは、トーストの「元に戻す」で戻せる。ブラウザには保存しない。
  - 小窓や手に取った本の上でも使え、その小窓の題を一緒に残す。ピンは、タップした要素とその中の位置から置き直すので、画面の幅が違っても同じ要素の上に立つ。見つからない、隠れている、別の大きさの画面で残した、というときは点線のピンにして、カードに理由を添える。

  - 最初の staff は、マイグレーションを適用した時点でいちばん古いアカウント（けにーさんのもの）。足す・外すときは、けにーさんが SQL Editor で `private.staff` に `user_id` の行を足す・消す。

       n.target as under_finger,

## 検証

- `pnpm test:db`: PGlite（Node.jsで動くPostgres）にマイグレーションを流し、ログインなし・本人・他人の立場で、読める・書ける・拒否されることを確かめる。
- `pnpm test:supabase`: 手元で `supabase start` した本物の Supabase（ログイン、コードのメール、REST、RLS）に対して、招待、コードでのログイン、最初のプロフィール作成、ログアウトを通す。続けて2人の読書家が街を使い、保存したものが読み込み直しても残ること、公開したものだけが相手に届くこと、断られた変更が画面で戻ること、つながらないあいだの変更があとで保存されることを確かめる。`supabase status -o env` の値を環境変数に入れてから実行する。
- `pnpm test:town-sync`: データベースなしで、行から街と書店めぐりを組み立てる処理と、書き込みの計画を確かめる。
- GitHub Actions の CI（`.github/workflows/ci.yml`）で、PRごとに型チェック、lint、ドメインテスト、データベーステスト、ビルド、ブラウザでのログイン、本物の Supabase でのログイン、デモのビルド（Supabase の設定なし）でのブラウザの通し確認（書店めぐり、店内の飾りつけ）を回す。ほかのブラウザの通し確認（下のバーと検索と読書、既存機能、街、ホーム、本の前景、ポスター）は、時間がかかるので手元で回す。
- `supabase/config.toml` の `[auth.email] enable_signup` はメールでのログインそのもののスイッチなので、`true` のままにする。新規登録を止めるのは `[auth] enable_signup = false` のほう。
