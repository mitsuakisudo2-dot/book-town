# 監査の台帳と報告

BookTown の品質を、開発の速さに置いていかれないように、見つけた問題を番号で追い、次の監査で比べるための置き場です（けにーさん 2026-10-17「今回の監査を基準点にして、週1回の簡易監査＋月1回の総合監査を標準にする」）。

役割は変えません。Claude が開発し、外の検証役（ChatGPT）がこのフォルダと GitHub を読んで独立に確かめ、Claude が直し、もう一度確かめます。

## ファイル

- [台帳.md](台帳.md): 見つけた問題を1件1行で持つ、ずっと使う表です。**監査の結果の正本はここです。** 行は消しません。直しても行は残し、状態を変えて、その状態の表（未解決／直した（再確認待ち）／再確認済み・見送り）へ移します。ふだん読むのはこの台帳だけです。
- [経緯.md](経緯.md): 台帳の「記録」に収まらない経緯を、番号ごとの見出しの下に持ちます。扱う番号の見出しだけを読みます。書いたことは消さず、書き足します。
- `YYYY-MM-DD_*.md`: その日の監査の報告です。書いたあとは直しません（その日の写し）。最初は [2026-10-17_基準点.md](2026-10-17_基準点.md)。

## 台帳の欄

| 欄 | 書くこと |
|---|---|
| 番号 | `AUD-001` からの通し番号。一度振ったら変えない |
| 重要度 | A 今すぐ直す（セキュリティ、データの破損・消失、情報漏れ、根本的な設計ミス）／B 公開前に解決（主な使い勝手、機能の不足、速さ、運営）／C 公開後でよい改善／D 新しい提案（管理表にない機能、もっと合理的なやり方） |
| 分野 | ①仕様の整合性 ②機能の抜け ③データ設計 ④使い勝手 ⑤セキュリティ ⑥コード品質 ⑦速さ ⑧将来の設計 ⑨思想 ⑩進め方・運営 |
| 題 | 1行。何が起きるか |
| 見つけた日 | その監査の日付 |
| 原因 | 設計／実装の抜け／テスト不足／仕様の食い違い／資料の古さ／進め方 |
| 状態 | 未解決／直した／再確認済み／見送り |
| 再発 | 初めてなら「初」。前に同じ種類があれば、その番号 |
| 管理表 | 関わる管理表の番号（機能一覧と作る順番） |
| 記録 | 300字まで。未解決の行は「次：」（次にすること）か「残り：」（まだ残っていること）で始める（手をつけていない基準点の行は「基準点の案のまま（手つかず）」）。直したら提案書（PR）と日付、再確認した日と確かめた人、見送りの理由。長い経緯は経緯.md に書き、ここからリンクする |

## 状態の移り方

状態を変えたら、行をその状態の表へ移し、台帳の上の「数」も直します。「直した」は終わりではなく、別の目の確かめを待っている状態です。

1. **未解決**: 監査で見つけた。
2. **直した**: 直す提案書が main に入った。直したスレッドが PR 番号と日付を書く。
3. **再確認済み**: 次の監査で、直っていること、ほかの機能に悪影響が出ていないことを確かめた。直した人とは別の目（外の検証役か、けにーさん）で確かめる。
4. **見送り**: けにーさんが「やらない」「今はしない」と決めた。理由と日付を書く。

## 台帳の形を守る確かめ

- `tests/audit-ledger.test.ts`（CI の `pnpm test:settings`）が、番号が AUD-001 から欠けず重ならないこと、行が状態の表にあること、未解決が重要度の順で記録が「次：」「残り：」「基準点の案のまま（手つかず）」で始まること、記録が300字までであること、数が行と合うこと、経緯の見出しと台帳のリンクが互いに合うことを確かめます。
- 台帳を組み替えるときは、組み替えのあとで `pnpm exec tsx tests/audit-ledger-kept.ts origin/main` を流します。前の版の行が全部残り、番号・重要度・題・状態などが変わらず、前の記録と経緯の文が1字も欠けずに台帳か経緯にあることを確かめます。
- 行が増えて「直した」や「再確認済み・見送り」の表が重くなったら、状態ごとにファイルを分けることを考えます（2026-10-23 の時点では分けていません）。

## 次の監査で出す数

前の監査の日からその監査の日までで、次の4つと再発を数えます。

- 新しく見つけた問題（その監査で台帳に足した行）
- 解決した問題（その期間に「直した」か「再確認済み」になった行）
- 未解決の重要な問題（A と B で、状態が未解決の行）
- 仕様との不一致（分野①で、状態が未解決の行）
- 再発（「再発」の欄に前の番号が入った行）

同じ原因の種類が2回目に出たら、1件ずつ直すのではなく、開発の決まり（CLAUDE.md、docs/開発と運用/作るときの規格.md）か自動の確認（tests/）を足して止めます（けにーさん 2026-10-17）。報告にはその案を書きます。

## 公開のリポジトリに書かないこと

このリポジトリは誰でも読めます。

- **まだ直していないセキュリティの問題**は、題を一般的な言い方にし、起こし方・場所を書きません。中身は共有フォルダの控え（`booktown/総点検/非公開の控え.md`）に置き、直して本番に出たら台帳に書き足します。
- 鍵、メールアドレス、個人情報、本や読書家の ID、注釈モードの注釈の中身は書きません。

## 頻度

- 毎週金曜 19:05（日本時間）に簡易監査をし、その月の1〜7日の金曜は総合監査にします（運用指針8節、けにーさん 2026-10-18）。始めるのはプロジェクト運営スレッドの予定「毎週の点検」です。大型機能の完成時の点検と、自動で受け取る仕組みは、決まったらここに書きます。
- 毎週の簡易監査で、機能ごとのつまずきの数（管理表110）の先週の合計を読み、失敗の割合が前の週より上がった機能をけにーさんに伝えます。読み方は [docs/09](../09_段階2_ログインと保存.md)「つまずきの数」。20回に届かない欄は「20回未満」とだけ書きます。

## 毎週数える大きさ

けにーさん 2026-10-23「毎週の監査で見直すのがいいと思う」（資料とコードの整理が続いているかを見るため）。毎週の簡易監査で、その日の main を取り出して次の2つを数え、下の表に1行足します。

- まだ移していない仕様が残る docs/09 の行数とバイト数: `wc -l -c docs/09_段階2_ログインと保存.md`
- src のいちばん大きいファイルとその行数: `git ls-files -z src | xargs -0 wc -l | sort -rn | sed -n 2p`（1行目は合計）

表の前の行より、docs/09 の行数かバイト数、または src のいちばん大きいファイルの行数が増えていたら、台帳に1行足します（どのファイルがどれだけ増えたかと、増やした PR を書く）。減ったときと同じときは表に足すだけです。

| 日 | main | docs/09 の行 | docs/09 のバイト | src のいちばん大きいファイル | その行 |
|---|---|---|---|---|---|
| 2026-10-23 | `c3bee64` | 547 | 184,453 | `src/components/ScanSession.tsx` | 2,550 |
| 2026-10-23（#337 のあとの基準） | `b78a06a`（#337 の head） | 542 | 173,602 | `src/components/ScanSession.tsx` | 2,550 |

- 2つ目の行は、連続スキャンの仕様を docs/09 から移す #337 を、取り込む前にその head で数えた物です（#337 は src に触れない）。次の週はこの行と比べます。

## 毎週出す片付けの候補

けにーさん 2026-10-23「整理と片付けは定期的にやろう」。数えるだけでなく、毎週の簡易監査で、小さい片付けの候補を週に1本まで出します。

- 種類は次のどれか1つです: docs/09 の節を正本の資料へ移す、使われていないコードや古い資料を外す、大きいファイルを1つ分ける。画面と動きは変えません。
- 監査は候補（何を、どこへ、なぜ今か、触るファイル）を報告に書くだけです。作るのは開発スレッドで、ほかのブランチとぶつからないかはコーディネーターが確かめてから立てます。
