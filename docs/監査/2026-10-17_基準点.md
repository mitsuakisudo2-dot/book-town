### AUD-001 同じ ISBN を登録すると、ほかの読書家が手で入れた本の行を共有する

- 分野: ③データ設計（権限とデータの破損にもかかる）。管理表 4。
- 何が起きるか:
  - 読書家 A が ISBN のある本を手で入れ（`books` の `source = manual`、`created_by = A`）、人生の9冊や公開の棚に置くと、その行はほかの人の街にも読み込まれます。
  - 読書家 B が同じ ISBN をスキャンするか打つと、アプリは B の行を作らず、A の行をそのまま使います。B が打った題名は捨てられます。
  - そのあと A が題名・著者・ISBN を直すと、B のライブラリ・読書記録・投稿・棚の本が、B に知らせなく変わります。手元の試しでは、A が ISBN を上巻から下巻に変えると、B のライブラリと記録（本文は「上を読んだ」）が下巻を指しました。
  - B は自分では直せません（RLS で直せる行が0）。A の行が保留になっても B には知らせが来ず、保留の間は B の感想も作品から外れます。
  - A が退会すると `created_by` が空になり、その行は誰も直せず、保留にも答えられなくなります。
- 根拠: `src/lib/store.ts:827`（`const existing = decided ?? bookByIsbn(state.books, isbn);`。上のコメントは「otherwise any book the town has with the ISBN」）、`src/lib/library-journal.ts:598-600`（まとめスキャン）、`src/components/BarcodeRegister.tsx:160`。テスト `tests/domain.test.ts` 975-1050行「a book is already registered only when it is in the reader's library」がこの使い回しを求めています。DB の方針は `20261012000000_initial_schema.sql` の "people fix the books they typed in"。
- 仕様との食い違い: CLAUDE.md と docs/09「作品と版」は「登録＝`books` の1行、だれかが登録した1冊」、docs/09:149 は「自分の記録・印・棚は自分の登録のまま」。一方、退会の台帳 `tests/fixtures/account-tables.ts` は books を「a book is a catalog entry, not a person's」としていて、2つの考えが混ざっています。
- 確かさ: DB の動き（読める、記録を付けられる、直せない、ISBN の変更が広がる、知らせがない）は手元の台本で確かめました。アプリの使い回しはコードとテストで確かめました。
- 原因: 設計（登録と目録が混ざっている）。
- 直し方の案: 登録はいつも自分の行にします。同じ ISBN なら版と作品は DB がその場で同じにするので、行を分けても感想は作品に集まります。`registerBook` とまとめスキャンでは、ほかの人の行は題名の下書きに使うだけにし、上のテストも書き換えます。すでに共有している行は、`private.keep_copy` で控え → 共有している人ごとに自分の行を作る → ライブラリ・記録・投稿・棚を付け替える → `private.check_copy` で照らし合わせる、の順で移します。
- 悪用のされ方と、その確かめは公開しません（非公開の控え）。

### AUD-002 保存で1件断られると、待っていたほかの変更が全部捨てられる

- 分野: ③。管理表 18・36・37・46。
- 何が起きるか: 電波のない所で、ほかの人の便りに返信し、続けて読了の記録を感想つきで書き、書店をフォローします。電波が戻る前に相手が便りを消していると、返信は断られます。すると街が読み直され「保存できない変更があったため、保存されている状態に戻しました」と出て、関係のない記録とフォローも送られないまま消えます。本は「読了」と保存されたのに記録はない、という途中の状態が残り、記録の書きかけは先に消えているので言葉はどこにも残りません。消えた便りへのいいね、閉じた書店へのフォロー、別の端末で読書中のまま古いタブで「読書を開始」を押したときも同じです。
- 根拠: `src/lib/supabase/sync.ts:228-263`（断られると `reload("recovered")` で、待っていた変更を丸ごと置き換える）、`town-remote.ts:1217-`（書く順）、`initial_schema.sql:301`（読書中は1人1つ）。
- 確かさ: 確かめた。保存の仕組みを本物のまま、偽の DB で返信を外部キー違反で断らせると、記録は DB にも画面にも0件、フォローも消え、`library_entries` の読了だけが書かれました。
- 原因: 設計（書き込みの束を、1件の拒否でまとめて捨てる）。
- 直し方の案: 断られた1件だけを外し、残りは送り直す。外した物は書きかけに戻して「送れなかった物」として見せる。読み直す前に、待っていた変更を端末に控える（AUD-125）。

- 根拠: `src/components/AccountView.tsx:433-459`、`src/lib/store.ts:1308`、`src/lib/supabase/account-backend.ts` の `signOut()`。確かめた（画面の通し）。

### 書誌

**AUD-013 巻の書き方（「巻1」・BOOK・部・前編）を読めず、見逃しと誤った保留の両方が起きる**（③、4・6）
- 国立国会図書館の巻は「巻1」の形で来ますが、DB が巻を読む前置きは `(第|vol\.?|volume|book|part|no\.)` だけです。1巻の ISBN に「ONE PIECE 2」と打つと「近い」になり保留になりません。「1Q84 BOOK2」と「BOOK 1」、「第2部」と「第1部」、「上」と「前編」も「近い」でした。逆に、openBD だけが答えた「One piece 巻1」に正しい「ONE PIECE 1」と打つと保留になります。テストの見本（`tests/fixtures/bibliography.ts` の `sru()`）に本物の「巻1」の形がありません。
- 根拠: `20261102000000_bibliography_holds.sql:174`（`bib_volume`）、`20261101000000_bibliography.sql` の `ndl_answer`（207行〜）。確かめた（台本）。
- 案: 「巻」を前にも後ろにも読む（第1巻・巻1・1巻）。国立国会図書館の読み（transcription）も持つ。BOOK・部・前編／後編を巻として読む。共有フォルダの書誌の見本をテストの見本に入れる。直したら、もうある本を判定し直す。

**AUD-014 著者が合えば、題名が少しも重ならなくても「近い」になる**（③、4）
- 同じ著者の別の本の ISBN を打ち間違えても保留になりません（試しで「ノルウェイの森」の ISBN に「海辺のカフカ」など3つが「近い」）。本のページの見出し・作品・表紙が別の本になります。著者を書かなければ保留になるので、丁寧に書く人ほど見逃されます。
- 根拠: `20261102000000_bibliography_holds.sql` 192行〜の `bib_verdict`。確かめた（台本）。
- 案: 著者が合っても題名の言葉が1つも重ならなければ保留にする、または「題名が違う」の段を作る。どこまでゆるくするかはけにーさんの判断。

**AUD-015 国立国会図書館が記録を取り消しても古い書誌が残り、運営の一覧に出ない**（③、4）
- 取り元が「Record does not exist」に変わっても、国立国会図書館の分は誤った題名のまま残り、判定も変わりません。openBD は「なかった」で消すので、2つの扱いが違います。運営の一覧（`bibliography_review`）は保留と失敗4回以上しか出しません。
- 根拠: `bib_take`、`20261101000000_bibliography.sql:1133`。確かめた（台本）。
- 案: 「なかった」が2回続いたら運営の一覧に出し、数回続いたら国立国会図書館の値を使わない。

**AUD-016 国立国会図書館に聞ける量が規模に足りず、送る処理が待ちの行の数に比例して重くなる**（③⑦、4・5）
- 20秒に1冊、1日最大4,320件です。資料の見積もりは1万人で1日約3,300件（docs/09:281）、10万人ならその約10倍です。決まった聞き直しだけで版の数の約1/180件/日が要ります。本番では 429 と30秒を超える答えが出ていて（docs/09:282）、実際に聞ける数は上限より少ない見込みです。`bib_send` は期日の来た行を全部並べてから選ぶので、PGlite で期日の行2,000で159ms、40,000で2,569ms（行の数に比例）でした。
- 確かさ: 速さは台本で確かめた。量は資料の見積もりからの計算（推測）。
- 案: `bib_send` は `next_at` の索引で先頭の数件だけ取ってから並べる。聞き直しの間を使われ方で変える。一括データでの先取りと利用の相談（AUD-129・132）。

**AUD-017 保留の本でも、その ISBN の本の表紙が出る**（③、4）
- 保留は「ISBN が別の本らしい」と分かっている本ですが、表紙はその ISBN の本のものが出ます。見出しは本人の入力なのに表紙だけ別の本になり、公開の棚ではほかの人にも見えます。
- 根拠: `src/components/ui.tsx:351`・`:452`（`useCover(book.coverUrl ? undefined : book.isbn, book)`）。`Book` に保留の印がない。コードで確かめた（画面では流していない）。
- 案: 保留の本は装丁カードにする。保留をほかの人に知られないよう、「書誌が返った本だけ ISBN の表紙を使う」形もある。

**AUD-018 一部の表で、日時を端末が決めて送れる**（③⑤、43・88）
- 並び順や人数に使う日時の一部を、端末が送った値のまま DB が受け取ります。アプリ自身は送っていませんが、API から直接書けます。どの表かと確かめ方は非公開の控えにあります。

### 速さ

**AUD-040 特集「本棚をのぞく」「POP」の計算が、店×本×街の本の数に比例して重くなる**（⑦、58・88）
- `src/lib/features.ts:93-96` の `shownBooks` が棚の本1冊ごとに街の本を端から探します（`:161` も）。`bookById`（`src/lib/book-name.ts:194-200`）も端から探す作りで77か所から呼ばれます。合成した街で、1,000人 341ms、1万人 43.9秒（この機械。スマホは4倍ほど遅い見込み）。
- 案: 本の配列ごとに ID→本の Map を一度だけ作って使う（AUD-138）。

**AUD-041 人生の9冊の組み立てが、読書家の数の2乗で重くなる**（⑦、88）
- `src/lib/town-remote.ts:528-539` の `nineOf` が読書家1人ごとに9冊の行全体を絞り込みます。1万人で組み立て 9,954ms のうち、9冊を除くと 298ms。案: 最初に読書家ごとにまとめる。

**AUD-042 自分の反応を読むたびに、DB が反応の表を全部なめる**（⑦、88）
- `town-backend.ts:196-200` は条件なしの `select *` と件数を頼み、本人の分かは RLS の OR に任せるので索引が使えません。PGlite で20万件から200件を返すのに約106ms、1回開くと2回なめます。案: 本人の反応と自分の便りへの反応の2本に分ける。

**AUD-043 読んでいる間に行が増え続けると、街が開かず「つながらない」と出続ける**（⑥⑦、88）
- 1000件を超える表は数ページに分けて読み、その間に行が動くと街ごと読み直します。3回でだめなら「つながらない」を出し、間を空けて街全体を読み直し続けます。並び順の鍵が乱数の ID だと、どこに足されてもずれます。訪問者は見本だけの街で止まります。
- 根拠: `src/lib/supabase/sync.ts:272-298`（`load()`）、`:86-148`（`allRows`）。行がずっと動く表をまねると、1秒で24回読み、読み込みは終わらず「つながらない」が21回出た。
- 案: 最後のキーから続きを読む、または DB の関数1本で同じ時点の写しから返す（AUD-135）。

**AUD-044 初めて開いてから最初の便りまで約6.2秒（目標 2.5秒）**（⑦、58）
- 390px・遅い4G・CPU 4倍で、ログインしている人 6,244ms（触れるまで 8,494ms）、訪問者 6,168ms、2回目 1,197ms（触れるまで 8,116ms）。流れは HTML 0.6秒 → JS を読み終えるのが約4.3秒 → Supabase に24本、それぞれプリフライトつき → 描くのに約0.4秒。
- 案: AUD-045 の JS を減らす。最初の便りを JS と並べて取りに行く（AUD-134）。

**AUD-045 最初に読む JS がどのページも同じ**（⑦、58）
- どのページも `TownApp` を通すので、検索や本棚でもホームの部品を読み、ホームでも店や本のページ、ポスター、デモ用の保存を読みます。TownApp を使う12ページはどれも 1,131KB（gz 349KB、br 293KB）。中身は react-dom 約62KB・Next 約66KB・supabase-js 約68KB（使っていない realtime も入る）・アプリ約149KB（gz）。
- 案: ページごとに要る画面だけを読む。店と本のページを別ファイルにして後で読む。Supabase は auth と postgrest だけにする。

**AUD-046 Android と Windows で、Google の日本語の字を最大約2MB 読む**（⑦、58）
- `src/app/tokens.css:173-178` のゴシックの並びで、ウェブフォントの "Noto Sans JP" が端末の字より前にあります。Android の端末の字は "Noto Sans CJK JP" と名前が違うので、ウェブフォントを読みに行きます。日本語の字のない Linux の Chrome でホームを下まで送ると 2.67MB のうち 2.0MB が字でした。最初の便りは遅らせません（Linux で確かめた、Android と Windows は推測）。
- 案: 端末の字を Noto より前にし、ウェブフォントはポスターと見出しだけにする。

**AUD-047 書店めぐりを初めて開くと約3.2MB を読む**（⑦、33・58）

**AUD-048 CI に、大きさ・速さ・人数の見張りがない**（⑥、58・63）

## 8. 重点5つへの答え

### 重点1 書誌データの根本的な正しさ

- **よくできている所**: 作品・版・登録を分ける設計、ISBN の変換とチェックディジット、雑誌と価格のコードを断ること、旧字・異体字の扱い、取得の失敗の扱い、公開範囲（書誌の表は private、`book_bibliography` は公開か自分の本だけ）。まとめる・戻す・外すで記録は消えません。運営の直しは版のすべての登録に届き、判定もやり直されます。
- **間違った書誌が広がったとき安全に直せるか**: 版の書誌は直せますが、1つ前の状態に戻すこと、あとから経緯を追うこと（AUD-012）、取得元の取り消しに気づくこと（AUD-015）、非公開の版を直すこと（AUD-086）ができません。いちばん重いのは、書誌ではなく登録の行の共有で、ほかの読書家の打ち間違いが全員に黙って広がること（AUD-001）です。
- **シリーズ（6）の前に**: 巻の読み方が DB とアプリで違い、本物の「巻1」の形も読めません（AUD-013・087）。叢書とシリーズが混ざります（AUD-089）。6 の設計の前に決める所です。
- **規模**: 国立国会図書館に聞ける量は1日4,320件で、10万人の目標には足りません（AUD-016）。10分の待ちを使う案（AUD-129）と利用の相談（AUD-132）で大きく減らせます。

### 重点2 実際の利用シナリオ（新しく来た人が30冊を登録し、本棚を作り、書店に並べ、感想を書く）

| 段 | タップ | 迷った所 |
|---|---|---|
| 初めて開く | 0 | 「本を登録」の入口がない。タブは「本棚」、見出しは「ライブラリ」 |
| 30冊を登録（新しく26冊） | 約24（＋ISBN 4つと書名4つを打つ） | スキャン18冊はタップ0。二度読み・値段のバーコード・前回の本は自動で断る。検索は街にない本で行き止まり。本のページに「持っている」がない。取り消した本が残る |
| 本棚を作る | 約31 | 長い棚の名前で画面が崩れる。「棚」と書店の「本棚」の違い |

- **説明なしで使えるか**: 登録・整理・開店まではほぼ説明なしで進めました。連続スキャン（1冊あたり1タップ未満）と開店（12タップ）はよくできています。開店の画面、飾った店内、手に取った本の手触りは十分に楽しいです。
- **減らせる所**: 「本棚」の言葉と店の2つの編集をそろえる、本のページで自分の状態が分かりそこから店に並べられる、スキャンのあとにまとめて片づけられる。

### 重点3 想定外の操作への耐性

- **強い所**: いいねの連打（13回で DB に1行）、投稿・本屋を開く・退会・通報の二度押し、送り直しで二重にならない（ID は端末で決める UUID）、電波なしのスキャンの控え、存在しない ID の住所、同じブラウザでのアカウントの入れ替え（書きかけ・控え・既読・書誌の答えは持ち主ごと）。

### 重点5 思想が守られているか

- **守られている所**: 表紙はそのまま出し、AI のあらすじ・店主の写真・AI の画像はコードのどこにもありません。書店のフォロワー数は店主本人にだけ。公開にした本棚を見せる場所がまだないことを正直に伝えています。出典のページがあります。読書記録の既定（記録は自分だけ、状態は人数だけ）は画面と DB で決定どおりです。下のタブは決定どおり6個です。ログインしたばかりの空の街で0は出ません。
- **ずれている所**: 見本の人が人数と「いま」に混ざる（AUD-037）、総数「3 / 6」（AUD-063）、「あらすじは登録されていません」と無いことを書く（AUD-073）、人数だけが少人数で人を特定する（AUD-066）、順位を生みやすい計画（AUD-067）、AI の決まりが資料にない（AUD-124）。
- **操作が障壁にならないか**: 登録と開店は障壁になっていません。障壁は「ライブラリから書店へ」（AUD-053）と編集の分かれ方（AUD-056）です。

## 9. 確かめて問題なかった所

- `pnpm test:db` は全部通過（約57〜62秒）。lint 0・typecheck 0。CI と同じ tsx テスト55ファイルのうち53ファイルを流して PASS 1,007・失敗0。
- RLS: public・private・keep のどの表にもある。anon に書き込みの権限なし。public のビューなし。2026-10-20 より前からある public の関数で anon が呼べるのは害のない物だけ。
- security definer の関数60個はすべて `search_path = ''`。API から呼べるのは6つで、どれも呼んだ本人のことか誰でも見られる物だけを返す。
- 読めない列（`books.created_by`・`books.edition_id`・`reports.status`・`urgent`）は絞り込み・並べ替え・`on conflict` にも使えない。
- ブロックしたあとの反応・ネタバレの報告・返信・フォロー・店への反応は断られる。通報の重みは、新しいアカウント3つの通報ではたたまない。
- 書誌の非公開の扱い: 非公開の登録の有無は、作品の ID・エラー・待つ行の鍵・公開の本のキャッシュからは分からない。pg_net の URL に入る ISBN は13桁に限られ、取得先は2つで固定。
- 退会は呼んだ本人の行だけを消し、台帳のテストが全部の表の全部の列で通る。
- 画面に渡す鍵は publishable だけ。リポジトリと履歴に鍵らしい文字列なし。フォークからの PR では Actions に鍵が渡らない。文字の列にはすべて字数の上限。
- 新しいマイグレーションの名前の順番は `scripts/check-migration-versions.sh` が CI で止めている（先の日付まで進んだ名前でも、今日の時刻で作ると CI が断る）。
- 管理表の「先に要る」はすべて自分より小さい番号で、β前が後の時期に頼っていない。
- 本番（10-17、select）: マイグレーション23本がリポジトリと一致、書誌の取得は20秒ごとに動き失敗0。
- キャッシュの決まりは `vercel.json` と `tests/head.test.ts` が一致。
- 日本時間の扱い（`tonight.ts`・`social.ts`・`notifications.ts`）は正しい。
- localStorage に残す物にはどれも上限がある（ポスターの書きかけだけ上限なし、小さい心配）。

## 10. 確かめられなかった所と理由

- 本番の画面（booktown.page）: 作業環境から届かず、Vercel の読み取りも 403。
- 本番 Supabase の一部の設定（新規登録の停止、JWT の期限、ログインの記録を DB に残すか、`max_rows`、マイグレーションの外で作られた物の有無、`private.staff` の中身）: 読むだけの約束の範囲で見ていない。
- 本物の PostgREST を通した確かめ（`pnpm test:supabase` は Docker が要る）と、本物の Postgres での速さ（PGlite だけで測った）。
