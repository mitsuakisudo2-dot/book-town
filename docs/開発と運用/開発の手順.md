ブランチの切り方、ほかの作業とぶつからない見方、手元とCIの確かめ、取り込みの注意の正本です。作るときの共通の物は [作るときの規格.md](./作るときの規格.md)、だれが何をできるかは [権限と鍵.md](./権限と鍵.md)、本番に出る道は [本番への反映.md](./本番への反映.md) にあります。資料の全体は [../README.md](../README.md) にあります。新しくわかった手順は、ここに書き足してください。

ここには、時間とともに古くなる「今だれが何をしているか」や取り込んだ PR の歴史を書きません（下の「今の作業の見方」）。

## 今の作業の見方

同じファイルを2か所で直さないための決まりです。今だれが何を作っているかの正本は、運営のプロジェクトのスレッドの一覧と、GitHub の開いている PR です。このメモには一覧を書きません（古くなって、初めての人を間違った方へ連れて行くため）。

- **最新のコードは `main`。** 新しい作業は `main` から新しいブランチを切って始めます。2026-10-12 にブランチ `claude/book-town-sns-features-3ij9a9` を `main` にまとめ、書店めぐり Phase 1・2（旧PR #6・#7）、使い勝手の改善（旧PR #3）、POP の切り替え（旧PR #5）はすべてここに入っています。`feat/woodshop-phase2-20261012` などの古いブランチから続けません。
- 始める前に、開いている PR と、main に入っていないブランチ（`git branch -r --no-merged origin/main`）を見て、自分が触るファイルをほかの作業が触っていないか確かめます。ブランチがあっても、だれかが今も作業中かはリポジトリだけでは分かりません。触りそうなら、触る前にユーザーに聞いてください。
- スレッドの一覧が見られない人は、見られないことを前提に、ぶつかりそうなファイルは聞いてから触ります。
- **取り込む前に必ず:** main を取り込み直し（`git fetch origin main` → `git merge origin/main`）、ぶつかったファイルがないか確かめ、通しの確認を流し直してから、承認が要るものは取り込みのカードを出します。取り込みは1本ずつです。

## 作る前にオープンソースを調べる

けにーさんの決まりです（2026-10-27）。原文:

> 不慣れな機能はゼロから書かないでください。まずGitHubなどのオープンソースサイトでオープンソースプロジェクトを検索し、アイデアを比較してから着手してください。検索後、まず取捨選択を示し、実装をそのまま持ち込むのではなく、参考プロジェクトが解決するシナリオ、導入する依存関係、現在の要件との違いを明確に記述してから、最小限の検証を行ってください。

ほかのサービスの作り方や評判を調べること（画面や体験の参考）とは別で、こちらは中身の作り方を調べます。BookTown では次のように使います（運営の補足。けにーさんの了承はまだです）。

- **使う場面:** 新しい仕組みを作るとき（バーコードの読み取り、グラフ、検索、画像の処理、ログインまわりなど）。画面の小さな直しや、もう BookTown にある仕組みの直しでは調べません。
- **順番:** 1 GitHub などで探して2〜3件を比べる → 2 取捨選択を示す → 3 最小限の検証 → 4 作る。
- **最小限の検証:** 本体に組み込む前に、小さな試作で要件のいちばん難しい所（例: 暗い所で ISBN が読めるか、320px で収まるか、ページの JS がどれだけ増えるか）が動くかを確かめ、結果を取捨選択に書き足します。試作は本体に入れません。
- **取捨選択に書くこと:** それぞれについて、解決している場面、持ち込む依存、今の要件との違い、使ってよい決まり（MIT など）、今も手入れされているか、重さ（ページの JS が増えるか）。
- **持ち込まないも選べる:** 比べた結果、自分で書くほうが小さくて安全なら、理由を添えてそうします。実装を写さず、考え方を借ります。
- **依存を足すとき:** 新しい依存は下の「してはいけないこと」のとおり勝手に足しません。取捨選択を添えて、けにーさんに提案してから足します。

## 作業の手順で気をつけること

- **取り込み:** けにーさんへの言葉は平易に（PR は「提案書」、merge は「本体に取り込む」）。取り込みは1本ずつです。了承が要るか、承認なしで取り込める軽微な直し・資料だけの変更かの正本は、リポジトリの外の運営の指示（運用指針の4章）です。見られないときは取り込まずにユーザーに聞きます。CODEOWNERS のファイルと、権限・安全設定・その確かめに関わる変更は、CI が通っていてもけにーさんの承認のあとに取り込みます（[権限と鍵.md](./権限と鍵.md)「main を守る決まり」）。main に入ったマイグレーションは、けにーさんの承認のあと本番に入ります（[本番への反映](./本番への反映.md)）。
- **持ち主の承認が要るファイル:** [権限と鍵](./権限と鍵.md)「main を守る決まり」。
- **見直しの重さ:**
  - 小さな直し（画面が変わらない直し、確認の手順の直し、数行の直し）は見直し1回です。
  - DB、ログイン・お金・権限、ホームの大きな画面は、2人で見直します。
  - 迷ったら大きい側にします。
- **自動の確認（CI）を弱める変更はしません。** 必要なら、けにーさんの明示の了承を取ってからにします。
- **GitHub は REST で操作します**（GraphQL は 403 になることがあります）:
  - 提案書を出す: `gh api repos/mitsuakisudo2-dot/book-town/pulls -f title -f head -f base -F draft=true -F body=@file`
  - 下書きを外す: `POST .../pulls/N/ccr/ready_for_review`
  - 取り込む: `PUT .../pulls/N/merge -f merge_method=merge -f sha=<先頭の sha>`
  - CI の結果: `commits/<sha>/check-runs`
- **本番の確かめ:** [本番への反映](./本番への反映.md)「本番の確かめ」。
- **通しの確認（手元）:**
  - ブラウザ: CI と同じ Chrome Headless Shell を使います。CI は `pnpm exec playwright install chromium` で入れるので、版は入っている Playwright が決めます（2026-10-15 は Playwright 1.64、Chrome 156）。作業環境に前から入っているブラウザは古いことがあるので、`BOOK_TOWN_CHROME` で 156 を渡します。
  - デモのビルド: `env -u NEXT_PUBLIC_SUPABASE_URL -u NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY pnpm build`
  - ログインのビルド: `NEXT_PUBLIC_SUPABASE_URL=https://test-project.supabase.co NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_test pnpm build`
  - 立て方: `python3 -m http.server <port> --directory out` で立て、`BOOK_TOWN_URL`・`BOOK_TOWN_CHROME`・`BOOK_TOWN_QA_OUTPUT` を渡して `flock` で1本ずつ流します。ビルドで `out/` が作り直されるので、毎回ビルドしてから流します。
  - ページの JS の大きさ（`pnpm test:page-js`）を main と比べるときは、両方を同じ場所でビルドします。同じコミットでも、作業環境の `/home/user/book-town` と別の worktree とでは、どのページも gz で約1KB違いました（2026-10-23、管理表112。理由は未確認）。
  - 画面の通しの確認は、2026-10-16 から全部が CI で走ります（feedback と poster-journey は demo-journeys に足しました）。手元で流すのは、直した画面の通しと、CI で落ちた通しの原因を探すときです。
  - クラウドの作業環境では、始まりに `.claude/hooks/session-start.sh` が `pnpm install --frozen-lockfile` を済ませ、`BOOK_TOWN_CHROME` に入っている Chromium を渡します（作業環境からは Playwright のブラウザを落とせないため。CI より古い版です）。
- **通しの確かめで「まだ読んでいる間」を見るとき（AUD-120）:** 読み込みを決まった秒数だけ遅らせて、その間に画面を見る書き方はしません。`page.goto` はページの書体まで待つので、遅い CI ではその秒数が先に終わり、確かめが見る前に読み終わっています（2026-10-17〜18、ログインの通しのホームの骨組みと前回の便りで3回）。代わりに答えを止めて、見終えてから放します（`tests/login-journey.mjs` の `holdTown()`・`holdOwnProfile()`）。画面の中のタイマー（3.6秒で消える案内など）は `page.clock` を止めて見ます（`tests/walk-journey.mjs` の最初の書店めぐり）。`page.clock.runFor` で時計を進める前は、ページが前の答えを受け取り終えたことを画面の変化で確かめます。網の返事が届いただけでは、ページが受け取るのが時計を進めたあとになり、「さっき読んだばかり」になります（ホームに戻った新しい便りの読み込み。レンの顔が「新しい便り」に加わるのを待つ）。
- **「戻る」の層（`src/lib/back-layer.ts`）:** 遅いスマホでは、離れた画面の片付け（React の passive effect のあと片付けと `setTimeout(0)`）が数秒待たされ、読書家が「戻る」で戻ってきたあとに走ることがあります。層を外す処理は、外した時から履歴が動いていないとき（`popstate` の数が同じとき）だけ段を消します。層の登録と片付けは `useLayoutEffect` で、画面を離れたその時に行います。確かめは `tests/app-journey.mjs` の「on a slow phone, 戻る from another page returns to the step left」（CPU を6倍遅くして、本屋を開く途中でホームへ出て戻る）。ただし、ページ自身が戻している途中（小窓を閉じてその段が外れるまで）の `popstate` は数えません。数えると、返信の小窓を閉じてすぐ便りのページを閉じたとき、便りが外れた段の上でもう一度開きます（2026-10-17、ホームの通しが CI で時々落ちていた原因。確かめは `tests/home-journey.mjs` の「a 便り's page: by keyboard…」で、小窓と便りを5ミリ秒の間に閉じる）。
- **同時に動かす確かめ:** 書誌マスタの判定・保留・聞く順は、DB のテスト（PGlite、1本ずつ流れる）のほかに、本物の Postgres 17 で登録・直し・運営の道具・裏の回を同時に動かし、終わったあとにデータの食い違いがないかを確かめています。台本と手順は共有の資料「書誌マスタ_同時の確かめ」にあります（`pg` を使うのでリポジトリには入れていません）。この辺りを変えるときは、もう一度流してください。
- **DB のテストの時計:** PGlite の `now()` はミリ秒までなので、続けて流した2つの文が同じ時刻になることがあります（本番はマイクロ秒）。同じ時刻だと、時刻で決まる並び（どの版を先に問い合わせるか）が乱数の ID の順になり、テストがときどき落ちます。置いた順・問い合わせた順を確かめるテストは、`oneMomentEach`（`tests/fixtures/pglite-supabase.ts`）を通した db を使います（`tests/db-bibliography.test.ts` の `migrated`）。
- **使い心地の見直し:** 画面に関わる変更は、取り込む前に `.claude/skills/booktown-ux-review` の物差しで見直します（スマホの幅で実際に触り、0・戻る・書きかけ・押しやすさなど）。見た目が変わるものは、取り込む前に 320px と 390px の画像をけにーさんに見せて OK をもらいます（了承の正本は運営の指示の運用指針4章、けにーさん 2026-10-23）。ただし、はみ出し・崩れの直しで新しい物や言葉を足さない物は、前後の画像を添えて先に取り込み、あとで見てもらいます。見た目を変える選択がある物（要素を外す・置き換えるなど）は先に見てもらいます（けにーさん 2026-10-28）。
- **してはいけないこと:**
  - `git add -A` と、むき出しの `git stash`。
  - 作業用の `tests/zz-*` をコミットすること。
  - 新しい依存を足すこと（入れるのは `pnpm install --frozen-lockfile` だけ）。
- **鍵と個人情報:** [権限と鍵](./権限と鍵.md)「鍵の決まり」。
- **Supabase の接続（MCP）:** [権限と鍵](./権限と鍵.md)「作業環境の接続」。
- **作業役（Agent）に渡すとき:** 長いコマンドは前面で流すこと、push しないことを書きます。終わったら worktree が片付いているか、サーバーが止まっているかを確かめます。
