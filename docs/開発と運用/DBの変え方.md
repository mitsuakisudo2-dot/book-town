# DB の変え方

マイグレーションの書き方、本を指す物を足すときの決まり、退会とブロックの台帳、データを移す前の控えと戻し方、DB の確かめの正本です。だれが何を読めるかは [公開範囲.md](../機能/公開範囲.md)、main に入ったマイグレーションが本番に入る道は [本番への反映.md](./本番への反映.md) にあります。

## 書き方の決まり

- 一度適用したマイグレーションは書き換えない。変更は新しいファイルで足す。main にあるマイグレーションの中身を変える・消す・名前を変える提案書は、CI（`scripts/check-migration-versions.sh`）が止める（AUD-180）。ファイル名の頭の14桁は版の番号で、暦の日付ではない（版は日付より先に進んでいる）。
- 新しい表には必ず RLS と権限を書き、`pnpm test:db`（`tests/database-policies.test.ts`）に確認を足す。台帳（`tests/fixtures/account-tables.ts`）にも1行足し、退会のテストに消える人の行を入れる（下の「アカウント削除の型」）。
- 版 `20261020000000`（`privacy_locks`）のマイグレーションから、public に新しく作った表・関数は誰にも開かれていない状態で始まる。関数も、呼ばせたい相手に `grant execute` が要る。
- 今あるデータを移すマイグレーションは、控えを取ってから移し、照らし合わせる（下の「移す工事の前の控えと戻す手順」）。

## 本を指す物を足すとき

- 手で入れた本をだれが読めるか（決まりそのもの）は [公開範囲.md](../機能/公開範囲.md)「表と公開範囲」の「手入力の本は、使われている場所で読める」。
- 決めるのはデータベースの関数 `private.book_is_listed`（公開の場で使われているか）と `private.book_is_mine`（読む本人が使っているか）で、`books` の読み取りの方針がこの2つと下の `private.book_is_shared` を聞く（今の方針は `20261029000000_visibility.sql`）。本のIDを持つ表や列を足すときは、方針は変えずに、この2つを `create or replace` で広げる（関数の `set` の行は残す）。広げ忘れると、その本が画面から消える（本を指す外部キーが増えると、`pnpm test:db` の「every book a reader sees used, they read」が気づかせる）。もう1つ、`private.book_is_shared`（フォロワー限定の記録の本を、その記録を読める人に見せる。`20261029000000_visibility.sql`）も同じ方針が聞く。フォロワー限定で使える物（棚など）を足すときは、こちらも広げる。読み取りの方針と3つの関数、`private.seen_book_ids`、`private.search_candidates`、`copy_book` が、いろいろな作り方・使い方の本と読書家（フォロー、両向きのブロック、運営が隠したもの、退会など）で同じ答えを出すことと、手で作った本をだれが読めるかは `tests/db-who-sees-books.test.ts` が確かめる。本を指す使い方を足したら、そのテストの `CASES` にも1冊足す。
- 本を指す jsonb を足したときは、目録の行を取り出すときに残す `private.catalog_used` も広げる（[本と書誌](../機能/本と書誌.md)「図書館の目録」）。
- 同じ決まりを1つの問い合わせに書いた `private.seen_book_ids`（街の新しい本と検索が使う）も、広げるときも狭めるときも同じに直す。使う表が足りないと `tests/db-newest-books.test.ts` が、作った街の本と読書家で答えが違うと `tests/db-who-sees-books.test.ts` が止める。本を名指す行の候補 `private.search_candidates` も広げる。
- 速さ：方針は、読む人に見せない手入力の本ごとに、この2つを聞く。自分の本屋は ID を先に見つけ、その1軒の棚だけを探す。公開の棚と店内は、本屋が何軒でも GIN の索引で探す（本屋が数百軒より少ないと、データベースは棚の中身を開く手間を数えずに1軒ずつ読むほうを選ぶので、`book_is_listed` は順に読む計画を使わない設定にしてある）。街の新しい300冊は `books_created` の索引で新しい順に読み、読める本が300冊になったところで止まる。それより新しい、見えない手入力の本の数だけ時間がかかる。`pnpm test:db` の「a book is asked about without searching every shop」が、この計画を確かめる。

## アカウント削除の型（2026-10-16、管理表の2）

表を足すたびに、退会で消し忘れる所とブロックの抜けが出ないようにする仕組み。

- **台帳。** `tests/fixtures/account-tables.ts` に、全部の表について「人を指す列が退会でどうなるか」（行ごと消える `delete`／列が空になる `forget`）と「ブロックした相手に見えるか」（本人だけ `own`／ブロックで隠す `blocks`／別の表を通して読む `via`／API から誰も読めない `nobody`／理由つきで見える `open`）を書く。
- **台帳と DB の照らし合わせ（`tests/account-tables.test.ts`）。** 次のどれかがあると `pnpm test:db` が止まる。
  - 台帳にない表がある。
  - 人（`auth.users`・`profiles`）を指す外部キーが、退会を止める形（on delete の指定なし）になっている。
  - 外部キーの消え方と台帳が違う。
  - 人と一緒に消える行（投稿、店など。そこから連鎖して消える表も）を指す外部キーが、連鎖も空にもならない形になっている（退会が止まる）。
  - 外部キーのない uuid の列が、人を指すかどうか台帳に書かれていない（主キーでも、`id` という名前の1列の主キー以外は同じ）。
  - 新しいスキーマやビューの表も台帳に要る（Postgres と auth の分だけ除く）。
  - `blocks` の表の読む規則が `is_blocked_with` を聞いていない（規則が呼ぶ関数の中で聞いていればよい）。`own` の表の規則が `auth.uid()` を聞いていない。`nobody` の表を API から読める。
  - わざと間違えた表を足して、それぞれ止まることもテストで確かめている。
- **退会の通し（`tests/database-policies.test.ts` の「deleting an account removes everything it owned」）。**
  - 台帳で人を指す列の全部に、消える人（ベン）の行を入れる。
  - 退会の前に、ベンと互いにブロックしたチーとして、`own` と `blocks` の表を読み、ベンの行が1つも見えないことを確かめる（規則の字面だけでなく、実際に読めるか）。
  - 退会のあと、全部のスキーマの全部の表の全部の列（文字や JSON の中も）に、ベンの ID が残っていないことを確かめる。台帳で「残す」とした列（上の通報と非表示）だけは除く。控えの中の確かめは `tests/db-copies.test.ts` にある。
- **表を足すとき。** 台帳に1行足し、退会の通しで消える人の行を入れる。どちらかを忘れると止まる。
- **今あるブロックの抜け**（43 で決める）: ブロックした相手にも、人生の9冊（`profile_nine`）が見える。投稿を書いた人と本屋の店主には、ブロックした相手からの反応（`post_reactions`、`pop_reactions`）も見える。台帳に理由を書いて残している。

## 移す工事の前の控えと戻す手順（2026-10-16、管理表の3）

今あるデータを移す工事（作品と版など）を安全に始めるための手順。Supabase は無料の段で毎日の控えがないので、工事のたびに、移す表の控えを DB の中に取る（毎日の控えは管理表の46）。

- **控えの置き場所。** 同じ DB の `keep` スキーマ。API にも、ログインした人にも、service_role にも開いていない。行は DB の外に出ないので、公開のリポジトリにも Actions のログにも載らない（エラーの文も、表の名前と件数だけにしている）。マイグレーション `20261026000000_moving_copies.sql`。
- **移す工事のマイグレーションの書き方。** 1つのファイルに、控え → 移す → 照らし合わせ、の順で書く。

  ```sql
  select private.keep_copy('20261101000000_works',
    array['public.books', 'public.posts']::regclass[]);
  -- ここで移す
  select private.check_copy('20261101000000_works');
  ```

  - 控えの名前は、そのマイグレーションのファイル名（拡張子なし）。
  - 移す表と、その表をトリガーで追いかけている表（`book_marks` と `library_entries` など）を全部控える。主キーのない表は控えられない。
  - `keep_copy` は控える表を全部まとめて押さえ、ファイルの終わりまで書き込みを待たせる（読むのは止めない）。押さえるのに10秒待っても書き込み中の人が終わらなければ、工事ごと止まる（もう一度流せばよい）。
  - `check_copy` は、控えにあった行が主キーで見つからない（失った行）か、外部キーの列が控えでは入っていたのに今は空か列ごとない（失ったつながり）を数え、1つでもあれば例外を出す。ファイル全体が1つのトランザクションなので、移した分も控えも取り消され、本番は元のまま。意図して減らす表は、つながりなら2つ目の引数、行なら3つ目の引数に渡すと、数えて記録するだけにする（`check_copy(名前, array['public.x']::regclass[])` はつながりだけ、`check_copy(名前, '{}', array['public.x']::regclass[])` は行だけ）。主キーが変わった表は行を照らし合わせられないので止まる。
  - 移す SQL も、行の値を含むエラーを出さないように書く（`raise exception` には件数と表の名前だけ）。Postgres 自身のエラー（一意や check の違反）は行の値を含み、Actions のログは公開のため。
  - `supabase db push` はファイルを1つのトランザクションで流すが、`create index concurrently` などは外で流す。控えを取るファイルにこれらと `begin`・`commit` を書くと、`pnpm test:db` が止める。
  - 照らし合わせた数（前後の件数、失った行とつながり）は `keep.copies.checked` に残る。Supabase の接続（select だけ）で読める。

- **戻すとき。** 新しいマイグレーションで `select * from private.restore_copy('20261101000000_works');` を呼ぶ（本番への書き込みなので、取り込みの了承が要る）。
  - 控えの行を全部書き戻す（なければ足し、変わっていれば控えの値に戻す）。親の表から順に書く。そのあいだ表のトリガーは止める（更新日時などは控えのまま）。
  - 控えのあとに増えた行は残る。消すときは3つ目の引数を `true` にする（その行から連鎖して消えるものも消える）。
  - 表を選ぶときは2つ目の引数に配列で渡す。
  - 控えのあとに親が消えた行（退会した人の行、消えた投稿への返信）は戻さない。親が消えたら空になる外部キー（set null）の列だけは、空にして戻す。
  - 戻したあとで、同じ値の一意の列（ハンドルなど）がぶつかると、全体が止まって何も変わらない。そのときのエラーは表の名前と SQLSTATE だけにして、行の値は出さない。
  - 行を1つずつ控えの値に戻すので、移す工事が2つの行のあいだで一意の値を入れ替えていると、戻すときにぶつかる。そういう工事を戻すときは、戻すマイグレーションで先にぶつかる値をよけてから `restore_copy` を呼ぶ。
  - 止めていたトリガー（もともと止まっていたもの）は、戻したあとも止まったまま。
  - 戻した表、戻した行、戻さなかった行、消した行の数を返す。
- **退会と控え。** 控えを取るとき、行ごとに「退会で一緒に消える人」を `keep_owners` の列に書いておく（その行の人への連鎖のほか、連鎖の外部キーをたどった先の持ち主。店の非公開の棚は店主、返信と反応は元の投稿の書き手）。控えがあるあいだに退会があると、`auth.users` のトリガー（`forget_in_copies`）が、全部の控えからその人と一緒に消える行を消し、元の表で空になる列（本の作成者）は空にする。元の表が運営のために残す行（その人への通報）は、控えにも残る。手で消した控えがあっても、退会は止まらない。
  - たどるのは人まで5段まで。もっと遠い表は `keep_copy` が断る（そのときは、たどり方を広げてから控える）。自分の表を指す連鎖（返信の返信）だけは5段で止まり、それより深い行は退会のあとも控えに残る（その人の行ではなく、ほかの人の返信。親が消えているので戻されず、`drop_copy` で消える）。今の返信は1段まで。
- **片付け。** 本番で確かめたら（管理表で「本番確認済み」）、次のマイグレーションで `select private.drop_copy('20261101000000_works');` を呼んで控えを消す。退会した人の行は控えからも消えるが、控えを長く置かない。開いている控えは下の「開いている控え」に書く。
- **試したこと。**
  - `pnpm test:db`（`tests/db-copies.test.ts`）: 行を失う工事・つながりを失う工事・列を消す工事が丸ごと取り消されること、失わない工事が控えを残すこと、あとから壊したものを戻すと控えを取る前と全部同じになること、増えた行の扱い、選んだ表だけ戻すこと、トリガーが止まって戻ること、複合キーと自分の表を指す外部キーの戻し方、退会した人と一緒に消える行（店の非公開の棚、投稿への返信と反応）が控えからも消えて戻らないこと、戻せないときのエラーに行の値が出ないこと、手で消した控えがあっても退会できること、API の役から届かないこと、控えの名前と主キー、片付け。
  - 2026-10-16、手元の本物の Supabase（CLI 2.120.0、postgres は superuser でない本番と同じ形）で一度ずつ: 全部のマイグレーションが流れること、行を失う工事が取り消されること、控えを取って本を書き換え、投稿を消して記録を書き換えたあと、`restore_copy` で4つの表の中身（md5）が工事の前と同じに戻ること、認証の管理 API でアカウントを消すと控えからも消え、そのあと戻してもその人の行が戻らないこと、REST から `keep` と `private` に届かないこと、`drop_copy` で片付くこと。

## 開いている控え（`keep`）

- 移す工事で控えを取ったら、ここに名前を書き、本番で確かめて `private.drop_copy` で消したら消す（上の「片付け」）。
- `20261105000000_own_book_rows`（#156）と `20261106000000_own_books_only`（#168）、自分の本の行の控え: どちらも本番で確かめた（2026-10-18。2本目は `keep.copies.checked` で失った行もつながりも0）。1本目は2本目が、2本目は版を確かめて書く（`20261107000000_write_versions`）が `drop_copy` する。
- `20261118000000_bibliography_judging`（判定の直し、#245）の控え: 本番で判定し直しの前後と `keep.copies.checked`（失った行もつながりも0）を確かめ、取り元の直し（#250、`20261119000000_bibliography_fetching`）が `drop_copy` で消した（2026-10-19）。
- `20261125000000_authority_qualifiers`（AUD-163、#268）と `20261128000000_authority_trades`（AUD-167、#277）と `20261129000000_credit_names`（AUD-168、#282）と `20261201000000_credit_roles`（AUD-170）、著者の名前の作り直しの控え（書誌の答え・本・判定・検索の言葉）: 本番で `keep.copies.checked` と名前を確かめたら、次の目録のマイグレーションが `drop_copy` で消す。
- #97 作品と版と #106 見せる範囲の控えは、`20261030000000_drop_kept_copies` で消した。#116 版の ID の控え（`20261031000000_edition_ids`）は、本番で確かめて書誌マスタ（`20261101000000_bibliography`）で消した。

## 確かめ

- `pnpm test:db`: PGlite（Node.jsで動くPostgres）にマイグレーションを流し、ログインなし・本人・他人の立場で、読める・書ける・拒否されることを確かめる。
- `pnpm test:supabase`: 手元で `supabase start` した本物の Supabase（ログイン、コードのメール、REST、RLS）に対して、招待、コードでのログイン、最初のプロフィール作成、ログアウトを通す。続けて2人の読書家が街を使い、保存したものが読み込み直しても残ること、公開したものだけが相手に届くこと、断られた変更が画面で戻ること、つながらないあいだの変更があとで保存されることを確かめる。`supabase status -o env` の値を環境変数に入れてから実行する。
- `pnpm test:town-sync`: データベースなしで、行から街と書店めぐりを組み立てる処理と、書き込みの計画を確かめる。
