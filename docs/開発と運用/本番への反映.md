# 本番への反映

main に入ったものが本番に出るまでの道と、それぞれの承認、確かめ方、戻し方の正本です。鍵の置き場と、だれが承認できるかは [権限と鍵.md](./権限と鍵.md) にあります。取り込み（マージ）にだれの了承が要るかは、リポジトリの外の運営の指示（運用指針の4章）が正本です。

## 本番が変わる道

本番は https://booktown.page です（Vercel のプロジェクト `book-town-851k`。`www.booktown.page` は booktown.page へ送り、`book-town-851k.vercel.app` もそのまま開けます）。main への取り込みが、そのまま本番への公開になります。

| 道 | いつ動くか | 承認 | どこに書いてあるか |
|---|---|---|---|
| サイト | main に入ったとき、Vercel 自身の GitHub 連携がビルドして公開する | なし（main だけ） | 下の「サイト」 |
| サイトの出し直し（ensure） | main に入ったとき、Vercel が作り始めなかったら | なし（main だけ） | 下の「サイト」 |
| DB のマイグレーション | `supabase/migrations/` のファイルが main に入ったとき | apply でけにーさん | 下の「DB のマイグレーション」 |
| ログインの設定 | `supabase/hosted-auth.json` などが main に入ったとき | apply でけにーさん | 下の「ログインの設定」 |
| Vercel の手の動き（main の deploy、rollback、promote-latest、domains-apply、mail、mail-apply） | Actions の画面から手で | けにーさん | 下の「Vercel の手の動き」と「戻す」 |
| 図書館の目録の取り込み | 毎晩と手で | なし（目録の行しか書けない役割） | docs/09「図書館の目録」 |
| 目録の役割のパスワード | 手で | けにーさん | docs/09「図書館の目録」 |

- どの道も、main 以外のブランチと PR からは本番を変えられません。PR の実行には鍵が渡りません（権限と鍵「鍵の決まり」）。
- ワークフローのファイル（`.github/workflows/`）は、コメントだけを直しても、main に入るとそのワークフローが動きます。承認つきの段（ログインの設定の apply など）は、中身が同じでもけにーさんの承認待ちになります（2026-10-22、#320 で supabase-auth.yml のコメントを直したとき）。ワークフローを触る PR は、取り込むと承認待ちが出ることを先にけにーさんに伝えます。
- 取り込む前に、CI（`.github/workflows/ci.yml`）が PR ごとに、型チェック、lint、ドメインテスト、データベーステスト、ビルド、ブラウザでのログイン、本物の Supabase でのログイン、デモのビルドでのブラウザの通し確認を回します。画面の通しの確認は 2026-10-16 から全部が CI で走ります。

## サイト

- main に入った変更は、Vercel の GitHub 連携が本番に出します（`vercel.json` の `git.deploymentEnabled`）。これは GitHub の外で動くので、GitHub の環境の承認は掛かりません。
- `claude/` で始まるブランチ（Claude の作業ブランチ）では、確認用の URL を自動では作りません。Vercel の無料プランはデプロイが24時間で100回までで、確認用の URL で使い切ると main を取り込んでも本番が作られないためです（2026-10-13 に一度起きた）。確認したい `claude/` のブランチは、下の Vercel の deploy で作ります。ほかのブランチはプレビューだけが作られます。
- main に入ったときは Vercel のワークフロー（`.github/workflows/vercel.yml`、`scripts/vercel.mjs`）の ensure が動き、Vercel が自分でその変更を作り始めなければ（またはすぐ止まったら）、同じ main を出し直します。巻き戻し・切り替え・ドメインと DNS の変更はしません。本番の公開が始まらなかったときの直しなので、承認で止めません（けにーさん 10-21「通常の本番公開とensureによる再試行は自動のままにしたい」）。
- ビルドには `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`（または旧名の `NEXT_PUBLIC_SUPABASE_ANON_KEY`）を渡します。どちらも公開してよい値で、なければデモのまま動きます。Vercel では種類を「Config」にして、Production、Preview、Development のすべてに入れます（「Secret」で保存すると書き込み専用になり、あとから種類を変えられないので、消して作り直す）。収益を得る段階では Vercel の有料プランが要ります。

## DB のマイグレーション

`supabase/migrations/` のファイルが main に入ると、Deploy database（`.github/workflows/deploy-database.yml`、`scripts/migration-plan.mjs`）が3つの仕事で本番に入れます（2026-10-20）。

- **plan**: 読むだけの鍵で、本番のマイグレーションの履歴を読みます。本番にあってリポジトリにない版、本番に入った版より古いのに入っていないファイル、同じ版の番号の2つのファイルのどれかがあれば、赤で止めます。本番にまだ入っていないファイルを全部、名前・中身の指紋（sha256）・データを失いうる操作（表や列や schema を消す、`truncate`、`delete from`、`where` のない `update`、`on delete cascade`）とともに実行の Summary に並べます。PR からではなく、本番の履歴との差で並べます。「none found」は安全の証明ではありません。
- **apply**: 入れる物があるときだけ動き、けにーさんの GitHub での承認を待ちます。承認のあと、`supabase db push --dry-run` が挙げるファイルと中身が plan の一覧と1つでも違えば、何も流さずに止めます。同じなら流します。
- **applied**: もう一度読むだけの鍵で履歴を読み、一覧の全部が入ったことを確かめます。
- 承認の前に、けにーさんが Summary を見ます。Claude は承認を押せないので、承認を待つ実行が出たらけにーさんに頼みます（権限と鍵）。
- 入れる物がないときは、手で動かしても plan だけで終わります。
- 動いている反映は途中で止めません（`cancel-in-progress: false`、手でも止めない）。途中で止まったときは、履歴だけで「入っていない」と決めず、そのファイルが作る・変える表・列・関数・権限とデータを本番で select して確かめ、残った変更とぶつからない形で入れ直します。消して戻しません（障害への対応や変更の取り消しを理由に、利用者が保存したデータを失わせない）。
- マイグレーションの書き方（書き換えない、RLS と権限、台帳、控え）は [DBの変え方.md](./DBの変え方.md) にあります。

## ログインの設定

- 本番の Supabase のログイン設定は `supabase/hosted-auth.json` と `supabase/templates/` のメールに書きます。main に入ると Supabase auth settings（`.github/workflows/supabase-auth.yml`）が、まず look で本番との違いを出し、次の apply がけにーさんの GitHub での承認を待ってから本番をそれに合わせます。look が本番を読めなければ（鍵がない、401・403）、赤で止まり apply に進みません。
- PR には鍵を1つも渡さず、ファイルの形は `pnpm test:settings` が確かめます。Actions の画面から check（look だけ）と apply（look のあと承認して合わせる）を手でも動かせます。
- 何を合わせるか（コードの桁数と期限、メールの送信、回数の上限、人間の確認）は docs/09「本番の設定」にあります。

## Vercel の手の動き

`.github/workflows/vercel.yml` を Actions の画面から動かします。承認が要るものは、権限と鍵の表の `production-vercel` の動きです。

- status: ブランチの最近のデプロイと、失敗したビルドのログの末尾を見ます。
- deploy: ブランチをもう一度ビルドします（`main` は本番で、承認が要ります）。プレビューがビルド前に数秒で止まったときは deploy でやり直します。
- domains: 本番のアドレス（`booktown.page` と `www`、`vercel.app`）がそれぞれどこへ向き、DNS が合っているかと、`booktown.page` の DNS の記録を見ます。
- domains-apply: `booktown.page` をプロジェクトにつなぎ、`www.booktown.page` はそこへ送ります（308）。`book-town-851k.vercel.app` もそのまま開けます（このブラウザに残した書きかけはアドレスごとに分かれるので、送り先にはしていない）。
- mail と mail-apply: `booktown.page` からログインのメールを送るのに足りないものを見て、Resend にドメインを足し、Resend の求める DNS の記録（SPF と DKIM）と DMARC（`p=none`、知らせを受けるだけ）を Vercel の DNS に入れ、Resend の確認を待ちます。同じ名前に別の値の記録があるときは、上書きせずに止まります。

## 本番の確かめ

1. GitHub の `deployments?sha=` と、その statuses が success になるのを待ちます。
2. booktown.page は、作業環境の curl や Chrome からは開けないことがあります。開けないときは、毎朝の見張りの本番の通し（docs/09「毎日の控えと見張り」）の結果を見ます。

## 戻す

- **戻すことと消すことを分けます。** 障害への対応や変更の取り消しを理由に、利用者が保存したデータを失わせません。DB の巻き戻しと、データを消す戻し方は、けにーさんの承認が要ります（運用指針）。
- **サイトを直前の版に戻す（AUD-033）。** 画面が壊れたら、Actions の Vercel を `rollback`（branch は main）で動かします。`booktown.page` が今出している版の、ひとつ前の本番の版に戻します（Vercel の無料の段は直前の1つだけ）。rollback と promote-latest は、けにーさんの GitHub での承認を待ってから流れます（運用指針、2026-10-21）。夜中に壊れても承認まで戻らないので、DB との互換とサイトの障害を機械で確かめられるようになったら、条件を絞った自動の戻しを見直します。
  - 2つの版のあいだで `supabase/migrations/` が変わっていたら（または比べられなければ）、何もせずに止まります。DB が古い画面と合うと確かめてから、`allow_migrations` を付けてもう一度動かします。
  - 戻しているあいだ、Vercel は main を作っても公開しません（main に入ったときの ensure が警告を出す）。直したものを出すときは `promote-latest` で、いちばん新しい本番の版を公開し直します。
- **マイグレーションを戻す。** 入ったファイルは書き換えず、戻す変更を新しいマイグレーションで足します。今あるデータを移す・消す変更は、控えを取ってから行います（[DBの変え方.md](./DBの変え方.md)「移す工事の前の控えと戻す手順」）。
- **毎日の控えから DB を戻す** 手順は docs/09「毎日の控えと見張り」にあります（Supabase Pro にしてから）。
