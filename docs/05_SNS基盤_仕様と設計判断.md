# SNS基盤 — 仕様と設計判断 v0.1

更新日: 2026-10-11 / 状態: **モックで操作できる試作（1ブラウザ内）**。複数ユーザー・認証・通知は次段階。
ブランチ: `feature/sns-feed` / 実装: Claude / レビュー予定: ユーザー・ChatGPT

この文書は、ユーザーが2026-10-11に示したSNSの方向性と、それを試作するときに決めたこと・保留したことの記録です。表記は [docs/README.md](./README.md) に従います（**決定** / **有力案** / **提案** / **未決定**）。「実装済み」は、このリポジトリのモックとして動き、テストで確認したことだけを指します。

## 1. 方向性（ユーザー決定 2026-10-11）

- このサービスは、本の街だけでなく、TwitterやInstagramのように**自由に投稿・交流できるSNS**である。【決定】
- 本の感想に限定せず、**日常の出来事や雑談**も投稿できる。【決定】
- 目指す体験は「**この人の呟きが好きだから、この人が好きな本を読んでみたい**」と思える場所。【決定】
- UIはまず**一般的なSNSとして直感的に**。本の街の比喩に無理に寄せない。**スマートフォン優先**。【決定】
- 完成を急ぐより**今後拡張しやすい設計**を優先する。【決定】

既存方針との関係: [01](./01_ビジョンと設計原則.md) の「SNSには独立した入口も設ける」「通りに投稿全文を混ぜない」と矛盾しないよう、SNSは独立した入口（タイムライン）として追加し、本の街の通りには投稿を混ぜていない。

## 2. 今回の範囲

| 区分 | 内容 |
|---|---|
| **実装済み（モック）** | タイムライン（みんな／フォロー中）、投稿（テキスト・画像最大4枚・任意の本）、感想として公開、作品ページの「みんなの感想」、返信（本を添えた推薦つき）、会話ページ、いいね、読みたくなった、読みたいリストへの保存と出会い元の記録、人のフォロー、プロフィールの投稿一覧、ネタバレ保護、ネタバレ指定漏れの報告（報告者の画面のみ）、自分の投稿のネタバレ指定の追加・解除、削除 |
| **モックの限界** | 投稿・反応・フォローは**このブラウザのlocalStorageだけ**に保存。ほかの人には届かない。デモの読書家6人の投稿・反応・フォローは固定の架空データ。 |
| **次段階（別途合意）** | 認証、共有DB、複数ユーザー間の投稿・返信、通知、画像のオブジェクトストレージ、通報・ブロック・ミュート・運営モデレーション、編集、検索、おすすめ表示 |
| **対象外** | チャット／DM、課金、AI選書、外部SNS連携 |

## 3. 中心体験と画面の対応

| # | 体験（ユーザー指定） | 実装 | 画面・URL |
|---|---|---|---|
| 1 | タイムラインに読書家の投稿が流れる | 新しい順。「みんな」「フォロー中」 | `/feed/` |
| 2 | 感想から作品ページへ移動できる | 投稿の本カードから作品ページの該当感想へ（`#post-<id>`） | `/books/[id]/` |
| 3 | 作品ページに感想が集まり、返信で会話が続く | 「みんなの感想」「会話の中で薦められた本」。各感想から会話ページへ | `/books/[id]/`, `/posts/?id=` |
| 4 | 投稿者のプロフィールで好きな本・個人書店を見る | アイコン・名前→プロフィール（人生の9冊・書店・投稿） | `/profiles/[id]/` |
| 5 | 感想に「読みたくなった」を送れる | 本が添えられた他人の投稿に表示 | 各投稿 |
| 6 | 「読みたくなった」から読みたいリストに追加し、経由した感想を記録 | 反応後に「読みたいリストに追加」を提示。追加すると出会い元を保存し、プロフィールの読みたいリストに「○○さんの感想から」と表示 | 各投稿、`/profiles/me/`, `/reading-list/` |

## 4. 投稿の仕様

| 項目 | 仕様 | 状態 |
|---|---|---|
| 本文 | 2000文字まで（前後の空白は除去）。本文か画像のどちらかは必須 | 決定（上限値は仮） |
| 画像 | 最大4枚。ブラウザ内で長辺1080pxのJPEGに再エンコード（EXIF・位置情報を除去）。画像ごとに任意の代替テキスト | 決定（枚数・サイズは仮） |
| 本の添付 | 任意。添付しただけでは**感想にならない** | 決定 |
| 感想として公開 | 投稿時に「本を添えるだけ」「感想として公開する」を明示的に選ぶ。感想は作品ページにも表示。感想は本文必須 | 決定 |
| 返信 | どの投稿にも返信できる。返信にも画像・本を付けられる | 決定 |
| 返信に本 | 返信に添えた本は常に「おすすめ」。その本の作品ページの「会話の中で薦められた本」にも表示 | 決定 |
| 反応 | いいね（全投稿）、読みたくなった（本が添えられた他人の投稿） | 決定（範囲は §10 Q3） |
| フォロー | 人をフォロー。書店のフォローとは別 | 有力案（§10 Q4） |
| 削除 | 自分の投稿のみ。返信は残し、親は「削除された投稿」と表示 | 有力案 |
| 編集 | 未実装。自分の投稿のネタバレ指定の追加・解除だけ可能 | 未決定 |

## 5. ネタバレの仕様

1. 投稿者が「ネタバレを含む」を指定できる。【決定】
2. **タイムライン・プロフィールの投稿一覧では、本文と画像を表示しない。** CSSで隠すのではなく、DOMにも出さない（スクリーンリーダー・コピー・検索でも漏れない）。本（書名）は表示する。【決定】
3. 作品ページと会話ページでは「ネタバレを表示する」ボタンで、**閲覧者が自分の意思で**開ける。開いた状態は保存せず、ページを離れると再び隠れる。【決定】
4. ネタバレ投稿への返信は、祖先のネタバレ指定を**継承して保護**する。会話ページでは一度開けば会話全体が開く。【有力案】
5. **ネタバレ指定漏れの報告**: 他人の投稿をメニューから報告できる。報告すると、報告者の画面ではすぐに本文が隠れる（返信も同様）。取り消し可能。投稿者は後からネタバレ指定を追加できる。【有力案・モック】
   - 報告の送信・集計・投稿者への通知・運営の確認は**未実装**（このブラウザにだけ保存）。設計は §10 Q6。

## 6. 「読みたくなった」と読みたいリスト

[01 §5「行動と感情を混同しない」](./01_ビジョンと設計原則.md) に従い、次の3つを分けた。

| 行動 | 意味 | 公開範囲（モック時点） |
|---|---|---|
| 読みたくなった（反応） | 「あなたの言葉で読みたくなった」という**投稿者への明示的な表明** | 件数を表示（§10 Q2で要決定） |
| 読みたいリストに追加 | 自分の予定・記録 | 本人のみ |
| 出会い元（DiscoverySource） | どの投稿を**経由して**保存したか。「その投稿のおかげ」とは断定しない | 本人のみ |

- 反応を押しても自動では保存しない。押した直後に「読みたいリストに追加」「今はしない」を提示する。
- 出会い元は最初の1件だけを記録し、別の投稿から再度保存しても上書きしない。リストから外すと出会い元も消える。
- 出会い元の投稿が削除された場合は「きっかけの投稿は削除されました」と表示する。

## 7. データモデル（モック）

```ts
Post {
  id, authorId, createdAt, text,
  images: PostImage[]                 // {src, alt, width, height}
  book: { bookId, purpose: "mention" | "review" | "recommend" } | null
  spoiler: boolean
  reply: { rootId, parentId } | null  // Blueskyと同じ根元＋直接の親
  demo: boolean
}
Reaction { postId, readerId, kind: "like" | "wantToRead" }
Follow { followerId, followeeId }          // 人のフォロー
SpoilerReport { postId, reporterId }        // 報告者本人にだけ効く
TownState.wishSources: Record<bookId, { kind: "post", postId, savedAt }>
```

- **規則**: `review` はトップレベル投稿のみ・本文必須。返信の本は常に `recommend`。`wantToRead` は本のある他人の投稿のみ。これらはストア（作成時）とリポジトリ（読み込み時）の両方で検証する。
- **保存**: SNSは `book-town-sns-v1`（新規キー）、出会い元は既存の `book-town-v1` に**任意項目として追加**（旧データはそのまま読み込める）。デモデータは保存しない。
- **ID**: 自分の投稿は `mine-post-<連番>`。連番は削除しても戻さない（削除済みIDの再利用による誤った紐付けを防ぐ）。
- **画面とデータの境界**: 画面は `src/lib/social/selectors.ts` の純粋関数だけを通してデータを読む。サーバー化するときはここをクエリに置き換える。

| ファイル | 役割 |
|---|---|
| `src/lib/social/types.ts` | 型・上限値・`SocialRepository` 境界 |
| `src/lib/social/data.ts` | デモの投稿・反応・フォロー |
| `src/lib/social/repository.ts` | 保存・読み込み・レコード単位の検証・容量上限 |
| `src/lib/social/store.ts` | 操作（投稿・削除・反応・フォロー・報告）と `useSocialStore` |
| `src/lib/social/selectors.ts` | タイムライン・感想・会話・ネタバレ保護などの問い合わせ |
| `src/lib/social/image.ts` | 画像の縮小・再エンコード |
| `src/lib/routes.ts` | SNS画面のURL生成 |
| `src/components/social/` | タイムライン・投稿カード・投稿画面・会話ページ・作品ページの感想・プロフィールの投稿 |

## 8. 設計判断（レビュー用）

各判断に、採らなかった案と見直す条件を残す。

**D1. 投稿・感想・返信をひとつの `Post` 型にする**
理由: 返信にも画像・本・いいね・返信が自然に付き、「会話が続く」を同じ部品で表現できる。Bluesky・ActivityPubと同じ考え方で、将来の連携も考えやすい。
不採用: `Review` / `Comment` を別型にする案（[03](./03_Codex実装仕様_v0.1.md) の `Post` / `Reply` 分離案）。型ごとに反応・通報・削除を重複実装することになる。
見直す条件: 「本への手紙」（長期保存・読了者限定）の要件が通常投稿と大きく異なると決まったとき。

**D2. 本の添付の意味を `purpose` で明示する**
理由: ユーザー決定「本を添付しただけでは自動的にレビュー扱いにしない」をデータで保証する。表示（感想欄・推薦欄）も推測ではなく `purpose` から決まる。
不採用: 本が付いていれば感想とみなす／本文の長さで判定する。

**D3. 「読みたくなった」は反応、読みたいリストは別操作**
理由: 01 §5・§9（読みたいの行動を勝手に公開・通知しない）。反応は投稿者への表明、リストは本人の記録として分ける。
不採用: 反応と同時に自動でリストへ追加する（表明と記録が混ざり、保存したくない人も記録される）。

**D4. ネタバレ本文はタイムラインのDOMに出さない**
理由: 「通常のタイムラインにはネタバレ本文を表示しない」を、視覚だけでなく支援技術やテキスト選択でも守る。開く操作は作品ページ・会話ページに限る。
不採用: タイムライン上でぼかし・タップで開く（誤タップで読めてしまう）。

**D5. ネタバレ報告は、まず報告者本人を守る**
理由: 少人数の段階で、1件の報告で全員から隠すと濫用に弱い。一方、報告した本人が続けて目にするのは避けたい。投稿者自身が後から指定できる手段も用意した。
未実装: 投稿者への通知、件数による自動非表示、運営確認（§10 Q6）。

**D6. SNSのデータは別キー・容量上限つきで保存する**
理由: 既存の書店・プロフィール・読みたいリストを壊さない。画像はlocalStorageを圧迫しやすいため、SNSキーに2,000,000文字の上限を設け、同じオリジンの町の保存領域を残す。上限やブラウザの容量超過のときは投稿を**受け付けない**（メモリだけに残して再読み込みで消えるより、その場で伝える）。保存自体ができない環境（プライベートモード等）は町と同じくメモリで動き、警告を出す。

**D7. 投稿のURLは `/posts/?id=`**
理由: 現在は `output: "export"` の静的サイトで、ブラウザで作った投稿は `generateStaticParams` で事前生成できない。URL生成を `routes.ts` に集約し、サーバー導入時は `/posts/[id]` に1か所の変更で移れるようにした。

**D8. 画像はブラウザで縮小・再エンコードする**
理由: 保存容量の節約と、写真の位置情報（EXIF）を保存前に取り除くため。サーバー導入後もアップロード前の縮小として残せる。
制約: HEICなどブラウザが読めない形式は追加できない（メッセージを表示）。GIFアニメーションは静止画になる。

**D9. 人のフォローと書店のフォローを分ける**
理由: 投稿を追いたい相手と、棚の更新を追いたい書店は一致しないことがある。データは別にし、プロフィールでは「フォロー」と「書店をフォロー」を並べた。統合するかは §10 Q4。

**D10. タイムラインは新しい順、終わりを正直に見せる**
理由: 推薦アルゴリズムの方針（[03](./03_Codex実装仕様_v0.1.md)）は未決定。デモの反応・フォローはデモの読書家同士のものだけで、件数を水増ししない（01 §8）。

**D11. 時刻は日本時間の絶対表示**
理由: 静的に生成したHTMLと閲覧時の表示を一致させる（相対表示「3分前」は生成時と閲覧時でずれ、ハイドレーションエラーになる）。

**D12. `/` は本の街のまま、ナビに「タイムライン」を追加**
理由: 既存の体験とテストを壊さない。どちらをホームにするかはユーザーが触って決める（§10 Q1）。

**D13. デモ投稿の書き方**
架空の読書家のものとして「デモ」と表示する。作品への言及は独自の感想で、引用や具体的な筋書きの断定を避けた。

## 9. 次の段階への移行メモ

| 現在（モック） | 次段階の想定 |
|---|---|
| `ME_ID = "me"` 固定 | 認証済みユーザーIDに置き換え。`SocialPersonalData` は「自分の行動」をサーバーへ送るキューとして再利用できる |
| `SocialRepository`（同期・localStorage） | 非同期のサーバーアダプタ。楽観的更新と失敗時の巻き戻し（`commit` が成功時のみ反映する現在の形を踏襲） |
| `selectors.ts` が全件をフィルタ | タイムラインはカーソル方式のページング、作品ページの感想はサーバーで絞り込み |
| 画像はdata URL | オブジェクトストレージのURL。`PostImage.src` の型はそのまま |
| `/posts/?id=` | `/posts/[id]`（`routes.post` だけを変更） |
| 報告はブラウザ内 | `spoiler_reports` テーブル、状態（未確認・対応済み）、運営画面 |
| 通知なし | 返信・いいね・読みたくなった・フォローの通知と受信設定（01 §9） |

DBの叩き台（未確定）: `posts`（`reply_root_id`, `reply_parent_id`, `book_id`, `book_purpose`, `spoiler`）、`post_images`、`reactions`（`post_id, reader_id, kind` が主キー）、`follows`、`spoiler_reports`、`wish_sources`。

## 10. 未解決の問題（ChatGPTとのレビュー論点）

**Q1. ホームとナビゲーション** — `/` を本の街とタイムラインのどちらにするか。現在のナビ順は「本の街・タイムライン・わたしの書店・プロフィール」。

**Q2. 「読みたくなった」の見え方** — 件数を全員に見せるか、投稿者だけにするか。誰が押したかを投稿者に見せるか。通知するか。01 §9「読みたいの行動を勝手に公開・通知しない」は、明示的な反応にも及ぶか。

**Q3. 「読みたくなった」を付けられる投稿** — 指示は「レビューに」。モックでは、本を添えただけの投稿と、本を薦める返信にも付けられるようにした（「この人の呟きで読みたくなった」を拾うため）。感想に限定すべきか。

**Q4. フォローの統合** — 人と書店のフォローを分けたままにするか。プロフィールに似たボタンが2つ並ぶ問題。

**Q5. ネタバレの開き方** — 読了登録したら自動で開くか。作品単位で「この本は読了済み」を設定できるか。開いた状態を覚えるか。シリーズ物で書名自体がネタバレになる場合、本の表示も隠すか。

**Q6. ネタバレ報告の運用** — 何件で全員から隠すか。投稿者に通知するか（報告者は匿名か）。濫用・嫌がらせへの対策。ネタバレ以外の通報（誹謗中傷・著作権）と同じ仕組みにするか。

**Q7. 会話の表示** — 現在は会話ページでフラット表示（返信先の名前を表示）。ツリー表示にするか。作品ページで感想の下に返信を数件見せるか。

**Q8. 投稿の編集** — 本文の編集を許すか、履歴を見せるか。「感想として公開」を後から付け外しできるか。

**Q9. 上限値** — 本文2000文字・画像4枚・長辺1080pxは仮。読後の長い感想（「本への手紙」）を考えると本文は足りるか。

**Q10. タイムラインの並び** — 時系列のみ。少人数の時期に古い会話や反応の少ない投稿をどう再び見せるか（03の推薦フェーズとの接続）。

**Q11. 匿名投稿** — 01 §9 は匿名投稿を個人書店に結び付けないことを定めている。匿名で投稿できる場を作るか。作る場合、タイムラインとの関係は。

**Q12. 作品ページの構成** — 「みんなの感想」を既存の「この本を並べている書店（POP）」より上に置いた。POPと感想の関係（POPも投稿の一種にするか、出会い元に `pop` を加えるか）。

**Q13. 削除と退会** — 返信を残してtombstoneにする方式でよいか。退会時に投稿と返信をどう扱うか（01 §9「本人が削除した痕跡を不必要に残さない」）。

**Q14. 未ログイン閲覧** — 読むだけは未ログインで可能にし、投稿・反応時に登録を促すか（03の有力案）。

## 11. 既知の問題（今回の変更以前から）

- 静的エクスポート（`out/`）を素の静的サーバーで配信すると、Next.jsのセグメントprefetch（`__next.<segment>.__PAGE__.txt`）が404になる。ビルドは `__next.<segment>/__PAGE__.txt` という階層で出力する。`main` のビルドでも同じで、画面遷移自体は動く。本番のホスティングでの扱いを確認したい。
