# 検索

本・読書家・書店・タグの検索の正本です。だれの本が検索に出るか（読める本だけ）は [公開範囲.md](./公開範囲.md)、目録の大きさでの速さは [本と書誌.md](./本と書誌.md)「図書館の目録」にあります。docs/09 から移した節です。

## 本の検索（第1段・第2段、2026-10-13）

設計の全体は共有フォルダの「検索_設計_2026-10-13.md」（PR-1〜7）にある。ここには、いまのコードが守っている決まりだけを書く。

- **文字は1つの「たたみ方」でそろえてから比べる**（`src/lib/search/fold.ts` の `searchFold`）。全角と半角、ひらがなとカタカナ、小さい字、長音（とうきょう・トーキョー）、助詞の「は」と「わ」、旧字（`itaiji.ts`）を同じに読む。ロケールに頼る手順は使わないので、あとでデータベースでも同じたたみ方をくり返せる。打った言葉がローマ字なら、打っている途中でも、かなとしても読む（`romaji.ts`。tokyo は「ときょ」、最後の n は「ん」とも、な行の始まりとも読む）。
- **本の並びは、合い方の種類で決まる**（`rank.ts` の `MATCH`）。ISBN、題名そのもの、題名の始まり、題名の途中、著者、すべての語、1字違いの題名、それ以外の順。同じ種類の中では、打ったとおりの書き方を先にし、街での目立ち方（公開の棚・投稿・読みたくなった、`presence.ts`）はわずかに並びを動かすだけで、数として画面には出さない。
- **4字以上で探したときの1字違い（10字以上なら2字まで）の題名は、合った本として後ろに並べる。字面が近いだけの本は「近い題名の本」として分けて出す**（著者が近いときは「著者名が近い本」）。近い本は合った本とは混ぜない。見出しは小さいが、読める濃さ（4.5:1 以上）にする。
- **本を選ぶ欄の Enter は、確かなときだけ1冊を取る**（`surePick`）。題名の始まりまで合っているか、合う本が1冊だけのとき（1字違いの題名1冊も含む）。「近い題名の本」は Enter で取らない。かな漢字変換を確定する Enter は無視する（`enterPressed`）。投稿に添える本、本屋を開く、読書、本棚の編集、人生の9冊、店内の飾りつけ、ポスターの本は、どれも同じ探し方（`useBookSearch`）を使う。
- **読み**: 本は題名と著者の読み（`titleReading`・`authorReading`、出どころつき）を持てる。見本の本には読みを入れてある。登録した本に openBD などから読みを付けるのは第3段で、まだしていない（読みを持つのは見本の本だけ）。ログインできるビルドで、街にない本も目録まで含めて探すのは、下の「DB で探すもの・数えるもの」の `find_books` でしている（2026-10-19、6b）。
- **読書家と書店も同じたたみ方で探す**（`text.ts`、`town.ts`）。同じ種類の合い方の中では、長音や「は」をたたまずに合うほうを先にする（「ゆき」では、ゆき が ゆうき より先）。読書家は名前と @ID だけ（自己紹介では探さない）。@ID がローマ字なら、かなで打っても見つかる（凪 @nagi は「なぎ」、@shinya は「しんや」）。@ で始めると、読書家も書店も @ID だけを、書いたとおりに見る（@mio2 は @mio_2 ではない）。書店は店の名前、店主（名前と @ID）、店の紹介の順に並べ、最後に公開の棚にある本で探す。通報でたたんだ店の紹介は、見えないのと同じく探す対象にもしない。
- **タグは、同じ言葉の書き方の違いだけを1つにまとめる**（`textKey`）。かなとカタカナ、全角と半角、大文字と小文字、長音の記号（#ミステリ・#ミステリー・#みすてり・#ﾐｽﾃﾘ）。検索のたたみ方とは違い、「は」と「わ」や「へ」と「え」はまとめない（#へび と #えび は別のタグ）。ローマ字で探すと、かなのタグが見つかる（misuteri で #ミステリ）が、ローマ字で書いたタグ（#misuteri）は別のタグのまま。人気のタグは「そのタグを書いた投稿の数」で並べる（1つの投稿は1回）。
- **検索の結果に数は出さない。** 見出しにも件数を付けず、合うものがないときは言葉で伝える（街の検索の読み上げも「まだ見つかりませんでした」と言う）。
- **ログインできるビルドの検索の画面は、DB にも聞く**（2026-10-19、6b）。街にない本も、読める本なら見つかる。並べ方はここの決まりのまま。詳しくは下の「DB で探すもの・数えるもの」。
- 確かめるのは `pnpm test:search`（`tests/search.test.ts` と `tests/search-text.test.ts`）と、ブラウザの通し確認（`test:app` ほか）。DB の側は `tests/db-search.test.ts`。

## DB で探すもの・数えるもの（2026-10-19、管理表 6b・6c）

docs/09「街を読む関数」から移した。

- **本の検索と気持ちは DB で探す**（6b、マイグレーション `20261113000000_search_in_database.sql`、2026-10-19）。
  - 検索の画面は、打つ手が止まって0.3秒たつと、打った言葉を DB にも聞く（`TownBackend.more({ search })`、関数 `find_books`）。DB は、読む人が読める本の全部から探す（街が読んだ新しい300冊と行が指す本だけではない）。並べるのは今までどおりアプリで、街で見つけた本と DB が見つけた本を一緒に `rank.ts` で並べる（`useBookSearch` の `extra`）。街がもう持っている本（同じ ID か同じ ISBN）と、自分の本があるほかの人の本は足さない。答えが来るまでは街の本だけで出す。
  - DB は、本ごとに題名と著者のたたんだ字の2字の組（`private.book_grams`、アプリの `bookGrams` と同じ作り方で、それより少なくはしない）を持ち、本を書くたびにトリガーが作り直す。アプリが送るのは、打った言葉の形ごとの2字の組と、いくつ合えばよいか（`databaseSearch`、`queryGrams`）。全部の組を持つ本を先に、足りないときだけ近い題名の本を探す。数えたり切ったりするのは、読む人が読める本だけ（2026-10-19、マイグレーション `20261114000000_search_candidates.sql`）。`private.search_candidates` が、目録の本と自分の本は「読める」、ほかの人の手で入れた本は、それを名指す行のうち本の決まりが見せうるもの（9冊、公開かフォロワーに見せる記録か自分の記録、ひとり読みでない投稿か自分の投稿、公開したポスターか自分のポスター、一緒の読書か自分の読書、自分の印や本棚や出会い、持ち主の店の公開の棚と店内）があるものだけを「本の決まりを聞く」として残し（2026-10-19、`20261117000000_search_candidates_shown.sql`。本人だけの記録がある見えない本1万冊に当たる検索が、作った街で約20秒から約0.2秒に）、ほかは索引を数回引くだけで外す。残った本は、並べる順に本の決まり「books are seen where they are used」と同じ問いを聞き（2026-10-19 から100冊、200冊…ずつまとめて、`private.keep_seen_books` と `private.seen_book_ids`、AUD-160）、版ごとに1冊（自分の本を先に）、100冊になったら止める。全部の組を持つ本はどれも同じ点なので、自分の本・目録の本・古い順に、500冊、1000冊…と切って見ていく。答えは読む人が読める本だけで決まる（`tests/db-search.test.ts`「見えない本があってもなくても同じ」）。作った街で、だれも読めない本2万冊に当たる検索が約4.1秒から約0.16秒、ふつうの検索が約145msから約82msになった。`private.book_grams` は関数のほかだれも読めない（見えない本の題名が分かるため）。たたみ方は `private.fold_book_loose`（`kanaFold`）と `private.drop_long_vowels`（`dropLongVowels`）に分け、`fold_book_text` はその2つを続けたもの（たたみ方は変わらない）。
  - 検索の気持ちの一覧（`felt_in_town`）と、気持ちを選んだときの記録（`feeling_records`）は、その気持ちの記録を索引（`reading_entries_felt`）で新しい順に100件ずつ見つけ（`private.felt_page`、ID と時刻だけ）、読む人として読めるものだけを使う。だれにもない気持ちは索引を1回見るだけで済む。前は、どれかの気持ちがまだだれにもないあいだ、検索を開くたびに見られる記録を全部読んでいた（作った街で記録5,000件に約1.1秒、5万件で約12秒。今は約30ms）。
  - 6c（マイグレーション `20261116000000_felt_seen_first.sql`）から、`private.felt_page` は読む人に見えるかもしれない記録だけを出す。だれにでも見せる記録（索引 `reading_entries_felt_everyone`）、フォローしている人がフォロワーに見せる記録（自分のフォローからたどる）、自分の記録の3つで、決まりが見せる記録はどれもこの中にある。前は見えない記録もページごとに試していたので、その気持ちの記録がほとんど見えないとき（本人だけの記録2万5千件）は、訪問者で `felt_in_town` 約1.8秒、`feeling_records` 約1.9秒かかった。今は約0.14秒と約13ms（PGlite の数で、本番の数ではない）。ブロックし合った人と運営が隠した人の記録はまだこの中にあり、ページごとに読み飛ばす（隠した人がだれにでも見せる記録をとても多く持つと、その分だけ遅くなる。候補を出す前に人ごとに確かめると、ふだんの気持ちの一覧が遅くなるので、今はしない）。
  - 関数のない DB では、アプリは街の本だけを探し、気持ちの記録は前の読み方で読む。
  - 確かめは `tests/db-search.test.ts`（アプリが本を並べる組をどの本も DB が持つ、作った本の集まりにいろいろな問いを出してアプリが見つける本を DB も見つける、読めない本を返さない、版ごとに1冊、ISBN、トリガー、気持ちと記録が表から読めるものと同じ、権限、戻す SQL）と `tests/town-view.test.ts`（街にない本を検索で読む、関数のない DB）。
  - 読書家と書店の検索は、まだ街が読んだ全員と全店から探す（街が全部を読んでいるため）。全部を読むのをやめる新1で、読書家と書店も DB で探す。タグの検索は街の新しい便り500件から探す。
- **数は DB で数える**（6c、マイグレーション `20261115000000_counts_in_database.sql`、けにーさん 10-18「街の数と一覧は全期間」）。
  - 検索の「多くの棚に並ぶ本」「話題の本」「棚の隅の本」は、本ごとに、開いている書店の公開の棚のうちその作品の本を置く棚の数と、その作品について話す便り（返信を含む、一人読みは数えない）の数で選ぶ。前は街が読んだ新しい便り500件と全店から数えていたので、それより前に話された本は話されていないように見えた。今は DB が作品ごとの数を `private.work_counts` に持ち（だれの列もない。関数のほかだれも読めない）、便りを書く・動かす・消す、棚を変える、店を開く・閉じる、本が作品を移る・消える、運営が隠す・通報で保留になる（隠れ方が変わったときだけ）、のたびに、トリガーがその書き込みで増えた分と減った分だけを足す。作品を数え直さないので、同じ本を登録した人が何人いても、書き込みの重さはその書き込みが触った分だけ（作った街で同じ作品の本300冊・300店のとき、便り1つ・棚の保存・店を閉じる・プロフィールを隠すはどれも約5ms。前の形は約0.1〜1.4秒だった。PGlite）。足すのは作品の順なので、同時の書き込みでも数は消えず、待ち合いで止まらない。毎晩3:30（日本時間）に `private.recount_all` が行から全部を数え直して、ずれた分を直す（隠すのと同時に書いた便りなど）。数は読むときに0より下にしない。書き込みが数のせいで断られることはない。運営が隠したものと保留のものは数えない。
  - 検索を開くと、アプリは関数 `town_counts(books, top)` に街の本（`booksBeforeSearch`、最大1000冊）を送り、その本の数と、いちばん棚に並ぶ作品・話される作品（それぞれ12まで）を受け取る（`TownBackend.more({ counts: true })`、`countsFromAnswer`）。読む人として動き（security invoker）、読めない本の数は返さない。ブロックし合った人の分は、その人たちの便りと店からその場で数えて引く。上位の作品は、読む人が読めるその作品の本（自分の本、目録の本、新しい便りの本、開いた店の公開の棚の本の順）で返し、アプリは街のその作品の本で出す（街にない作品は出さない）。見本の本と見本の書店・便りの数は今までどおりアプリで数えて足す（`bookSignals`）。DB に聞いていない本（検索を開いたあとに来た本、1000冊より後ろの本）は、街が読んだ分で数える。
  - 「読みたくなった」は数えない。便りに読みたくなった人の数は書いた本人にしか見えないので、今までどおり街が読んだ分から数える。
  - 関数のない DB では、アプリは街が読んだ分で数える（前と同じ）。
  - まだ街の分で数えるもの: タグ（新しい便り500件から）、本のページの感想の「残りN件」、プロフィールの「N 便り」、本を置く書店の名前（新1）。人生の9冊の重なりはまだ機能がない。
  - 確かめは `tests/db-counts.test.ts`（前からある行を数える、読む人ごとに表から数えた数と同じ、読めない本は答えない、トリガーが書き込みのたびに合う、ブロック、上位の本と順、まとめての書き込みと退会、毎晩の数え直しがずれを直す、だれも表を読めず関数の権限、戻す SQL）、`tests/town-view.test.ts`（街の窓より前の便りも数える、関数のない DB）、`login-journey`（検索を開くと数を聞き、読めない本は送らない）。
